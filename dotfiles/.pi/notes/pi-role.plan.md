# pi role — 要件メモ

セッションに **権限ロール** を持たせ、ハードブロックとソフト誘導の両方で振る舞いを制限する。

委譲の本質は **別プロセス／別セッションの pi**。親コンテキストを薄く保ちつつ、既存 skill を別セッションで使う。

## 背景・動機

- Pi（Mario）の思想では、コアに巨大なサブエージェント機構を載せない。必要なら外付けする
- 欲しいのは「オーケストレータ製品」ではなく、**席（role）に権限が付いている**こと
- 委譲の本質は専用製品ではなく、**別プロセス／別セッションの pi**
- `pi-subagents` のようなフル装備は、今の目的には厚すぎる可能性がある
- 親のコンテキストを汚染せずに専門作業を進めたい
- 無限委譲や、指揮役がファイルを読みすぎてコンテキストが膨らむのを防ぎたい
- 親が渡す粒度は implement / test / code-review 程度の粗さになりがちで、内側の専門分解まで親が管理するのは現実的でない。そのため **最大3ロール階層（orch → manager → worker）** までの委譲を許し、中間の分解は manager に任せる
- 専門性はペルソナ agent ではなく **skill** に置く
- 収束ループなどの指揮手順は、role が揃えば skill / AGENTS.md だけで足せる

## ゴール

- セッションが常に1つの role を持つ（デフォルト manager）
- role に応じて委譲・ファイル読み書きを **extension が機械的に制限**する
- role 別の短いプロンプトでソフトにも方向を与える
- 力量・権限不足時は上位者へ報告する
- orch が判断・指揮し、重い読み書き・レビュー・調査などを manager / worker に任せられる
- manager は必要なら専門作業を worker セッションに分けられる
- ユーザーには manager・worker の進行がすべて見える
- 呼び出し元モデルには直下の子の最終結果（必要なら要約・成果物参照）だけが返り、中間ログでコンテキストが膨胀しない
- ペルソナ用エージェント体系は作らない。専門性は既存／今後の **skill** に置く

## 非ゴール

- reviewer / implementor / scout / oracle などの専門ペルソナ一覧
- `pi-subagents` 相当の async / retry / watchdog / 多段 chain DSL を最初から作ること
- モデルに入口ロールを選ばせること
- ソフト（プロンプト）だけで権限を守ること
- 子セッション種別や skill↔作業の対応表を人手で事前設計すること
- すべての作業を必ず別セッションに出すこと
- orch が子の結果を見ずに丸投げすること（ファイル直読み書きはしないが、戻り値は見る）
- 無制限の再帰委譲
- find / use を role 権限表に載せること（当面対象外）

## ロールと権限

| ロール (EN) | ロール (JA)      | 委譲                  | ファイル読み書き                 | 子の戻り値 |
| ----------- | ---------------- | --------------------- | -------------------------------- | ---------- |
| orch        | オーケストレータ | manager / worker へ可 | **不可**（ツールで直接開かない） | 見る       |
| manager     | マネージャ       | worker へ可           | 可                               | 見る       |
| worker      | ワーカ           | **不可**              | 可                               | —          |

許可する委譲遷移:

- orch → manager
- orch → worker（単純作業の直接委譲）
- manager → worker

拒否する例:

- worker → 誰か
- manager → manager / orch
- orch → orch

意図:

- **orch** — 判断・指揮・収束判定・結果の解釈・ユーザー対話。実ファイルの読み書きはしない。子の戻り値は見る
- **manager** — 読んで書いて進める。内側の専門分解が必要なら worker に分ける
- **worker** — 渡された指示／skill で作業する末端。再委譲しない
- 無限再帰は worker の委譲不可（および不正なロール遷移の起動拒否）で機械的に止める

これらは **権限ロール** であり、職種ペルソナではない。「reviewer エージェント」のような職種ロールは作らない。「適切な skill を読ませた別セッション」で足りる。

## 入口ロール

- デフォルトは **manager**
- **orch はオーナーが明示したときのみ**（エージェントは入口ロールを選ばない・昇格しない）
- 実現: 起動後 `/orch`（pi extension の `registerCommand`）
- `/new` 等の `session_start` では manager に戻す
- 途中で orch が必要なら、同じセッションでの黙昇格ではなく、オーナーが `/orch` する（または方針として開き直す）

## エスカレーション

規則は1本:

**自分の権限や力量を超えたら、上位者に報告する。権限外の手段を黙って取らない。**

上位者は「今だれに呼ばれているか」で決まる:

| 今の席  | 上位者                                            |
| ------- | ------------------------------------------------- |
| worker  | 呼んだ manager / orch。オーナー直呼びならオーナー |
| manager | 呼んだ orch。オーナー直呼びならオーナー           |
| orch    | オーナー                                          |

オーナーが manager / worker を直接使っているときは、報告先がオーナーになるだけでよい。特別分岐を増やさない。

## 観測の非対称（重要）

- **ユーザー向け:** manager・**worker を含む**全委譲セッションの出力をストリームまたは同等の可視性で見せる
- **呼び出し元モデル向け:** 最終的な戻り値（要約、成否、成果物パス、要点など）だけを渡す
  - orch ← manager / worker: 生ログ全部は orch コンテキストへ流し込まない
  - manager ← worker: 同様に、worker の生ログ全部は manager コンテキストへ流し込まない（要点だけ）
- ユーザーへの可視性と、モデル間のコンテキスト分離は両立させる

## 委譲の粒度

- **固定のセッション種別（実装用／レビュー用など）は作らない。** そのロールの主体が都度決める
- orch の目安: implement / test / review / 調査など粗粒度。小さなお願いや一行修正は委譲しないこともある（ただし自身はファイルを直接触らないので、触るなら manager / worker へ）
- manager の目安: 同じタスク内で専門領域が分かれ、コンテキスト分離の価値があるときだけ worker を出す。同じセッション内の skill だけで足りるならセッションを増やさない
- 実装・テスト・レビューを毎回すべて別セッションで回す必要はない。状況に応じて省略・結合してよい
- 判定の目安（AGENTS.md に短く書く）:
  - コンテキストが膨らみそうか
  - 新鮮な文脈が効くか（特にレビュー）
  - 戻り値が呼び出し元で解釈できるか
  - 1 skill で完結しそうか／複数工程をまとめた方が安いか
  - （manager）専門分解が orch の管理範囲を超えているか

## project instructions（AGENTS.md）の方針

常時方針は skill より **AGENTS.md（または同等の project instructions）** に書く。「欲しいタイミングで発火しない」問題があるため。長い指揮手順が後から必要になったら、任意の skill として足せばよい。

含めるべき趣旨:

- 大きめの実装・レビュー・調査では別セッション委譲を検討する
- orch は子の結果と必要な要点は把握する（ファイル直読み書きはしない。盲目委譲もしない）
- 小さい作業は委譲しないこともある
- セッション単位は固定せず、コンテキスト分離の価値で都度決める
- 権限ロールは orch / manager / worker。委譲とファイル読み書きの表に従う

書かない／避けたいこと:

- 「子の結果も見るな」といった極端な禁止（ファイル直アクセス禁止とは別）
- 長大なオーケストレーション手順の全文
- skill↔作業の固定対応表や専門ペルソナ一覧
- 将来変わりやすい起動コマンドの詳細な固定
- 利用 skill の網羅リストの焼き込み

## 既存 skill の再利用

- 既存 skill（例: mattpocock/skills の `code-review`）を別セッションで使うことを第一選択とする
- 他エージェント向け前提（例: Claude Code の Agent tool 前提）が含まれる skill は、pi 上でそのまま動かない部分があり得る。必要なら薄い補足・ラップで吸収し、審査観点自体は活かす
- 新しい専門ペルソナ md を量産するより、既存 skill の再利用・必要なら人手での調整を優先する
- プラン本文や AGENTS.md に、利用 skill の網羅リストを焼き込まない

## ハードとソフト

| 層     | 担当                                      | 内容                                                                            |
| ------ | ----------------------------------------- | ------------------------------------------------------------------------------- |
| ハード | role extension                            | `tool_call` で禁止ツールを block。委譲ツールで遷移チェック・子ロール伝播        |
| ソフト | 同じ extension が role 別プロンプトを注入 | 振る舞いの方向（委譲方針・エスカレーション・orch はファイルを自分で開かない等） |

ソフトだけに頼らない。ハードが柵、プロンプトが道順。

ロール別プロンプトは短く保つ（長文ペルソナ化しない）。指揮の長い手順が必要なら **skill** に置く。オーケストレーション skill は必須ではない。

## 実現方針（extension）

仮称: role extension（名称は実装時に決めてよい）

### 状態

- セッションメモリ（extension のクロージャ等）に `role` を持つ
- 初期値 / `session_start`: `manager`
- `/orch`: `role = orch`（通知・status 表示など）
- 任意で `/manager` で戻してもよい

### 誰がいつ権限判定するか

| タイミング                   | 誰                        | 何をする                                |
| ---------------------------- | ------------------------- | --------------------------------------- |
| `session_start`              | extension                 | `role = manager`                        |
| `/orch`                      | command handler           | `role` を書き換え                       |
| 毎 turn の `tool_call`       | 同じ extension            | 禁止ツールなら `{ block: true }`        |
| 委譲ツール `execute`         | 委譲ツール（role を参照） | 遷移チェック → 子にロールを渡して spawn |
| （任意）`before_agent_start` | 同じ extension            | 現在 role の短い指示を system に足す    |

**権限の真実は extension の `role` 値。** モデルに自己申告させない。

### 子セッション

- 別プロセスなので、起動時にロールを env 等で渡す（名前は未決）
- 子側 extension がその値を読んで同じハード／ソフトを適用
- worker には委譲ツールを出さない、または呼んだら拒否

### orch と skill の分担

- **role extension**: 席・権限・`/orch`・ブロック・ロール別の短い誘導
- **skill / AGENTS.md**: 収束ループの手順、いつ委譲するか等のプレイブック
- **薄い委譲ツール（名称未定）**: 別 pi の起動・ロール伝播と権限チェック・ユーザー向けストリーム・呼び出し元向け戻り値の切り出し
- orch **専用** extension は作らない

## 要件

### R1. ロール状態

- 対話セッションは常に role を1つ持つ
- デフォルト manager。`/orch` で明示切替
- `session_start` で manager にリセット

### R2. ハード権限

- orch はファイル読み書きツールを使えない（block）
- 委譲は許可遷移のみ。それ以外は拒否
- worker からの再委譲は拒否

### R3. ソフト誘導

- role 変更後、次 turn からロール別の短いプロンプトが効く
- エスカレーション方針（上位者へ報告）を含める

### R4. 委譲との接続

- 既存／今後の薄い委譲手段が、呼び出し元 role を見て子 role を付ける
- 下位には、実行してほしい skill やタスク内容を渡せることを優先する

### R5. 観測の非対称

- ユーザーには manager・worker を含む全委譲セッションの進行が見えること
- 呼び出し元モデルには最終戻り値（要点）だけを渡し、生ログ全部は流し込まないこと

### R6. project instructions

- AGENTS.md 等に、短い委譲方針（粒度・ロール権限・盲目委譲しないこと）を置くこと
- 長大なオーケストレーション全文や skill 固定対応表は置かないこと

### R7. 既存 skill の再利用

- 既存 skill を別セッションで使うことを第一選択とすること
- 他エージェント前提の skill は必要なら薄いラップで吸収し、観点自体は活かすこと

### R8. 最小実装

最初に揃えるもの:

1. セッション内 `role`（デフォルト manager）
2. `/orch`
3. orch のファイルツール block
4. 委譲のロール伝播と遷移チェック
5. ロール別の短いプロンプト（エスカレーション一文を含む）
6. ユーザーへの可視化と、呼び出し元への戻り値分離
7. AGENTS.md 等への短い委譲方針

あとでよいもの:

- `/manager` への戻し
- find / use のロール別制限
- 指揮用の本格 skill
- UI でのロール常時表示の洗練
- 並列実行・非同期ジョブ管理・高度な TUI

## 成功条件

- 普段の `pi` は manager として読み書き・必要なら worker 委譲ができる
- `/orch` 後はファイル直アクセスできず、manager / worker へ委譲して指揮できる
- orch のコンテキストが、manager・worker の中間作業で過度に膨胀しない
- ユーザーは manager・worker の出力を追える
- worker から無限に委譲が生えない
- 権限外の委譲が起きない
- 小さな作業まで強制委譲されない
- レビューや大きめ作業を、skill 付きの別セッションで回せる
- 力量不足時に上位者（オーナー直ならオーナー）へ報告する方針がプロンプトに載る
- orch 専用 extension なしで運用できる
- `pi-subagents` なしでも、日常の実装〜レビュー循環が回る

## 未決

- extension / コマンドの正式名称
- 子へのロール伝播方法（環境変数名など）
- ファイル系ツールの具体的な block 対象リスト（read / write / bash 経由などどこまで見るか）
- `/manager` を用意するか
- ロール別プロンプトの文言の最終形
- 指揮 skill を最初から用意するか、AGENTS.md の短文だけにするか
- 委譲インターフェースの正式な名前・引数形
- 戻り値の形（純テキスト / 成果物ファイル / 両方）
- ユーザー向けストリームで manager と worker をどう区別表示するか
- AGENTS.md に書く文言の最終形

## 参考にした判断

- 制限の本体は「何段目か」より「席に付いた権限」
- 入口はデフォルト manager、orch はオーナーオプトイン
- ハードが柵、ロール別プロンプトがソフト誘導
- エスカレーションは「上位者へ報告」の1規則
- 専門性は skill。role は権限だけ
- 委譲の本質は別セッションの pi。フル装備の subagent 製品は後回し
- 文脈制御の肝は「人には見せる、モデル間には要点だけ」
- セッション単位は事前設計せず、コンテキスト分離の価値で都度決める
- 発火信頼性のため、常時方針は skill より AGENTS.md
- skill 一時利用などは関連: `pi-orch.plan.md`
