# AGENTS.md

## 動作

- チャットでは必ず日本語で回答すること
- プログラミングのソースコードでは必ず英語を使用すること
- 実装・編集を行うのは、成果物を伴う動詞(実装・編集・修正・追加・削除・リファクタ・変更など)による明示的な指示のときだけ。「直せる？」「やってくれる？」「～お願い」「～して」等の依頼表現も指示に含む
- 「～してほしい」「～と思う」「～と思っている」「～かな」「どう思う？」等は意志表明・意見募集であり指示ではないので相談として扱い、実装しない
- 質問・相談には回答のみを行い、明示的な指示がない限りファイルを編集しない。判断に迷ったときは実装せず確認を返す
- チャットで markdownコードブロック を出力するときは、それを4 backticks で囲み。markdown以外のコードブロックは3 backticks で囲う

## オーナーへの質問

確認が必要なときは、番号付きの質問にして、質問文が単独で yes/no で答えられる形になるようにする。オーナーの認知コストを下げることが目的。

- 回答記号は `y`=yes / `n`=no（小文字）とする
- 2択の質問は `y/n` で答えられる形にする（例: 「この実装で進めてよい？ (y/n)」）
- 3択以上になるときは、推奨または予想される選択肢を質問文に組み込んで yes/no 判定可能にする。`y` は推奨案への同意を指し、それ以外を `a`, `b`, `c` に振る。`y` 含む全選択肢を行で併記する。

  例:
  ```
  2. テストは vitest でいいですか？ (y/a/b)
     (y) はい
     (a) jest
     (b) node:test
  ```

## 技術スタック

- `python`は直接使わずに `uv` 経由で使う。独立した単一スクリプトは先頭に PEP 723 インラインメタデータを入れ、`pyproject.toml` 不要で `uv run script.py` だけで実行できるようにする。
- タスクランナーは基本的に `just` を使う。ただし JS プロジェクトの場合は `package.json` の npm-scripts を使う。
- JS/TS のパッケージマネージャー（pnpm, bun, vp 等）はプロジェクトごとに確認。
- 上記で規定されていない事項は都度確認。

## テスト

テストコードは品質保証判定の最終成果物であり、自然言語に近い読みやすさが求められる。テストでは常に可読性を優先する。
以下は可読性を上げるためのルールである。

- 変数名は、入っているデータを具体的に名詞で表す。`data` `info` `value` のような中身が不明な名前は避ける。
- コメントは原則禁止。変数名などソースコードで意味が理解できるようにする。ただし、イレギュラーな処理などに対するwhyの説明部分のみコメントは許される。
- 1つのテスト単位（it/test）では1つの確認に絞る。複数ケースは別テストに分ける。
- assert では説明変数を優先し、何と何を比較してどうなっているかが自然言語の感覚で読めるようにする（自明な場合は省略してよい）。

## 編集前の確認

ファイルを編集する前に必ず read し、対象ファイルの現状を確認する。会話途中で読んだ内容や以前の read 結果を記憶で信用して編集せず、常に最新の read 結果を正とする。記憶と現状が乖離している場合は現状に合わせる。

## 品質管理

編集後は必ず該当するリンター、フォーマッター、タイプチェック、テストを実行すること。プロジェクトに既存の設定・依存があればそれを優先し、なければ以下のデフォルトを使う。

- **Python**: `ruff format`, `ruff check`, `ty`, `pytest`
- **JavaScript/TypeScript**: (`vp format` or `oxfmt`), (`vp check` or `oxlint`), `vitest`

## 調査タスク

検索結果・ウェブサイト・コードベース（リポジトリ・ファイル・関数など）など、何かを説明・言及・引用するときは、該当箇所へクリックでジャンプできるリンクを必ず添える。

- ウェブ上のものは markdown link（`[text](url)`）
- ローカルファイル・コードベース内は平文のパス（markdown link にしない）

## 完了報告

成果物を伴う作業の完了時は、次の形式で報告する。内容がないセクションは省略する。

```markdown
## 結果

[依頼に対して完了したことを記述]

## 変更

- `path/to/file`: [変更内容]

## 検証

| 種別 | 実行内容 | 結果 |
|---|---|---|
| format | `...` | passed |
| lint | `...` | passed |
| test | `...` | passed |

## 補足

- [判断理由、制約、未解決事項など]
```

- `結果` は必須とし、完了した成果を簡潔に述べる。
- `変更` には変更したファイルと変更内容を記載する。
- `検証` には実際に実行または確認したものだけを記載する。結果は `passed`、`failed`、`skipped: 理由` のいずれかで示す。
- 実行できなかった検証が完了条件に影響する場合は、`検証` に理由を記載する。
- `補足` には、読み手の判断に必要な事項だけを記載する。該当しない場合は省略する。
- 実行していない操作を、正常な検証結果のように報告してはならない。

## SDD開発フロー

ロジックを伴う成果物は **spec（＝観測可能な振る舞いの仕様書）** を唯一の仕様ソースとして開発する（SDD: Spec Driven Development）。オーナーは spec だけ読んで go/no-go を出し、実装コードの詳細は読まない。フェーズ・収束ルールの詳細は `/skill:sdd-strategy` を参照。

## コーディング規範（lazy）

動く最小コードを優先する。上書きより削除、賢いより退屈、自作より標準。コーディング全般（実装・修正・リファクタ・レビュー・設計、依存選定）に適用する。`/skill:ponytail-review`（差分レビュー）と `/skill:ponytail-audit`（リポジトリ全体監査）はこの規範に基づく。

### ラダー

実装前に必ず問題を把握してから（対象ファイルと実際の流れを追う）、下位の段で解決できるならそこで止める。

1. **本当に必要か？** — 投機的需要なら書かず、1行で理由を述べる（YAGNI）
2. **既にこのコードにあるか？** — 近くの helper/util/type/パターンを再利用する。探さずに再実装するのが一番よくある無駄
3. **標準ライブラリでできるか？**
4. **ネイティブ機能で足りるか？** — `<input type="date">`、CSS over JS、DB制約 over アプリコード
5. **既存の依存で解決するか？** — 新しい依存を増やさない
6. **1行で書けるか？**
7. **それでも無理なら** 動く最小コード

バグ修正は根本原因を直す。触ろうとする関数の呼び出し元をすべて grep してから。共有関数にガードを1つ置く方が、各呼び出し元にガードを置くより diff も小さい。

### ルール

- 要求されていない抽象を作らない（1実装のインターフェース、1製品のファクトリ、不変値のための設定）
- 後のためのスキャフォールドをしない。後は後で作れる
- 追加より削除。退屈さは正義
- ファイル数と diff は最小 — ただし問題を理解した上で。間違った場所の最小変更は lazy ではなく2つ目のバグ
- 複雑な要求なら lazy 版を出しつつ同じレスポンスで確認する（「X やった。Y で足りる？ フル X が要る？」）。決め打ちできる答えなら止まらない
- 既知の上限がある簡略化（グローバルロック、O(n²)、素朴なヒューリスティック）には `ponytail:` コメントで上限とアップグレード path を併記する（`# ponytail: グローバルロック、スループット問題が出たら per-account ロックへ`）

### 出力

コードを先に出す。続く説明は最大3行（何を省いたか、いつ足すか）。説明がコードより長くなるなら説明を削る。ユーザーが明示的に求めた説明（レポート、ウォークスルー、フェーズ毎のメモ等）は省略せず全て出す。

パターン: `[code] → skipped: [X], add when [Y]`

### 怠ってはいけないこと

信頼境界での入力バリデーション、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティの基本、明示的に要求されたものは簡略化しない。ユーザーが完全版を望めば作る、再議しない。

問題を理解することを怠らない。ラダーは解を短くするもので、読むことを短くするものではない。触れるファイルと実際の流れを、段を選ぶ前に追う。実世界は紙上の理想とは違う（実クロックはドリフトする等）ので、キャリブレーションの余地は残す。
