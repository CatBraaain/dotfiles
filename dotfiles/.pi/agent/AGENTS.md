# AGENTS.md

## 動作

- チャットは日本語で、常体（だ・である調・体言止め）で簡潔に書く。敬体（です・ます）と前置き・言い換えの重複は省く
- プログラミングのソースコードでは必ず英語を使用すること
- 実装・編集を行うのは、成果物を伴う動詞(実装・編集・修正・追加・削除・リファクタ・変更など)による明示的な指示のときだけ。明示依頼と適用中の指示を変更範囲の根拠とし、依頼外の成果物を追加しない。「直せる？」「やってくれる？」「～お願い」「～して」等の依頼表現も指示に含む
- 「～してほしい」「～と思う」「～と思っている」「～かな」「どう思う？」等は意志表明・意見募集であり指示ではないので相談として扱い、実装しない
- 質問・相談には回答のみを行い、明示的な指示がない限りファイルを編集しない。判断に迷ったときは実装せず確認を返す
- 画像生成AIは、ユーザーが明示的に指示した場合に限り使用する
- ユーザーから図表を使うことを明示的に指示された場合は、必ずdrawioかmermaidを使用する
- チャットで markdownコードブロック を出力するときは、それを4 backticks で囲み。markdown以外のコードブロックは3 backticks で囲う

## Abbreviations

- `kwsk`: 詳しく教えて
- `is nani`: ~は何?

## 技術スタック

- `python`は直接使わずに `uv` 経由で使う。独立した単一スクリプトは先頭に PEP 723 インラインメタデータを入れ、`pyproject.toml` 不要で `uv run script.py` だけで実行できるようにする。
- タスクランナーは基本的に `just` を使う。ただし JS プロジェクトの場合は `package.json` の npm-scripts を使う。
- JS/TS のパッケージマネージャー（pnpm, bun, vp 等）はプロジェクトごとに確認。
- 上記で規定されていない事項は都度確認。

## ビルド

- ビルド成果物は `dist/` ディレクトリに出力する。ただし cargo の場合はデフォルトの `target/` ディレクトリを使う。

## 編集前の確認

ファイルを編集する前に必ず read し、対象ファイルの現状を確認する。明示依頼から対象・目的・入力・観測可能な完了条件・変更範囲を確定し、不明なら推測で開始せず確認を返す。会話途中で読んだ内容や以前の read 結果を記憶で信用して編集せず、常に最新の read 結果を正とする。記憶と現状が乖離している場合は現状に合わせる。

## 品質管理

編集後は必ず該当するリンター、フォーマッター、タイプチェック、テストを実行すること。完了報告では、実行した検証はコマンドと結果を根拠として示し、未実行の検証は理由を示す。プロジェクトに既存の設定・依存があればそれを優先し、なければ以下のデフォルトを使う。

- **Python**: `ruff format`, `ruff check`, `ty`, `pytest`
- **JavaScript/TypeScript**: (`vp format` or `oxfmt`), (`vp check` or `oxlint`), `vitest`

## 調査タスク

検索結果・ウェブサイト・コードベース（リポジトリ・ファイル・関数など）など、何かを説明・言及・引用するときは、該当箇所へクリックでジャンプできるリンクを必ず添える。

- ウェブ上のものは markdown link（`[text](url)`）
- ローカルファイル・コードベース内は平文のパス（markdown link にしない）

ロジックを伴う実装では、着手前に観測可能な振る舞いの合意を取る。

## オーナーへの質問

確認が必要なときは、番号付きの質問にして、質問文が単独で yes/no で答えられる形になるようにする。オーナーの認知コストを下げることが目的。

番号は質問への回答を対応させるための識別子であり、報告本文のリストとは無関係に、質問だけで 1 から振る。

### 質問の進め方

- 仕様確定や要件確認では、現在判明している独立した不明点を1回のメッセージにまとめる
- thinking-partner の「one question at a time」は、深い思考、仮説検証、診断にだけ適用する
- 回答記号は `y`=yes / その他は `a` から順に振る（小文字）とする
- 選択肢数にかかわらず `y/a/b/...` で統一する（`n`=no は使わない）
- 推奨案を質問文に組み込み、`(y)` を「はい」に固定する（具体値や「（おすすめ）」は置かない）
- 全選択肢を行で併記する
- 質問と選択肢をコードブロック（フェンス）で囲まず、素のテキストとして出力する
- 質問は `## 質問` 見出しのセクションに置く。見出しで質問ブロックの開始を構造的に示し、本文のリストとの連番誤結合を防ぐ
- 進め方・手順など本文の番号付きリストの連番を、質問の番号として引き継がない。質問は常に 1 から振り直す

### Bad

````
1. この実装をすすめますか？それとも計画までとしますか (y/a)
   (y) 実装をすすめる
   (a) 計画まで進める

2. テストランナーは、どうしますか？ (y/a/b)
   (y) vitest（推奨）
   (a) jest
   (b) node:test

```
3. 実装まで進めてよいですか？ (y/a)
   (y) はい
   (a) 計画までで止める
```

進め方の連番を質問に引き継いだ例:

1. 実装方針を調査する
2. 質問形式を確認する
3. テストを実行する

4. この手順ですすめますか？ (y/a)
   (y) はい
   (a) 手順を見直す
````

前半の例は、選択肢としては記号で答えられるが、質問文単体では yes/no で答えられないため認知コストが高い。また例2は推奨案（vitest）が質問文に乗っておらず、`(y)` が「はい」ではなく具体値になっている。例3はフォーマット自体は正しいが、質問全体をフェンスで囲んでいる。回答は記号1文字で打つため囲む利点がなく、読みづらさが増す。

後半の例は、進め方の連番 1〜3 を質問が引き継ぎ `4.` になっている。番号は質問への回答を対応させる識別子であり、本文リストの続き番号ではない。

### Good

```
## 質問

1. 実装まで進めてよいですか？ (y/a)
   (y) はい
   (a) 計画までで止める

2. テストランナーは vitest でいいですか？ (y/a/b)
   (y) はい
   (a) jest
   (b) node:test
```

本文の番号付きリストに続けて質問を置くときも、`## 質問` セクションで区切り、質問は 1 から振り直す:

```
## 進め方

1. 実装方針を調査する
2. 質問形式を確認する
3. テストを実行する

## 質問

1. この手順ですすめますか？ (y/a)
   (y) はい
   (a) 手順を見直す
```

## Git worktree 運用

main worktree ではファイルを編集しない。編集を伴う作業は、1ファイルの軽微な修正も含め、常にサブワークツリーとブランチを作成して着手する。

- 着手時: 「作成」の手順で worktree を作成する。セッションの cwd は main worktree に置いたまま、worktree を指定して作業する。
- まとまった作業単位の完了時: 「finish・discard・close」の finish を、owner の承認を得てから実行する。
- 適用しない: 読み取りのみの調査・検索・検証、コミット・マージなど worktree を必要としない操作。

### 作成

1. branch 名は取り組む機能を表す kebab-case 英語（例: `add-export-command`）。リポジトリ規約があれば優先する。
2. `git worktree add ~/projects/worktrees/<リポジトリ名>/<branch> -b <branch>` で HEAD から worktree を作成する。worktree はリポジトリごとに `~/projects/worktrees/<リポジトリ名>/` ディレクトリへ集約する。書き込みが sandbox にブロックされたら、作成先の worktree パス（またはその親ディレクトリ）を ask_permission で承認させる。
3. worktree 内のファイルは絶対パスで read/write/edit する。相対パスはセッション cwd（main worktree）に解決されるため、worktree のファイル指定に使わない。git 操作は `git -C <worktree のパス>` で実行する。

main の未コミット変更はその場に残す。worktree への持ち運びは行わない。

### 統合

ローカルの使い捨て worktree ブランチを統合先（main 等）へマージするときは、履歴を線形に保つ。

1. 統合先で `git merge --ff-only <branch>` を実行する。`git -C <main worktree のパス> merge --ff-only <branch>` でも実行できる。
2. 統合先が diverge して失敗するときは、対象ブランチを `git rebase <統合先>` してから再度 ff-only マージする。
3. `--no-ff` による merge commit と `--squash` による squash 統合は行わない。

- 適用する: ローカルの使い捨て worktree ブランチの統合。この統合のための rebase は、git skill「コミットの作成と分割」の rebase 禁止の対象外とする。
- 適用しない: remote へ push 済みで共有しているブランチ。トポロジーとして作業のまとまりを記録したいタスクは、worktree ではなく PR で統合する。

検証: 統合後に `git log --graph --oneline -n <統合した commit 数 + 2>` を確認し、merge commit がなく線形であること。

### finish・discard・close

worktree は自動掃除されないため、エージェントが作業完了時に自分で閉じる。原則として finish で閉じ、成果を捨てるときは discard で閉じる。閉じ方は次の3語で区別する。

owner は worktree を「wt」と略すことがある（例: finish wt）。略記も worktree への指示として解釈する。

| 言葉 | 意味 |
| --- | --- |
| finish | 成果を統合先へ取り込んで閉じる。owner の承認を得てから実行する |
| discard | 変更と branch を捨てて閉じる。owner の承認を得てから実行する |
| close | worktree と branch を削除する。finish・discard の最終段として実行する |

finish — 統合の判断が入るため、commit 前の未コミットの状態で owner の承認を得る。検証まで済ませた段階で、「オーナーへの質問」に従う `## 質問` として「この worktree を finish してよいですか？」と必ず尋ね、commit は承認後に行う。承認後:

1. worktree 内の変更を確認し、あれば git skill「コミットの作成と分割」に従って commit する。手順3の backup branch は、close で worktree ごと削除するため作らない。
2. 「統合」に従って統合先へマージする。
3. close を実行する。

discard — 成果を捨てる判断が入るため、実行前に owner の承認を得る。承認後:

1. worktree の branch 名と未コミット変更を確認し、捨てる対象を特定する。
2. close を `--force` と `-D` で実行する。

close — bash のカレントディレクトリが対象 worktree 内にあると削除に失敗するため、対象外のディレクトリから実行する。エディタのワークスペースから worktree を外す操作は本手順に含まず、owner が手動で行う。

1. `git worktree remove <worktree のパス>` で worktree を削除する。
2. `git branch -d <branch>` で、worktree が checkout していた branch を削除する。
3. `git worktree list` に prunable な参照が残っていれば、`git worktree prune` を実行する。

手順1・2は、未コミット変更・未マージの branch があると失敗する。失敗したときは close 単独で先へ進らず、成果を取り込むなら finish、捨てるときは owner の承認を得て discard として扱う。

検証: `git worktree list` に対象 worktree がなく、`git branch --list <branch>` が空であること。中途終了で残った worktree は `git worktree list` で点検する。

## 完了報告

成果物を伴う作業を報告するときは、結果だけでなく、結果を理解・検証・再開するために必要な作業の要約を報告する。詳細な作業ログや内部の思考過程は報告しない。

この形式は、変更・検証、または依頼された調査・レビュー・計画の結果を報告するためのものである。質問・相談・意見募集への直接の回答には使わない。

### 適用判定ラダー

目標: 返信がこの形式に沿うべきかを、返信までに実行した依頼作業だけで判定する。

最初に成立する段で止まる。

1. 条件: 返信までにファイル変更、検証、依頼された調査・レビュー・計画のいずれかを実行したか？
   行動: 必ずこの形式に沿う。質問や承認待ちの途中であっても同じであり、この形式に沿う返信を質問や承認待ちで終えるときは、必要なセクションの後に「オーナーへの質問」に従って `## 質問` セクションを置く。
2. 条件: 前段の作業を実行していないか？
   行動: この形式を使わず本文で直接回答する。質問・相談・意見募集への回答のように、返信本文自体が成果物である。

検証: 返信の前に、このターンで write・edit・検証コマンド、または依頼された調査・レビュー・計画を実行したかを振り返る。

### 見出し

最初の見出しである報告見出しとして、報告ラベルとタスクの要約を1行で示す。形式は `## <絵文字> <英語1語のラベル> — [タスクの要約]` とする。この形式は報告見出しだけに適用し、後続のセクション見出しや `## 質問` には適用しない。ラベルは、作業の結果または現在の状態を示す。要約は依頼対象を表す名詞形で簡潔に記述し、達成内容の説明は書かない。worktree で作業した返信では、達成内容の要約の前に、見出しの直下へ `worktree: <branch>` を1行で置く。達成したこと、または達成できなかったことの要約は、見出しまたは worktree 行の直下の本文に必ず書く。

### 報告ラベル

依頼の主成果物に対応する成功ラベルを選ぶ。未完了・待機・失敗では、成功ラベルの代わりに状態ラベルを使う。

| ラベル | 使う条件 |
|---|---|
| `📝 Created` | 変更対象がすべて新規ファイル |
| `📝 Edited` | 変更対象に既存ファイルの変更を含む。新規作成との混在も含む |
| `🔎 Researched` | 調査が主成果物 |
| `👀 Reviewed` | レビューが主成果物 |
| `📋 Planned` | 計画が主成果物 |
| `✅ Closed` | finish により worktree を統合・close まで完了した |
| `🧹 Discarded` | discard により worktree と branch を破棄した |
| `🟡 Partial` | 一部を完了したが、残課題がある |
| `⏳ Ready` | 検証済みの worktree を finish するため、オーナーの承認を待つ |
| `⏳ Waiting` | `Ready` 以外で、オーナーの回答・承認を待つ |
| `⛔ Blocked` | 権限・環境など、回答以外の要因で安全に続行できない |
| `❌ Failed` | 依頼された変更または検証に失敗した |

`Closed` は個別の編集完了ではなく、その worktree での一連の変更を統合・削除まで終えた報告だけに使う。

### 必須セクション

- `検証`: 実際に実行・確認した検証と、その結果を表で示す。

ファイルを変更した場合は、`変更` セクションも必須とする。変更がない場合は省略してよい。

### 任意セクション

重要な情報がある場合だけ、内容に合うセクションを追加する。`進め方`、`実施したこと`、`受入条件`、`残課題`、`要判断`、`再開地点`、`オーナーの操作` などの見出しは例であり、タスクに応じて統合・分割・改名してよい。空のセクションや定型文のためだけのセクションは作らない。

次の場合は、作業の要約を必ず含める。

- 重要な実装方針や設計判断を選んだ場合
- 依頼の解釈に判断が入った場合
- 検証に失敗し、原因の切り分けを行った場合
- `Partial`・`Ready`・`Waiting`・`Blocked` となり、別の担当者が再開する可能性がある場合

要約には、調査対象、採用した方針、意図的に変更しなかったもの、失敗の切り分け、再開地点など、第三者が判断や作業を引き継ぐために必要な観測可能な事実だけを記載する。`ls` や `grep` などの逐次ログ、結論に影響しない探索、内部の思考過程は記載しない。

### 基本形

```markdown
## 📝 Edited — [タスクの要約]

[依頼に対して達成したこと、または達成できなかったことの要約]

## 変更

| ファイル | 変更内容 |
|---|---|
| `path/to/file` | [変更内容の要約] |

## 検証

| 種別 | 実行内容 | 結果 |
|---|---|---|
| format | `...` | ✅ passed |
| lint | `...` | ✅ passed |
| test | `...` | ✅ passed |
```

- 見出しには報告ラベルに対応する絵文字を含め、` — ` に続けてタスクの要約を置く。例: `## 📝 Edited — [タスクの要約]`、`## 🟡 Partial — [タスクの要約]`。
- `変更` には変更したファイルと変更内容をテーブルで記載する。変更理由や詳細な背景は `変更` に書かず、任意セクションで補う。
- `検証` には実際に実行または確認したものだけを記載する。結果は `✅ passed`、`❌ failed`、`⚪ skipped: 理由` のいずれかで示す。
- `変更`・`検証` 以外のセクション名は、重要な情報が明確に伝わる範囲で柔軟に統合・分割・改名してよい。
- 実行できなかった検証が受入条件に影響する場合は、`検証` に理由を記載し、成功ラベルを使ってはならない。
- `Partial`・`Ready`・`Waiting`・`Blocked`・`Failed` の場合は、残課題、阻害要因、要判断、再開地点、オーナーの操作など、必要な情報を任意セクションで補う。
- 実行していない操作を、正常な検証結果のように報告してはならない。

## ファイルベース作業戦略

作業の入力と成果物はチャット出力で完結させず、ワークファイルとして残してパスで受け渡す。セッションやサブエージェントをまたいで参照でき、同じ内容を再出力するトークンを節約できる。単発の質問・相談、ファイル変更1件で終わる作業では作成しない。

### ワークファイル

ワークファイルは常に `~/.pi/agent/work/{project}/` に作る。

- `{project}` は作業中リポジトリのルートディレクトリ名。リポジトリ外ではカレントディレクトリ名とする。
- 複数リポジトリにまたがる作業は、作業を主導するリポジトリの `{project}` に置く。
- work は使い捨てにせず、後から見返せる前提で置く。

### 置き場の判定ラダー

目標: 成果物ファイルを、オーナーの指示に一致する置き場に1つだけ作る。

最初に成立する段で止まる。

1. 条件: 依頼が「specファイルを作って」「計画ファイルを作って」のようにファイルの作成そのものを指示しており、workへの作成を指示されていないか？
   行動: workには作らず、プロジェクト（表）のルートに `{name}.{type}.md` の実ファイルを作る。シンボリックリンクは作らない。
2. 条件: 前段に当てはまらない。「spec作って」「計画作って」のようにファイルの作成までは指示していないか、workへの作成を指示しているか、自主的にワークファイルに書き起こすだけか？
   行動: `~/.pi/agent/work/{project}/` に `{yyyymmdd-hhmmss}-{name}.{type}.md` を作る。

検証: 成果物が表とworkのどちらか一方にだけ存在すること。
出力: 採用した段と、判定の根拠になった依頼文の語。

### 命名

ファイル名は `{yyyymmdd-hhmmss}-{name}.{type}.md` とする。`name` は対象を表す kebab-case、`type` は次の6種に固定する。

| type | 作成するタスク | 中身 |
| --- | --- | --- |
| `interview` | オーナーへの質問・ヒアリングをするとき | 質問、回答、決定事項 |
| `plan` | 複数ステップの計画を立てるとき | 作業分解、順序、完了条件 |
| `research` | 対象同定・事実収集・比較の調査をするとき | 事実、出典、結論 |
| `review` | 成果物をレビューするとき | 指摘（場所・種別・重要度・修正案）。レビュー対象は編集しない |
| `report` | タスクの実行結果を残すとき | 結果、検証、残課題 |
| `spec` | オーナーの go/no-go 用に新規specを整備するとき | 観測可能な振る舞いと適用範囲 |

### review のカバレッジ記録

git リポジトリ内で `review` ワークファイルを作るときは、実際にレビューしたファイルの frontmatter スナップショットを記録する。ファイル内容ごとの ID（git blob hash）により、セッションをまたいで「この内容はレビュー済みか」を判定するための正本とする。対象ファイルの選び方はこの規則の対象外。リポジトリ外では省略する。

```yaml
---
snapshot:
  files:
    src/a.ts: 07d44e579bbd9318d1fd6c91d387248d8ab8b120
    lib/util.ts: 2ce75e2a24f7d6841a504cf3616ef5a59edb3a2d
---
```

blob hash はレビュー時に読んだ内容（作業ツリーの実ファイル）から `git hash-object <file>` で取得する。ID は内容のみで決まり、パス変更や rebase でコミットハッシュが変わっても同一内容なら同一 ID になる。

### 受け渡し

- サブエージェントへの委譲では、出力先ファイルパスを委譲文に指定する。本文を委譲文に貼らない。
- 前段のワークファイルを入力にするときも、パスを渡して読ませる。
- チャットへの報告は要約とファイルパスだけにする。本文をチャットに複製しない。
