# SDD 統合の判断記録

## 判断の要約

sdd-spec と sdd-audit は、それぞれ仕様書の整備と適合性の監査に特化していた。しかし、仕様と実装の乖離を継続的に扱う開発全体の判断を、複数の入口に分けたまま維持する負担が明らかになったため、両者を sdd-workflow に統合した。統合後は sdd-workflow を唯一の入口とし、spec-only、実装、監査、収束というモードで開発の段階を表すことにした。

これは spec の書き方や監査の観点を捨てたものではなく、要件合意から収束までを一つの判断体系として扱うための再配置だった。

## 仕様と実装は時間とともに乖離する

仕様と実装は、作成時点では一致していても、変更が積み重なると時間経過によって乖離した。実装だけが変更されて仕様が更新されない場合、または仕様だけが更新されて実装が追随しない場合、どちらを正とすべきかが不明確になった。仕様書を作る工程と実装を検証する工程を別々に持つだけでは、この乖離を継続的に発見する仕組みにならなかった。

そこで、観測可能な振る舞いを spec に集約し、spec を判断の基準（oracle）として実装とテストを照合し、差分ベースの AI 一致チェックと監査で乖離を検出して収束させる流れを採用した。完全な自動検出ではなく、変更箇所に対応する範囲を中心に継続確認することで、全文一致のコストを避けながら乖離を発見する方針になった。

## 旧 TDD で明らかになった限界

旧 TDD では「テスト＝仕様」として、実行可能なテストを単一の仕様ソースに置いた。テストは機械的に実行できるため、実装との接続は強かった。一方で、テストに分岐を自然言語に近い形で網羅しても、分岐の全体像や条件間の関係を人間が確認することは難しかった。テストが通ることは確認できても、仕様として必要な振る舞いが漏れなく並んでいるかを、オーナーが短時間で判断することは困難だった。

この問題はテストの実行可能性では解決しなかった。実行可能なテストと、人間が仕様全体を理解して承認できる文書は、同じものとして扱えないことが分かった。

## オーナーが spec だけで判断できる必要

オーナーは実装コードやテストの詳細を読まずに、要求された振る舞いが実現される見込みを判断できる必要があった。実装コードを読ませると内部構造の理解が判断に混ざり、テストを読ませるとモックやテストフレームワークの記法が仕様理解を妨げた。

そのため、オーナーの go/no-go の対象を spec に限定した。spec は単独で読め、要件文書や会話履歴を参照せずに対象・目的・適用範囲・観測者を理解できる必要があるとした。spec の承認は要件の承認に相当するため、spec の変更は再レビューを必要とする判断になった。

## 観測可能な振る舞いを視覚的な spec へ移した理由

テストに埋め込まれていた仕様上の分岐を、ユーザーが観測できる振る舞いとして切り出した。内部の関数名、クラス構造、データ構造、最適化などは、結果に現れない限り仕様の対象から外した。これにより、実装の変更で更新される層と、ユーザーに約束する振る舞いの層を分離した。

さらに、条件分岐を Markdown のテーブル、状態の変化を Mermaid の状態遷移図、時系列をシーケンス図、順序を持つ流れをフロー図で表した。自然言語の段落だけで分岐を追うよりも、条件・状態・順序の関係を視覚的に比較でき、オーナーが spec 単独で網羅性を確認しやすくなると判断した。spec は実装・テストを含めず、ユーザーが観測可能な振る舞いに限定した。

## 採用したことによる代償

この判断は旧 TDD の問題を解消した一方で、いくつかのコストを受け入れるものだった。

- spec とテストが別々に存在するため、仕様と検証の二重管理が復活した。
- spec は実装から独立した層に置かれたため、更新されずに腐敗する可能性が残った。
- spec とテストを ID で機械的に紐付ける方式は採用せず、coverage、fidelity、実装起点の余剰、逆指摘を AI が照合する構成にした。その結果、テスト不足や spec の曖昧さの検出が AI レビューの精度に依存した。
- 差分ベースの AI 一致チェックは確認範囲とコストを抑えられるが、AI が見落とせば乖離も見落とされる。最終防波堤を AI レビューに置いたことで、AI の弱さがそのまま全体の弱さになった。
- Mermaid の図表を読める環境に依存するため、レンダリングできない環境では視覚化の価値が下がった。

これらの代償は、spec を観測可能な振る舞いに絞ることで部分的に緩和した。実装の内部変更では更新不要な層に置くことで腐りにくさを得たが、腐敗を完全に防げるとは扱わなかった。

## 分離していた理由と統合した理由

sdd-spec と sdd-audit を分離していたのは、責務を混ぜないためだった。sdd-spec は合意済み要件から観測可能な振る舞いを抽出し、視覚的な仕様書として整える責務だけを持った。sdd-audit は完成した spec を oracle として、テストと実装を照合し、漏れ・過剰・順序ズレ・偽陽性・主語ズレ・余剰実装・曖昧さを指摘する責務だけを持った。どちらも実装やテストを直接編集しない境界を保った。

一方で、利用者から見ると、spec の整備、実装、監査、収束は同じ開発判断の連続であり、入口が分かれていることで全体像と次の判断地点が分散した。sdd-spec と sdd-audit の存在を個別に知り、適切な順序で呼び分ける必要も生じた。そこで、責務の分離は内部に残しつつ、利用者向けの入口を sdd-workflow に統合した。

統合によって、要件合意→spec 整備→go/no-go→実装→監査→収束という6フェーズを一つのワークフローとして提示できるようになった。spec-only、実装、監査、収束のモードも、この全体のどの判断を扱っているかを示すために sdd-workflow の下へまとめた。分離によって得ていた責務境界は維持し、入口だけを統一した。

## 統合後に残した境界

統合後も、実行規約と判断の背景は同じ文書に混在させないことにした。

- `SKILL.md` は、sdd-workflow を使う際のフェーズ、モード、収束条件、監査の扱いなど、現在の実行規約を担う。
- `note.md` は、その規約を採用した背景、旧 TDD からの転換理由、統合の経緯、受け入れたトレードオフを担う。

したがって、この記録は現在の AI に対する実行手順や命令ではない。規約を変更するときに、なぜ spec を唯一の仕様ソースとし、なぜ sdd-spec / sdd-audit を sdd-workflow の入口へ統合したのかを確認するための判断記録として残した。
