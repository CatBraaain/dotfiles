# Instruction Design

AI に与える指示テキスト（プロンプト・システムプロンプト・スキル・エージェント規範）は、AI を動機付ける文章ではなく、守るべき境界を持つ**契約**として書く。

契約ではない指示は「良いコードを書け」「ベストプラクティスに従え」「適切に処理せよ」といった方向の提示で終わる。AI は方向を受け取っても「良い」の意味を毎回推測し、結果がぶれる。契約は推測の余地を潰す — 何を許可し、何を禁止し、何を出力し、守られたかをどう検証するかを境界で縛る。

問いを変える:

- ✗「あと何を agent に伝えるか？」
- ◯「この指示は**どんな契約を強制するか**？」

「気をつけて」と書くのをやめ、「無関係なファイルをステージしない」と書き始める。boring で予測可能、それがコードベースに触れる agent に求められる性質。

もう一つの軸がある。ファイルとして存在する指示は、読まれるタイミングで2種類に分かれ、配置の作法が変わる:

- **入口ファイル**（AGENTS.md / CLAUDE.md / システムプロンプト等）— セッション冒頭で常時読み込まれる。個別の文を契約で縛るだけでなく**地図**として書く（詳細は「地図として書く」）。
- **スキルファイル**（SKILL.md 等）— trigger 発火時だけ読み込まれる。地図ではなく、発火したその場で完結する**自己完結する手続き書**として書く（詳細は「スキルは自己完結する手続き書」）。

契約が「何をやるか」の推測を潰すなら、配置の作法は「どこを見るか / どこで完結するか」の推測を潰す。

## Trigger（いつ起動するか）

このスキルが効くのは、AI に与える指示テキストを書く・直す・レビューするとき:

- 「プロンプトを書く」「スキルを書く」「指示を書いて」「システムプロンプト」「AGENTS.md の規範」等の依頼
- 明示がなくても、指示テキストを書く場面では常に

悪い trigger は広すぎる（「ソフトウェア工学をするとき」はほぼ全てを含むので trigger として機能しない）。always active な指示はモノリシックプロンプトへの逆行で、境界を失う。

## Owns one domain（何を所有するか）

このスキルが所有するのは**「AI への指示テキストの書き方」一点**。

所有判定テスト: 「これを1人・1チームが所有できるか？」No なら分割する。

- **書く**: プロンプト・システムプロンプト・スキル（`SKILL.md`）・エージェント規範（`AGENTS.md` 等）・エージェントへの作業指示
- **書かない**: コード本体（readable-code / ponytail）。観測可能な振る舞いの仕様書と spec ↔ テスト ↔ 実装の監査は、統合された `/skill:sdd-strategy` の責務である。

## Allowed（契約として許可・要求する記述）

判断ロジックは性質に応じた記法へ預ける。フラットな箇条書きで分岐を羅列しない — 読み手が条件を見落とす。記法の選び方を間違うと、解釈のズレがそのまま実行のズレになる。

| 性質 | 記法 |
| --- | --- |
| 単純な真偽 | 条件文 |
| 複数軸の組み合わせ | マトリクステーブル |
| 状態のライフサイクル | 状態遷移図 |
| 時系列のやり取り | シーケンス図 |
| 順序付き手続き | フロー図 |
| 優先順位付きフォールバック | Decision Ladder（後述） |
| 検証項目の羅列 | チェックリスト |

症状 → 直し方:

- ネストした条件が深い → ラダーか状態遷移で平坦に。
- 箇条書きなのに順序が意味を持つ → フロー図か番号付きへ。
- 同じ条件をあちこちで書いている → マトリクスで正規化。
- 「場合による」で終わっている → 軸を摘出して表に。

それ以外に許可・要求する記述:

- **完了条件・受入条件は観測可能に** — ファイルが生成された・テストが通る・コマンドの終了コードが 0・特定の出力が現れる 等。「対応しました」という自己申告で終わらせない。
- **主観語に基準を添える** — 「適切に」「十分に」「きれいに」alone は禁。誰が・何で判断するかを添えるか、観測条件へ置き換える。
- **適用する場合と適用しない場合をセットで書く** — 片方だけだと過剰適用や誤適用が起きる。

## Decision Ladder（優先順位付きフォールバックの記法）

Decision Ladder は、優先順位付きの行動手順を記述する記法。最も単純・安全・低コストな選択肢から始め、要件を満たせない場合に限って、より強力・高コストな選択肢へ移行する。判断規則を設計するための記法であり、あらゆる分岐を置き換えるものではない。

**適用する場合** — 次のいずれかに該当するとき:

- 行動に明確な優先順位がある。
- 低コスト・低リスクの行動を先に試すべき。
- ある行動が失敗・不十分な場合に代替策へ移行する。
- より強い行動へ移る条件を明示する必要がある。
- 要件を満たした時点で後続の処理を止めたい。
- 特定の条件で段を飛ばす、または人間の承認を求める必要がある。

典型用途: 実装方法の選択、ツールの選択、調査の深さ、障害対応、承認フロー、人間へのエスカレーション。

**適用しない場合** — 次は別の記法へ:

- 独立した真偽条件 → 条件文。
- 複数の軸の組み合わせの網羅 → マトリクス。
- 循環するワークフロー・状態遷移 → 状態機械。
- すべての条件を同時評価 → 決定表。

### 段の記法（4項目）

各段に必ず定義する:

- **適用条件** — その段を使える条件。
- **実行内容** — 許可された行動。
- **停止条件** — 目標を満たしたと判断できる観測可能な条件。不要なエスカレーションを防ぐ。
- **エスカレーション条件** — 次の段へ移る境界。

核心: 要件と受入条件を完全に満たす最初の段で停止する。複数段が要件を満たすなら、より単純で安全な段を選ぶ。十分な段が見つかった後に、仮定上の将来要件を調査し続けない。ラダーは調査・問題理解の代わりに使わない。

### テンプレート

```markdown
## Decision Ladder：[名前]

### 目標

[観測可能な成果と受入条件]

### 適用範囲

[このラダーが適用されるタスクと状況]

### 段

#### 第1段：[最も単純な選択肢]

- 適用条件：
- 実行内容：
- 停止条件：
- エスカレーション条件：

#### 第2段：[フォールバックの選択肢]

- 適用条件：
- 実行内容：
- 停止条件：
- エスカレーション条件：

### 例外

- [条件]の場合は、[段]へ直接移る。
- [条件]の場合は、実行前に承認を求める。

### 最終フォールバック

[どの段でも目標を満たせない場合の行動]

### 検証

[成功を報告する前に必要な証拠]
```

### 制約

- 可能な限り観測可能な条件を使う。主観的な条件には判断者を明記する。
- 重要な場合は時間・範囲・試行回数・予算などの上限を定義する。
- 各段の実行内容は明確な1つの行動を基本とする。
- ラダーは短く保つ。同じ判断境界を持つ手順だけをまとめる。
- 下位の段で目標を満たせる場合、上位の段を必須にしない。
- 入力検証・エラーハンドリング・セキュリティ・アクセシビリティ・データ損失防止は省略しない。
- 将来必要になるかもという理由だけで段を追加しない。

### エスカレーションと承認

エスカレーションは必ずしも失敗を意味しない。次の行動がより強力・高コスト・不可逆・権限外であるためにエスカレーションする場合もある。次の段が以下に該当する場合は人間の承認を求める:

- 破壊的または不可逆な変更を行う。
- 許可された範囲外のシステムやファイルに影響する。
- 依存関係の追加、または広範なアーキテクチャ変更を行う。
- 金銭・セキュリティ・プライバシー・コンプライアンスに重大なリスクがある。
- 要件が重大に曖昧なまま処理を進める。

下位の段を待つことでリスクが増える場合、または明示された要件に違反する場合は、例外として下位の段を飛ばしてよい。

### 検証

ラダーを確定する前に確認する:

- 目標が観測可能である。
- すべての段に適用条件・実行内容・停止条件がある。
- すべてのエスカレーション条件を検証できる、または判断者が定義されている。
- 例外が通常の順序を意図せず無効化していない。
- 最終フォールバックが定義されている。
- ラダーが、置き換える分岐より単純である。
- 代表的なケースで、選択される段が一意になる。

### 判断記録（出力契約）

内部の思考過程を長文で出力せず、次の要約だけを報告する:

```text
選択した段：[段の名前]
理由：[なぜ目標を満たすのか]
回避したエスカレーション：[不要だった上位段]
検証：[実行した確認または根拠]
```

## 地図として書く（Map, not manual）— 入口ファイル向け

地図として書くのは**常時読み込まれる入口ファイル**（AGENTS.md / CLAUDE.md / システムプロンプト等）。セッション冒頭で毎回流れるためコンテキストを常時消費し、巨大化は即、性能低下に直結する。契約が個別の指示文の**質**を縛る軸なら、地図は入口ファイル全体の**配置**を縛る軸。

※1回限りのプロンプトや trigger 発火時だけ読まれる SKILL.md には当てはまらない。SKILL.md は「スキルは自己完結する手続き書」へ。

問いを変える:

- ✗「この入口ファイルに何を全部書き下すか？」
- ◯「この入口ファイルは**何へのポインタ**で、何を他へ任せるか？」

文脈は希少資源である。巨大なマニュアル1つに全部詰めると: すぐ腐り、検証が難しく、「全部重要」＝「何も重要でない」になってガイドが効かなくなる。短い地図を入口に置き、必要になった時に深い情報源へ取りに行かせる（progressive disclosure）方が、探索の失敗を減らし命中率を上げる。

### 地図が置くもの（where）

- **参照・ルーティング** — より深い情報源（spec / docs / ARCHITECTURE.md / 各 SKILL.md）へのポインタ。
- **構造の提示** — リポジトリやプロジェクトのどこに何があるか。パスの列挙ではなく、ディレクトリの役割・パターンの記述。
- **硬い境界・検証・エスカレーション** — 停止条件・確認コマンド・権限外の領域。危険ルールは助言ではなく停止条件にする。

### 地図が置かないもの（how）

- **手続きの全文・長いアーキテクチャ記述・ポリシー全文** — ポインタを追うかコマンドを実行すれば手に入るものは貼らない。
- **実装の細部** — invariants（不変条件）を強制し、implementations は現場に任せる。
- **ツールで強制できる好み**（formatter / linter 設定）— ファイルに書かずツールに任せる。

### 地図が効いているか

セッション冒頭が `ls` や探索ではなく、的確なファイル読み込みで始まれば、地図が効いている証拠。アーキテクチャの概観は効かず、「どこに何があるか・何をするか」を告げる簡潔な機能的マップが探索ステップを減らす（詳しくは末尾の出典）。

### 入口ファイルのなかでも AGENTS.md 特有の作法

AGENTS.md は入口ファイルの代表格。地図の一般論に加え、下記は AGENTS.md で特に効く:

- **階層でマージされる** — ディレクトリを下るほど局所、上るほど集約。ルートは全リポジトリ共通の硬い境界、サブディレクトリの AGENTS.md はその配下固有の境界。同じ内容を両方に書かず、局所なものは局所ファイルへ。
- **真実は1箇所** — CLAUDE.md / .cursorrules 等の併存ファイルと重複させない。ツール間で読む側が違っても、同じ内容を複数ファイルに分散させると片方だけ更新されて腐る。
- **権限外を止める** — 実行禁止コマンド・承認必須の操作など、越えてはいけない境界は助言でなく停止条件にする。入口ファイルは常時効くので、硬い境界を置くのに最も適した場所。

## スキルは自己完結する手続き書（SKILL.md 向け）

SKILL.md は trigger 発火時だけ読み込まれる。入口ファイルのように「地図を置いて深い情報源へ飛ばす」作法は通用しない — 発火したその場で読めて動く、自己完結した手続きを書く。

問いを変える:

- ✗「このスキルはどの情報源へ誘導するか？」
- ◯「このスキルは発火したら何をさせるか？」

### description が trigger である

SKILL.md では description が常に context にあり、本文は on-demand で read される（progressive disclosure）。description が trigger の役を果たすので、「いつ使うか」を具体的に書く。広すぎる（「ソフトウェア工学のとき」）と全件に発火して trigger として機能せず、狭すぎる（固有名詞すぎる）と呼ばれない。trigger の一般論は「Trigger」へ。

### 自己完結の作法

- **発火時だけで完結** — 「詳しくは docs/xxx へ」とポインタで飛ばすと、on-demand read の1回で情報が揃わず失敗する。入口ファイルが where を書くのに対し、スキルは発火したら完結する how を書く。
- **長い参照資料は外だし** — API 一覧・網羅的なルールなど、発火のたびに必要でない長文は `references/` へ。SKILL.md には「いつ・どう使うか」の手続きを置き、必要なときだけ `references/` を read させるよう案内する。
- **helper script は `scripts/` へ** — 「どう」の複雑さは script が担い、SKILL.md は「何を・いつ呼ぶか」に絞る。
- **1スキル1ドメイン** — 複数ドメインを1スキルに詰め込むと trigger が曖昧になる。所有判定テスト（1人・1チームで持てるか）を満たさないなら分割する。

## プロンプトテンプレート（`/name`）

プロンプトテンプレートは `/name` で呼ばれたときだけ展開される Markdown スニペット。常時 context ではなく、autocomplete の description 経由で発見される。呼び出し前提で自己完結させる。

- **argument-hint で期待引数を明示** — frontmatter の `argument-hint` が autocomplete に出る。必須は `<angle brackets>`、省略可は `[square brackets]` で区別する。
- **位置引数とデフォルト** — `$1` `$2` の位置引数、`${1:-default}` のデフォルト、`$@` / `$ARGUMENTS` の全引数を使い分ける。

これらはテンプレート一般の作法。以下は引数 `$@` を扱うテンプレート特有の契約 — AGENTS.md / SKILL.md / 通常のプロンプトでは引数は出現しない。

### 原則：引数は生プロンプトとして引用し、本文へ変数展開しない

引数を本文のあちこちへ「`$@` について〜せよ」と変数のように埋め込まない。ユーザーが入力した生のプロンプト全体をコードブロックでそのまま引用し、本文は「その入力をどう解釈・処理するか」に専念させる。引用が入力の境界となり、AI が「`$@` をどの文脈に当てはめるか」を推測する余地を潰す。

### Before/After

Before（引数を変数展開で本文に埋め込む）:

```text
# Pure 出力

`$@` に対して、回答の本体だけを出力する。
```

After（生プロンプトを引用し、本文は処理に専念）:

```markdown
## 今回の依頼（最優先）

以下は、今回の `/pure` 呼び出しで渡された生の依頼内容です。

```text
/pure $@
```

## 出力ルール

引用した依頼に対して、回答の本体だけを出力する。
```

差：`$@` が本文の文に埋め込まれなくなり、ユーザーの実際の入力が観測可能な境界として引用される。本文は「その入力をどう扱うか」の処理契約に分離され、`$@` の展開先を AI が推測する余地が消える。

### 検証

- [ ] 引数（`$@` 等）を生プロンプトとして引用しており、本文への変数展開で埋め込んでいないか

## 通常のプロンプト（1回限り）

ファイルとして残らない、その場限りの指示。配置の作法（地図・自己完結・引数）は当てはまらないが、「契約として書く」軸は完全に効く。

- **地図不要** — 1回限りなので progressive disclosure の入口でない。必要な文脈はその場で与える。
- **trigger / owns one domain は非適用** — 呼び出し構造を持たない。「Trigger」「Owns one domain」の一般論は読まなくてよい。
- **暗黙前提に頼らない** — 過去の会話や「分かるよね」に頼らず、観測可能な入力・完了条件・出力形式を1回で渡す。1回限りほど、自己完結と即時性が効く。
- **共通軸はすべて適用** — 記法の選択・Decision Ladder・Forbidden・Output Contract は、ファイルの有無にかかわらず同じように効く。

## Forbidden（契約として禁止する記述）

- **方向だけの指示** — 「ベストプラクティスに従え」「きれいに」「適切に」など、方向は示すが境界を持たない文。動機付けであって契約でない。
- **自己申告で終わる完了** — 客観的に検証できない「やりました」。
- **投機的な段・例外・将来用の分岐** — 「将来こうなるかも」は追加の理由にならない。1実装のインターフェース、不変値のための設定項目、使われないパラメータも同様。
- **怠ってはいけないことは禁止対象外** — 入力検証・エラーハンドリング・セキュリティ・データ損失防止・明示要求は、簡略化の対象外。境界を削ってはいけない。

## Output Contract（指示テキストの出力契約）

書き上がった指示テキストは以下を満たす:

- **出力形式の明示** — テンプレ・フォーマット・構造を示す。形がぶれないように縛る。
- **出力しないことの明示** — 余計な解説・ファイル・変更を出さないよう境界を置く。
- **完成イメージ** — 具体例を1つ添える。形が一意に定まる。

## Verify（契約が守られたか）

指示テキストを書き終えたら、以下を満たすか。1つでも満たさなければ直す。

構造（契約の骨格）:

- [ ] 明確な trigger があるか（always active でないか）
- [ ] 1つのドメインを所有しているか（1人・1チームで持てるか）
- [ ] 許可する行動が定義されているか
- [ ] 禁止する行動が定義されているか
- [ ] 期待する出力が記述されているか
- [ ] agent が従ったか検証可能か（testable）

内容（契約の質）:

- [ ] 判断ロジックは性質に合った記法に預けたか（フラット羅列でないか）
- [ ] 主観語に判断者・基準が添えられているか
- [ ] 適用する場合と適用しない場合の両面を書いたか
- [ ] 投機的な段・例外・将来用の分岐を追加していないか
- [ ] 入力検証・エラーハンドリング・セキュリティ等の必須事項を省いていないか

配置（ファイル種別の作法）:

- [ ] 入口ファイル（AGENTS.md 等）は where を書き、how を他へ任せているか
- [ ] 入口ファイルにポインタやコマンドで手に入るものを貼り付けていないか
- [ ] 入口ファイルは巨大マニュアルになっておらず、短く保たれているか
- [ ] スキルファイル（SKILL.md）は trigger 発火時だけで自己完結しているか（ポインタで飛ばしていないか）
- [ ] プロンプトテンプレートは呼び出し前提で自己完結し、引数を生プロンプトとして引用しているか
- [ ] 通常のプロンプトは暗黙前提に頼らず、入力・完了条件・出力形式を1回で渡しているか

## 具体例（契約化の Before/After）

Before（方向の提示・観測不能・過剰）:

```text
- ファイルを適切に処理する
- エラーはよきに計らう
- 大きいファイルは分割してもよい
- 将来的にストリーミング対応も想定しておく
```

After（trigger・境界・出力を持つ契約）:

```markdown
### 入力ファイルの処理

- 適用する：単一ファイル（.csv / .json）
- 適用しない：ディレクトリ一括（別コマンド）

| 入力               | 結果                               |
| ------------------ | ---------------------------------- |
| 存在する・拡張子OK | 変換して dist/ へ出力、終了コード 0 |
| 存在しない         | stderr へパス、終了コード 2        |
| 未対応拡張子       | stderr へ拡張子、終了コード 3      |

やらないこと：ストリーミング、ディレクトリ走査
```

差：主観語（「適切に」「よきに計らう」）が終了コードと stderr へ、将来要件（ストリーミング）が削除、曖昧な「大きい」が無くなり分岐が表へ。trigger（適用/非適用）と forbidden（やらないこと）が境界として効く。

もう一つ、入口ファイル（AGENTS.md 等）の地図としての Before/After:

Before（全文マニュアル・手続きの羅列）:

```text
## ビルド・テスト
ビルドは webpack で src/ から dist/ へ出力。webpack.config.js の中身は
entry: src/index.ts, output: { path: dist/, filename: bundle.js }, mode: production...
テストは jest。jest.config.js は testMatch: **/*.test.ts, collectCoverage: true...
リントは eslint。.eslintrc のルール: semi: always, quotes: single, ...（以下200行）
```

After（地図・ポインタ・停止条件）:

```markdown
## コマンド
- ビルド: `just build`（詳細は webpack.config.js）
- テスト: `just test`（設定は jest.config.js）
- リント: `just lint`（ルールは .eslintrc — ツールが真実、ここに転記しない）

## 構造
- `src/api/` — HTTP ハンドラ、1リソース1ファイル
- `src/services/` — ビジネスロジック（I/O なし）
- `tests/` — `src/` の構造を鏡写し

## 境界
- 変更前は必ず `just test` を通す（停止条件）
- `infra/` は承認なく触らない

深い情報は docs/architecture.md と各ディレクトリの README へ。
```

差：手続きの全文がコマンドとポインタへ。ツールで強制できる好み（リントルール）をツールへ委譲。ファイルパスの羅列ではなくディレクトリの役割を記述（`describe patterns, not paths`）。危険領域（`infra/`）が助言ではなく停止条件に。

## 出典（「地図として書く」の根拠）

- [OpenAI — Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering) — 「1,000ページの指示マニュアルではなく、地図を与えよ」。AGENTS.md を百科事典ではなく目次として扱い、約100行で深い情報源へのポインタを置く。invariants を強制し implementations は任せる。巨大マニュアルは「文脈を食う／全部重要＝何も重要でない／すぐ腐る／検証困難」で失敗する。
- [Vercel — AGENTS.md outperforms skills in our agent evals](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals) — 完全な文書ではなく「特定の文書ファイルがどこにあるか」を告げるインデックス。40KB→8KB（80%カット）でも 100% pass rate。「Compress aggressively. Design for retrieval.」
- [Daniel Vaughan — Why Coding Agents Fail at Navigation](https://codex.danielvaughan.com/2026/04/19/why-coding-agents-fail-at-navigation-agents-md-file-maps) — ナビゲーション誤りが全失敗の27–52%（ツール使用誤りは17%未満）。アーキテクチャ概観は効かず、「どこに何があるか・何をするか」を告げる機能的マップが探索ステップを33–44%減らす。「Describe patterns, not paths.」
