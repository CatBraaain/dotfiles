# 指示テキストの品質基準（standard）

品質の境界に加えて、共通の記法・配置規範・チェックリストもこの標準が所有する。手続きの骨格（規則セットの組み立て → 適用 → 検証 → 出力）は汎用スキルが担い、この標準は規則を提供する:

- 指示テキストを書く・直す・整理する → any-implement + `references/implement.md`
- ファイルとして残る指示テキストをレビューする → any-review

## 適用条件

- 適用する: 指示テキストを書くとき。対象種別はプロンプト・システムプロンプト・スキル・エージェント規範・プロンプトテンプレート、および使い捨ての通常のプロンプト。
- レビューの対象: ファイルとして残る指示テキストのみ。使い捨ての通常のプロンプトは対象外（収束の必要がなく、Verify で完結する）。
- 適用しない: コード・spec・設定ファイルなど、指示テキスト以外。

## Owns one domain

1つの指示テキストは1つのドメインを所有する。次のいずれかが観測できる場合は複数ドメインを含むため分割する:

- 変更理由・更新タイミングが異なる内容が混在する。
- 変更履歴やレビュー議論が、内容の一部分ごとに分かれている。

## 記法の選択

記法の選び方を間違うと、解釈のズレがそのまま実行のズレになる。性質と記法の対応、複数該当時の選択、誤った記法で書いてしまったときの直し方は readable-docs-standard（`../readable-docs-standard/SKILL.md` §記法の選択）が所有する。

指示テキストでは、優先順位付きフォールバックを Decision Ladder（後述）で書く。複数の記法が該当するときは、Decision Ladder をフロー図と同等の縛り強度として扱う。

## Decision Ladder（優先順位付きフォールバックの記法）

Decision Ladder は、優先順位付きの行動手順を記述する記法。最も単純・安全・低コストな選択肢から始め、要件を満たせない場合に限って、より強力・高コストな選択肢へ移行する。判断規則を設計するための記法であり、あらゆる分岐を置き換えるものではない。

**適用する場合** — 行動に明確な優先順位がある、低コスト・低リスクの行動を先に試すべき、失敗時の代替策や強い行動へ移る条件を明示する必要がある、または承認を求める境界があるとき。

**適用しない場合** — 独立した真偽条件、複数軸の網羅、循環する状態遷移、すべての条件を同時評価する場合。これらは条件文、マトリクス、状態機械を使う。

### 段の記法（4項目）

各段に必ず定義する:

- **適用条件** — その段を使える条件。
- **実行内容** — 許可された行動。
- **停止条件** — 目標を満たしたと判断できる観測可能な条件。
- **エスカレーション条件** — 次の段へ移る境界（承認と段のスキップの全体規則は「エスカレーションと承認」が所有する）。

適用条件を満たさない段は対象外とし、適用条件を満たす最初の段から開始する（全段が適用条件を満たさない場合は最終フォールバックへ移る）。要件と受入条件を完全に満たす最初の段で停止する。複数段が要件を満たすなら、より単純で安全な段を選ぶ。ラダーは調査・問題理解の代わりに使わない。

### テンプレート

```markdown
## Decision Ladder：[名前]

### 目標

[観測可能な成果と受入条件]

### 適用範囲

[このラダーが適用されるタスクと状況]

### 段

#### 第1段：[最も単純な選択肢]

- 適用条件：
- 実行内容：
- 停止条件：
- エスカレーション条件：

#### 第2段：[フォールバックの選択肢]

- 適用条件：
- 実行内容：
- 停止条件：
- エスカレーション条件：

### 例外

- [条件]の場合は、[段]へ直接移る。
- [条件]の場合は、実行前に承認を求める。

### 最終フォールバック

[どの段でも目標を満たせない場合の行動]

### 検証

[成功を報告する前に必要な証拠]
```

### 設計上の制約

- 観測可能な条件を使い、主観的な条件には判断者を明記する。
- 時間・範囲・試行回数・予算を制約する要件では、その上限を定義する。
- 各段の実行内容は明確な1つの行動を基本とする。
- ラダーの各段は、§Forbidden「怠ってはいけないことは禁止対象外」が定める必須事項を省略しない。

### エスカレーションと承認

次の段が、元に戻せない変更（ファイル・データの削除等）、許可範囲外の操作、依存追加、複数ファイル・複数モジュールにまたがる変更、金銭・セキュリティ・プライバシー・コンプライアンスリスク、または要件の目的・入力・完了条件を特定できない状態を伴う場合は、人間の承認を求める。承認を求めたら、承認が得られるまでその段の実行を停止する。下位の段を待つことでリスクが増える場合、または明示要件に違反する場合は、下位の段を飛ばしてよい。

## 契約として要求する記述

- 許可する行動を明示し、その範囲が一意に読み取れるようにする。
- 完了条件・受入条件は観測可能にする。ファイル生成、テスト成功、終了コード 0、特定の出力などで示す。
- 主観語には判断者と基準を添える（readable-docs-standard §具体性）。
- 適用する場合と適用しない場合をセットで、対象種別が本文から読み取れるように書く。片方だけだと過剰適用や誤適用が起きる。

## 配置規範

### 入口ファイル

常時読み込まれる入口ファイル（AGENTS.md / CLAUDE.md / システムプロンプト等）は、参照先・構造・硬い境界を示す地図として書く。手続き全文、長いポリシー、実装詳細、ツールで強制できる好み、ポインタやコマンドで手に入るものを貼り付けない。

### スキルファイル

SKILL.md は trigger 発火時だけで完結する手続き書とする。trigger は frontmatter の `description` が担う。本文に trigger・発火条件を述べるセクションを持たない。発火後に適用/非適用を判断する材料が必要なら、trigger ではなく適用条件・非適用条件として書く。必要な手順をポインタだけにせず、発火時に必要な情報を本文に置く。本文を超える規模の参照資料は `references/`、複数ステップの処理を伴うコードは `scripts/` へ分離する。1スキル1ドメインとする。

### プロンプトテンプレート

`/name` で呼び出すテンプレートは、呼び出し前提で自己完結させる。引数（`$@` 等）は本文へ変数展開せず、生プロンプトとしてコードブロックに引用する。引数の扱いを本文の処理契約から分離する。

### 通常のプロンプト

1回限りのプロンプトは、暗黙の過去文脈に頼らず、入力・完了条件・出力形式をその場で渡す。trigger、owns one domain、配置規範は適用しない。

## Forbidden（契約として禁止する記述）

- **方向だけの指示** — 「ベストプラクティスに従え」など、方向は示すが境界を持たない文。動機付けであって契約でない。
- **重複する記述** — 同じ主張の再掲。正本の集約は readable-docs-standard（§重複の排除）に従う。skill の `description` と本文セクション、規範とチェックリスト、複数セクション間で同じことを繰り返さない。
- **自己申告で終わる完了** — 客観的に検証できない「やりました」。
- **投機的な段・例外・将来用の分岐** — 「将来こうなるかも」は追加の理由にならない。1実装のインターフェース、不変値のための設定項目、使われないパラメータも同様。
- **怠ってはいけないことは禁止対象外** — 入力検証・エラーハンドリング・セキュリティ・データ損失防止・明示要求は、簡略化の対象外。境界を削ってはいけない。

## Output Contract（指示テキストの出力契約）

指示テキストは以下を満たす:

- **出力形式の明示** — テンプレ・フォーマット・構造を示す。形がぶれないように縛る。
- **出力しないことの明示** — 余計な解説・ファイル・変更を出さないよう境界を置く。
- **完成イメージ** — 具体例を1つ添える。形が一意に定まる。

例:

```markdown
## 出力

次の表だけを出力する。

| 項目 | 結果 |
| --- | --- |
| 入力ファイル | 変換済み |

表以外の解説、未依頼のファイル変更、推測による追加項目は出力しない。
```

## 判断記録（出力契約）

Decision Ladder を使った場合、内部の思考過程を長文で出力せず、次の要約だけを報告する:

```text
選択した段：[段の名前]
理由：[なぜ目標を満たすのか]
回避したエスカレーション：[不要だった上位段]
検証：[実行した確認または根拠]
```

## Verify（契約が守られたか）

指示テキストは以下を満たす。1つでも満たさなければ、書き手は直し、レビュアーは指摘する。各項目の判定文言の正本は参照先セクションとし、ここでは再掲しない。項目は対象種別で意味を持つものだけを適用する（対応は下の表）。

構造（契約の骨格）:

- [ ] 明確な trigger（§配置規範）
- [ ] owns one domain（§Owns one domain）
- [ ] 許可する行動の定義（§契約として要求する記述）
- [ ] 禁止する行動の定義（§Forbidden）
- [ ] 期待する出力の記述（§Output Contract）
- [ ] agent が従ったか検証可能なこと（§契約として要求する記述）

内容（契約の質）:

- [ ] 判断ロジックの記法（§記法の選択）
- [ ] 主観語の判断者・基準（§契約として要求する記述）
- [ ] 適用/非適用の両面と対象種別の明示（§契約として要求する記述）
- [ ] 重複の排除（§Forbidden）
- [ ] 投機的な段・例外・将来用分岐の排除（§Forbidden）
- [ ] 必須事項の省略なし（§Forbidden）

配置（ファイル種別の作法）:

- [ ] 入口ファイルは where を書き how を他へ任せる（§配置規範）
- [ ] 入口ファイルにポインタやコマンドで手に入るものを貼らない（§配置規範）
- [ ] 入口ファイルに貼り付け対象（手続き全文・長いポリシー・実装詳細・ツールで強制できる好み）を含まない（§配置規範）
- [ ] スキルファイルの trigger 発火時の自己完結（§配置規範）
- [ ] スキル trigger の description への集約（§配置規範）
- [ ] スキルファイルの適用/非適用は trigger ではなく適用条件・非適用条件として書く（§配置規範）
- [ ] プロンプトテンプレートの自己完結と引数の生引用（§配置規範）
- [ ] 通常のプロンプトの1回完結（§配置規範）

種別ごとの適用（○ = 適用、— = 適用外）:

| 項目群 | 入口ファイル | スキル | プロンプトテンプレート | 通常のプロンプト |
| --- | --- | --- | --- | --- |
| 構造: trigger | — | ○ | — | — |
| 構造: owns one domain | ○ | ○ | ○ | — |
| 構造: 許可/禁止/出力/検証可能性 | ○ | ○ | ○ | ○ |
| 内容（全項目） | ○ | ○ | ○ | ○ |
| 配置（各種別の項目のみ） | ○ | ○ | ○ | — |
| 配置: 通常のプロンプトの1回完結 | — | — | — | ○ |
