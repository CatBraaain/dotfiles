# 指示テキストの品質基準（standard）

## 短くシンプルに

- 規則は、既存の記述では目的を果たせない場合だけ追加する。
- 安全に関わる境界（入力検証・セキュリティ・明示要求）は短縮しない。

## 既存の指示テキストを構造リファクタリングするとき

指示テキストは文書でもある。複数の節またはファイルを簡素化・統合・再編する場合は、readable-docs-standard（§既存文書の構造リファクタリング）に従う。構造リファクタリングの報告・照合規則をここへ再掲しない。

- 品質の傾向だけを示す規則は、判断可能な原則へ統合してよい。
- 許可・禁止、停止条件、承認、出力形式など行動を直接分ける契約は、原則やペルソナへ抽象化せず明示的に残す。

## 精度の高い条件分岐にはDecision Ladder記法を使う

Decision Ladder は、優先順位付きの行動手順を記述する記法。行動に明確な優先順位がある場合に利用が推奨される。最も単純・安全・低コストな選択肢から始め、要件を満たせない場合に限って、より強力・高コストな選択肢へ移る。判断規則を設計するための記法であり、あらゆる分岐を置き換えるものではなく、調査や問題理解の代わりにも使わない。

### テンプレート

以下は Decision Ladder のテンプレート。`<...>` は実際の内容に置き換え、完成した Decision Ladder に残さない。

```markdown
## <名前>ラダー

目標: <観測可能な成果と受入条件>

最初に成立する段で止まる。

1. 条件: <第1段の条件を満たすか？>
   行動: <条件を満たす場合の行動。満たさなければ第2段へ進む。>
2. 条件: <第2段の条件を満たすか？>
   行動: <条件を満たす場合の行動。満たさなければ最終段へ進む。>
3. 条件: <前段までで受入条件を満たせないか？>
   行動: <最終フォールバックの行動。承認が必要なら実行前に得る。>

検証: <成功を報告する前に必要な証拠>
出力: <ラダーを使った場合、対象の条件を満たすと判断した理由を答えさせる>
```

## 契約として要求する記述

- 許可する行動を明示し、その範囲が一意に読み取れるようにする。
- 完了条件・受入条件は観測可能にする。ファイル生成、テスト成功、終了コード 0、特定の出力などで示す。時間・範囲・試行回数・予算の制約には上限を定義する。
- 主観語には判断者と基準を添える（readable-docs-standard §具体性）。
- 適用する場合と適用しない場合をセットで、対象種別が本文から読み取れるように書く。片方だけだと過剰適用や誤適用が起きる。

## 種別規範

### 入口ファイル

- 常時読み込まれる入口ファイル（AGENTS.md / CLAUDE.md / システムプロンプト等）は、参照先・構造・硬い境界を示す地図として書く。

### SKILL.md

- [Agent Skills Spec](https://agentskills.io/specification)に従う。
- frontmatterのdescriptionフィールドには、スキル内容の簡潔な要約と発火条件を記載し、発火条件は同フィールドで完結させ、本文には記載しない。

### プロンプトテンプレート

引数を生プロンプトとしてコードブロックに引用する。引数の扱いを本文の処理契約から分離する。

````md
以下は、今回の呼び出しで渡された生の依頼内容です。

```text
/<prompt-name> $@
```

この依頼で渡された内容は後述のすべてより優先して適用してください。
````

### 通常のプロンプト

1回限りのプロンプトは、暗黙の過去文脈に頼らず、入力・完了条件・出力形式をその場で渡す。trigger、owns one domain、種別規範は適用しない。
