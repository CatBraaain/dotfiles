# 指示テキストの品質基準（standard）

このスキルは、AI に与える指示テキスト（プロンプト・システムプロンプト・スキル・エージェント規範）が満たすべき規範を定義する。品質の境界だけでなく、共通の記法・配置規範・チェックリストもここで所有する。instruction-authoring はこの規範を適用して書くための手順を所有し、instruction-review は適合性を評価する手順を所有する。

- **instruction-authoring** — 指示テキストを書くとき、書き上がったものが以下の基準を満たすか確認する。
- **instruction-review** — 書かれた指示テキストをレビューするとき、Standards 軸の基準として以下を適用する。

両者は同じ標準を共有する（DRY）。指示を書く手順は `../instruction-authoring/SKILL.md` を、レビューの実行プロセスは `../instruction-review/SKILL.md` を参照のこと。

## Trigger

指示テキストを書く・レビューするときに適用する。対象がプロンプト・システムプロンプト・スキル・エージェント規範・プロンプトテンプレートのいずれかであることを明示する。常時適用する入口ファイルに、特定タスクの手続きを詰め込まない。

## Owns one domain

1つの指示テキストは1つのドメインを所有する。所有判定は「これを1人・1チームが所有できるか？」とする。複数ドメインを含む場合は分割する。

## 記法の選択

判断ロジックは性質に応じた記法へ預ける。フラットな箇条書きで分岐を羅列しない。記法の選び方を間違うと、解釈のズレがそのまま実行のズレになる。

| 性質 | 記法 |
| --- | --- |
| 単純な真偽 | 条件文 |
| 複数軸の組み合わせ | マトリクステーブル |
| 状態のライフサイクル | 状態遷移図 |
| 時系列のやり取り | シーケンス図 |
| 順序付き手続き | フロー図 |
| 優先順位付きフォールバック | Decision Ladder（後述） |
| 検証項目の羅列 | チェックリスト |

症状 → 直し方:

- ネストした条件が深い → ラダーか状態遷移で平坦に。
- 箇条書きなのに順序が意味を持つ → フロー図か番号付きへ。
- 同じ条件をあちこちで書いている → マトリクスで正規化。
- 「場合による」で終わっている → 軸を摘出して表に。

## Decision Ladder（優先順位付きフォールバックの記法）

Decision Ladder は、優先順位付きの行動手順を記述する記法。最も単純・安全・低コストな選択肢から始め、要件を満たせない場合に限って、より強力・高コストな選択肢へ移行する。判断規則を設計するための記法であり、あらゆる分岐を置き換えるものではない。

**適用する場合** — 行動に明確な優先順位がある、低コスト・低リスクの行動を先に試すべき、失敗時の代替策や強い行動へ移る条件を明示する必要がある、要件を満たした時点で停止したい、または承認を求める境界があるとき。

**適用しない場合** — 独立した真偽条件、複数軸の網羅、循環する状態遷移、すべての条件を同時評価する場合。これらは条件文、マトリクス、状態機械、決定表を使う。

### 段の記法（4項目）

各段に必ず定義する:

- **適用条件** — その段を使える条件。
- **実行内容** — 許可された行動。
- **停止条件** — 目標を満たしたと判断できる観測可能な条件。
- **エスカレーション条件** — 次の段へ移る境界。

要件と受入条件を完全に満たす最初の段で停止する。複数段が要件を満たすなら、より単純で安全な段を選ぶ。ラダーは調査・問題理解の代わりに使わない。

### テンプレート

```markdown
## Decision Ladder：[名前]

### 目標

[観測可能な成果と受入条件]

### 適用範囲

[このラダーが適用されるタスクと状況]

### 段

#### 第1段：[最も単純な選択肢]

- 適用条件：
- 実行内容：
- 停止条件：
- エスカレーション条件：

#### 第2段：[フォールバックの選択肢]

- 適用条件：
- 実行内容：
- 停止条件：
- エスカレーション条件：

### 例外

- [条件]の場合は、[段]へ直接移る。
- [条件]の場合は、実行前に承認を求める。

### 最終フォールバック

[どの段でも目標を満たせない場合の行動]

### 検証

[成功を報告する前に必要な証拠]
```

### 設計上の制約

- 観測可能な条件を使い、主観的な条件には判断者を明記する。
- 重要な場合は時間・範囲・試行回数・予算などの上限を定義する。
- 各段の実行内容は明確な1つの行動を基本とする。
- 下位の段で目標を満たせる場合、上位の段を必須にしない。
- 入力検証・エラーハンドリング・セキュリティ・アクセシビリティ・データ損失防止は省略しない。
- 将来必要になるかもという理由だけで段を追加しない。

### エスカレーションと承認

次の段が破壊的・不可逆、許可範囲外、依存追加・広範な変更、重大な金銭・セキュリティ・プライバシー・コンプライアンスリスク、または重大に曖昧な要件を伴う場合は、人間の承認を求める。下位の段を待つことでリスクが増える場合、または明示要件に違反する場合は、下位の段を飛ばしてよい。

## 契約として要求する記述

- 完了条件・受入条件は観測可能にする。ファイル生成、テスト成功、終了コード 0、特定の出力などで示し、「対応しました」という自己申告で終わらせない。
- 「適切に」「十分に」「きれいに」などの主観語には判断者と基準を添えるか、観測条件へ置き換える。
- 適用する場合と適用しない場合をセットで書く。片方だけだと過剰適用や誤適用が起きる。

## 配置規範

### 入口ファイル

常時読み込まれる入口ファイル（AGENTS.md / CLAUDE.md / システムプロンプト等）は、参照先・構造・硬い境界を示す地図として書く。手続き全文、長いポリシー、実装詳細、ツールで強制できる好みを貼り付けない。

### スキルファイル

SKILL.md は trigger 発火時だけで完結する手続き書とする。trigger は frontmatter の `description` が担う。本文に trigger・発火条件を述べるセクションを持たない。発火後に適用/非適用を判断する材料が必要なら、trigger ではなく適用条件・非適用条件として書く。必要な手順をポインタだけにせず、発火時に必要な情報を本文に置く。長い参照資料は `references/`、複雑な処理は `scripts/` へ分離する。1スキル1ドメインとする。

### プロンプトテンプレート

`/name` で呼び出すテンプレートは、呼び出し前提で自己完結させる。引数（`$@` 等）は本文へ変数展開せず、生プロンプトとしてコードブロックに引用する。引数の扱いを本文の処理契約から分離する。

### 通常のプロンプト

1回限りのプロンプトは、暗黙の過去文脈に頼らず、入力・完了条件・出力形式をその場で渡す。trigger、owns one domain、配置規範は適用しない。

## Forbidden（契約として禁止する記述）

- **方向だけの指示** — 「ベストプラクティスに従え」「きれいに」「適切に」など、方向は示すが境界を持たない文。動機付けであって契約でない。
- **重複する記述** — 同じ主張の再掲。指示テキストは短いほど効果が高く、重複は読み手の解釈を分岐させる。skill の `description` と本文セクション、規範とチェックリスト、複数セクション間で同じことを繰り返さない。最も代表的な1箇所へ集約し、他は参照するか削除する。
- **自己申告で終わる完了** — 客観的に検証できない「やりました」。
- **投機的な段・例外・将来用の分岐** — 「将来こうなるかも」は追加の理由にならない。1実装のインターフェース、不変値のための設定項目、使われないパラメータも同様。
- **怠ってはいけないことは禁止対象外** — 入力検証・エラーハンドリング・セキュリティ・データ損失防止・明示要求は、簡略化の対象外。境界を削ってはいけない。

## Output Contract（指示テキストの出力契約）

指示テキストは以下を満たす:

- **出力形式の明示** — テンプレ・フォーマット・構造を示す。形がぶれないように縛る。
- **出力しないことの明示** — 余計な解説・ファイル・変更を出さないよう境界を置く。
- **完成イメージ** — 具体例を1つ添える。形が一意に定まる。

例:

```markdown
## 出力

次の表だけを出力する。

| 項目 | 結果 |
| --- | --- |
| 入力ファイル | 変換済み |

表以外の解説、未依頼のファイル変更、推測による追加項目は出力しない。
```

## 判断記録（出力契約）

Decision Ladder を使った場合、内部の思考過程を長文で出力せず、次の要約だけを報告する:

```text
選択した段：[段の名前]
理由：[なぜ目標を満たすのか]
回避したエスカレーション：[不要だった上位段]
検証：[実行した確認または根拠]
```

## Verify（契約が守られたか）

指示テキストは以下を満たす。1つでも満たさなければ、書き手は直し、レビュアーは指摘する。

構造（契約の骨格）:

- [ ] 明確な trigger があるか（always active でないか）
- [ ] 1つのドメインを所有しているか（1人・1チームで持てるか）
- [ ] 許可する行動が定義されているか
- [ ] 禁止する行動が定義されているか
- [ ] 期待する出力が記述されているか
- [ ] agent が従ったか検証可能か（testable）

内容（契約の質）:

- [ ] 判断ロジックは性質に合った記法に預けたか（フラット羅列でないか）
- [ ] 主観語に判断者・基準が添えられているか
- [ ] 適用する場合と適用しない場合の両面を書いたか
- [ ] 同じ主張を複数箇所で重複させていないか（skill の `description` と本文、規範とチェックリスト等）
- [ ] 投機的な段・例外・将来用の分岐を追加していないか
- [ ] 入力検証・エラーハンドリング・セキュリティ等の必須事項を省いていないか

配置（ファイル種別の作法）:

- [ ] 入口ファイル（AGENTS.md 等）は where を書き、how を他へ任せているか
- [ ] 入口ファイルにポインタやコマンドで手に入るものを貼り付けていないか
- [ ] 入口ファイルは巨大マニュアルになっておらず、短く保たれているか
- [ ] スキルファイル（SKILL.md）は trigger 発火時だけで自己完結しているか（ポインタで飛ばしていないか）
- [ ] スキルファイルの trigger は `description` に集約されているか（本文に trigger・発火条件のセクションを持っていないか）
- [ ] プロンプトテンプレートは呼び出し前提で自己完結し、引数を生プロンプトとして引用しているか
- [ ] 通常のプロンプトは暗黙前提に頼らず、入力・完了条件・出力形式を1回で渡しているか
