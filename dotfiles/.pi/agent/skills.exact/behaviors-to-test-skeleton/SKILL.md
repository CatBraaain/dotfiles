# Behaviors To Test Skeleton

behaviors 仕様書（to-behaviors の出力）を実装空のテストスケルトンに変換する。テストタイトル = 要件（不変）、テスト実装 = 検証（可変）。behaviors の視覚的構造（マトリクステーブル・状態遷移図・シーケンス図）からテストを機械的に割り当て、タイトルまで作り、実装と本番コードは後続セッションで書く。

このスキルが作るテストは実装を空（`() => {}` / `pass`）にする。ゆえに後続セッションが実装のために読める情報はテストタイトル以外になく、会話履歴・behaviors 仕様書・このスキルの実行時文脈にもアクセスしない前提で動く。タイトルは後続セッションへ渡す唯一の要件であり、欠落・曖昧を許さず、自己完結した仕様として書く。behaviors 仕様書が入力だが、タイトル化の過程で観測可能な具体値が足りなければ推測せずユーザーへ質問する — これが本スキルの出力契約の核である。

## 入力

behaviors 仕様書（`behaviors/<feature-name>.md` または `BEHAVIORS.md`）。実装に依存しないユーザー観測可能な振る舞いが、マトリクステーブル・状態遷移図・シーケンス図で構造化済みである前提で動く。

実装の詳細（関数/クラス名・DBスキーマ・APIエンドポイント/シグネチャ）は behaviors 作成時点で切り捨て済みのため、ここでは再処理しない。behaviors に書かれていない実装詳細を勝手に補完してはいけない。

タイトル化で観測可能な具体値が足りない・曖昧な場合は推測せずユーザーへ追加質問する。

## behaviors 構造 → テストのマッピング

behaviors 仕様書の視覚的構造を、1テスト=1振る舞いの単位へ機械的に割り当てる。

### マトリクステーブル → 1行 = 1テスト

表の列を Given/When/Then へ読み替える:

- 条件・状態・入力の列 → Given
- 操作の列 → When
- 結果の列 → Then

1行を1つの When-Then にする。結果を変える行は別テストに分ける。

### 状態遷移図（`stateDiagram-v2`）→ 1遷移 = 1テスト

各遷移 `A --> B: イベント` を1テストにする:

- Given = 遷移元状態 A
- When = イベント
- Then = 遷移先状態 B（自己遷移なら A のままで、Then は振る舞いを書く）

### シーケンス図（`sequenceDiagram`）→ テスト群

時系列順に並ぶ観測点をテストへ割り当てる。1シーケンスを1テストにするか、観測可能な検証点ごとに分割するかは、1テスト=1振る舞いの原則に従う。

## テストタイトルの書き方

ルール:

- **言語**: `tests/` 配下の既存テストの言語に従う。なければチャットで使っている言語（デフォルト日本語）。テスト識別子（`test_*` 等）は英字のまま、シナリオ本文は文字列/docstring に書く。
- **構造**: 自然な文で Given-When-Then を表現する。`Given:`/`When:`/`Then:` のマーカーは使わない。
- **観測可能な具体値を必ず含める**: behaviors 仕様書の具体値をそのままタイトルに持ち込む。抽象語で書かれていたら具体値へ展開してからタイトルにする。
- **1テスト = 1振る舞い**: 1つの When-Then ペアにする。結果を変える Given は別テストに分ける。結果が変わらない補助的な前提だけ1テストに畳む。
- **グループ = Feature**: behaviors のファイル/機能単位でグループ（describe/クラス）を作り、その下にテストを並べる。
- **Then の主語は常に実装**: Then に置けるのはテスト対象（実装）が支配する値のみ。behaviors が「ユーザー観測」を主語にしている場合、テストでは実装が保証できる振る舞いへ読み替える（次節）。

## 主語を読み替える（Then に外部依存の値が来たら）

behaviors は「ユーザーが観測する」が主語。テストの Then は「実装が保証する」が主語。このズレを埋めるのが本スキルの固有の仕事。Then に外部システムが決定する値が来たら、実装が保証できる振る舞いへ読み替えてからタイトルにする:

- ✕ 「検索すると10件の結果が返る」 — 10件は外部バックエンドが決める（実装の責務外）
- ◯ 「検索要求は件数10を指定してバックエンドへ問い合わせる」 — 実装が保証できる

## 配置

1 Feature（behaviors ファイル単位）= 1ファイル。

**配置**: `tests/` 直下に置く。種別分け（`e2e/`/`unit/`/`acceptance/`）のサブディレクトリは作らない。**ドメイン単位のサブディレクトリを作り、その下に Feature 単位で1ファイル** を置く。

**命名・拡張子**: `tests/` 配下の既存ファイル慣習を検出して従う。なければ FWデフォルト（vitest/bun-test: `*.test.ts`、pytest: `test_*.py`）。

behaviors が `behaviors/<feature-name>.md` の構成なら、テストも同様に `<feature-name>` をベース名に使う。

## セルフチェック

各タイトルを書き終えたら、次のすべてを満たすか。1つでも満たさなければ修正するかユーザーへ質問する:

- [ ] behaviors 仕様書の構造（マトリクス/状態遷移/シーケンス）をすべてテストに割り当てたか（漏れがないか）
- [ ] Then に観測可能な具体値（ステータス/コード/形状）が含まれる
- [ ] Given に具体的な入力値と「何がその条件を満たすか」が含まれる
- [ ] When に操作経路（UI/API）が判別できる語がある
- [ ] Then の値は実装が決定するもの（外部システムの実応答件数・実時間・実DB内容等に依存していない）
- [ ] 結果を変える Given を別テストに分けた
- [ ] 誰が読んでも、実装の解釈が1通りに定まる

## 完成イメージ

入力（behaviors 仕様書のマトリクス）:

| 入力              | 状態       | 結果                                    |
| ----------------- | ---------- | --------------------------------------- |
| 未登録のメール    | 初回       | 登録成功、その後サインイン可能           |
| 既存のメール      | 2回目以降  | 拒否（状態409・エラーコード email_taken）|
| 空文字 / `@` なし | 任意       | 拒否（状態400・エラーコード invalid_email）|

出力（vitest）:

```ts
describe("ユーザー登録", () => {
  it("未登録のメールアドレスで登録すると、その後そのメールアドレスでサインインできる", () => {});
  it("既に存在するメールアドレスで登録すると、状態409・エラーコード email_taken で拒否される", () => {});
  it("空文字または @ のない文字列で登録すると、状態400・エラーコード invalid_email で拒否される", () => {});
});
```

出力（pytest。クラス=Feature、メソッドは機能の省略名、docstring=シナリオ、実装は `pass`）:

```python
class TestUserRegistration:
    def test_register(self):
        """未登録のメールアドレスで登録すると、その後そのメールアドレスでサインインできる"""
        pass

    def test_register_duplicate(self):
        """既に存在するメールアドレスで登録すると、状態409・エラーコード email_taken で拒否される"""
        pass

    def test_register_invalid_email(self):
        """空文字または @ のない文字列で登録すると、状態400・エラーコード invalid_email で拒否される"""
        pass
```

## このスキルがやらないこと

- テスト実装（Given/When/Then のコード化、assertion）は書かない。
- 本番コード（src/ 等）は一切触らない。
- テストを実行して通すことはしない（全テストは赤で正常）。
- behaviors 仕様書を再編集・追記しない（入力は読むだけ）。
- behaviors に無い実装詳細（クラス名/DB/エンドポイント）を推測で補完しない。足りなければ質問する。
- 外部要因（実APIの実応答件数・実時間・実ネットワーク・実DB内容など、実装が支配しない事象）を Then に置く claim を作らない。実装が保証できる振る舞いへ読み替える。
