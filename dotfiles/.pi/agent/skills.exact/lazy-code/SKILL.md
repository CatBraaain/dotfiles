# Lazy Code

## 前提と知識

readable-code は、ここで残したコードを読みやすくする規則を所有する。

## 原則

### 最小の実装

動作要件と安全境界を満たす、保守対象が最も小さいコードを選ぶ。上書きより削除、賢いコードより退屈なコード、自作より既存の仕組みを優先する。最小化は、明示要求、信頼境界での入力検証、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティの基本に優先しない。

### 選択と調査

最小化を調査や問題理解の代替にしない。変更の必要性、受入条件、実際のデータ・制御の流れを踏まえて変更範囲を選ぶ。バグ修正では、必要に応じて呼び出し元も調べ、症状ではなく根本原因に働きかける。

### 選択肢の優先度

同じ要件を満たせるなら、変更しない・削除する、既存の helper・型・パターンを再利用する、標準ライブラリを使う、プラットフォーム機能を使う、導入済みの依存を使う、必要最小限の固有コードを足す、の順に軽い選択肢を優先する。この優先度は探索順や実装を固定するものではなく、保守対象、既存設計、安全境界を踏まえて選ぶための目安である。

### 将来性と共有

現時点の動作に寄与しない抽象、設定、拡張点は避ける。ただし、明示要求または既存設計との整合のために必要なものは、その理由を優先する。

## 契約

### 適用範囲

- 適用する: コードの実装・修正・リファクタ・設計・依存選定・レビュー。
- 適用しない: コードを変更・評価しない調査、文書、設定だけの作業。残ったコードの名前・構造・コメントの可読性は readable-code が所有する。

### 境界・上限・出力

- 最小版と完全版の境界が曖昧な場合は、オーナーに最小版の範囲と省略範囲を示して確認する。確認前は、最小版・完全版のいずれも実装しない。
- 既知の上限を持つ簡略化を選ぶときは、上限と移行条件を、その簡略化を採用するコードのコメントまたは変更の設計記録に残す。
- コードをチャットに出力するときは、コードブロックの直後に、各1文の `省略: ...` と `追加条件: ...` を添える。

### 承認が必要な変更

明示要求のない新規依存、またはデータ損失・セキュリティ境界の変更・外部状態の不可逆な変更を伴う操作は、追加・実行前に承認を得る。
