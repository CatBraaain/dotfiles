# Lazy Code

動作要件と安全境界を満たす、保守対象が最も小さいコードを選ぶ。上書きより削除、賢いコードより退屈なコード、自作より既存の仕組みを優先する。

readable-code は、ここで残したコードを読みやすくする規則を所有する。

## 適用範囲

- 適用する: コードの実装・修正・リファクタ・設計・依存選定・レビュー。
- 適用しない: コードを変更・評価しない調査、文書、設定だけの作業。残ったコードの名前・構造・コメントの可読性は readable-code が所有する。

実装前に、変更対象と実際のデータ・制御の流れを読む。バグ修正では、変更候補の関数の呼び出し元をすべて検索し、根本原因を変更対象にする。

## Decision Ladder: 最小の実装

受入条件、入力、完了条件を特定できない場合は、推測で実装せず確認を求める。複雑な要求で最小版と完全版のどちらを求めるか特定できない場合は、最小版の範囲と省略範囲を示して確認を求める。ラダーは調査や問題理解の代替にしない。

目標: 明示された受入条件と安全境界を満たし、変更範囲を最小にする。
受入条件: 変更差分に、明示要求または承認のない新規依存、投機的な抽象、将来用の設定、未使用の拡張点を含めない。

最初に条件を満たす段の行動を実行する。行動後に目標と受入条件を確認し、満たせば停止する。満たさなければ次段へ進む。

1. 条件: 現状が受入条件と安全境界を満たしている、または変更の観測可能な必要性が示されていないか？
   行動: 変更せず、変更不要の根拠を記録する。
2. 条件: 既存の helper、型、パターンだけで重複実装なく受入条件を満たせるか？
   行動: 既存の仕組みを再利用する。
3. 条件: 言語の標準ライブラリだけで、新規依存や自作の汎用処理なく受入条件を満たせるか？
   行動: 標準ライブラリを使う。
4. 条件: ブラウザ、CSS、DB制約などのプラットフォーム機能だけで、アプリケーションコードを追加せずに受入条件を満たせるか？
   行動: プラットフォーム機能を使う。
5. 条件: 導入済みの依存だけで、新規依存や自作の汎用処理なく受入条件を満たせるか？
   行動: 既存の依存を使う。
6. 条件: 1つの式または文だけで、抽象・設定・補助ファイルを増やさずに受入条件と安全境界を満たせるか？
   行動: その式または文だけを追加・変更する。
7. 条件: 第1〜6段の行動では目標と受入条件を満たせないか？
   行動: 必要最小限の固有コードを追加・変更する。明示要求のない新規依存または高リスクな操作が必要なら、実行前に承認を得る。

### 例外

- 明示要求、信頼境界での入力検証、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティの基本は、より小さい段のために省略しない。
- 新規依存は、明示要求または承認なしに追加しない。

### 検証

対象と実際の流れを読んだ根拠、選択した段、受入条件を満たすテストまたは観測結果を確認する。バグ修正では、呼び出し元の検索結果と根本原因への変更を確認する。

## 禁止

- 要求されていない抽象、将来用のスキャフォールド、使われないパラメータや設定を追加しない。
- 同じ機能を既存実装の探索なしに再実装しない。
- 既知の上限を持つ簡略化を、上限と移行条件の記録なしに採用しない。

既知の上限を持つ簡略化には、上限とアップグレード条件を示す `ponytail:` コメントを残す。例: `# ponytail: account は 100 件以下。超えたら indexed lookup に置き換える`。

## 出力

コードをチャットに出力する場合だけ、コードの後に省略したものと追加条件を最大3行で示す。実装していない追加ファイル、抽象、依存は出力しない。

例:

```text
skipped: retry queue, add when the API exposes retryable failures
```

## Verify

該当する項目をすべて満たす。

- [ ] Decision Ladder の最初に受入条件を満たす段を選んだ。
- [ ] 対象と実際の流れを読んでから変更した。
- [ ] 明示要求と安全境界を省略していない。
- [ ] 新規依存、投機的な抽象、未使用の拡張点を追加していない。
- [ ] 既知の上限を持つ簡略化に `ponytail:` コメントがある。
- [ ] バグ修正では、呼び出し元を検索し根本原因を変更した。
