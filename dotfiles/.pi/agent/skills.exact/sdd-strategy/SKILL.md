# SDD Strategy

ロジックを伴う成果物は **spec（＝観測可能な振る舞いの仕様書）** を唯一の仕様ソースとして開発する（SDD: Spec Driven Development）。オーナーは spec だけ読んで go/no-go を出し、実装コードの詳細は読まない。要件文書と分離して二重管理しない。テストは AI の収束作業用で、オーナーは内容を確認しない。**収束条件 ＝ spec と実装が一致し、AI レビューが通ること** をもって「完成」とする。

本スキルはその開発フロー（フェーズ・収束ルール・乖離検知）を定める。spec の書き方は `/skill:sdd-spec`、spec↔テスト↔実装の監査は `/skill:sdd-audit` を参照。

## フェーズ

1. **要件合意** — 会話で要件を確定
2. **spec 整備** — `sdd-spec` で視覚的仕様書（マトリクス/状態遷移図/シーケンス図）を新規作成・修正・改善する。`SPEC.md`（単一機能）または `spec/<feature>.md`（複数機能）、混在禁止
3. **go/no-go** — オーナーが spec を読んで承認。spec を変える ＝ 要件変更 ＝ 必ず再レビュー
4. **実装** — テスト + 本番コード。テストは AI の収束作業用でオーナーは読まない。ロジックを伴うもの（スクリプト等）が対象、設定ファイル群は対象外
5. **監査** — `sdd-audit` で spec ↔ テスト ↔ 実装 を照合、ギャップレポート（指摘のみ）
6. **収束** — ギャップを修正し再監査、指摘 0 で完成

## 収束ルール

- **収束ループ（監査 → 修正 → 再監査）は提案まで**。ギャップレポートと修正案を出したら止まり、オーナーの承認なく修正を適用・再監査しない
- **オーナーが収束ループの実行を承認したときは `/new-session` で切り替えてから回す**。前段（spec 整備・初回実装）の会話ノイズを排除し、spec と現状コードだけを入力として監査するため

## 乖離検知

- spec と実装の整合は、**差分ベースで AI に一致チェック**させる（commit/PR 時、変更ファイルに対応するセクションのみ）。全文一致は重すぎるのでやらない
- spec とテストは紐付けない（ID 紐付けをやめた）。乖離の自動検知はせず、AI レビューに任せる
- **最終防波堤は AI レビュー**。乖離の最終検知も腐り発見も AI に委ねる

## 背景とトレードオフ

- **前提：ドキュメントは腐る**。仕様と実装の乖離は時間で必ず起きる
- 旧 tdd 戦略は「テスト＝仕様」の単一ソース化でこれを防いだが、テストに分岐を自然言語で網羅するのは可読性に限界があり、オーナーが「網羅性」を頭で検証するのは無理だった
- 可読性を優先し、視覚的（テーブル・mermaid）な spec を主軸に切り替えた。この切り替えが下記の代償を生む
- **二重管理が復活**：spec + テスト。旧 tdd 戦略が避けていたコストを再度負う
- **spec が腐りうる**：差分 AI 一致チェック + AI レビューで軽減するが、完全解決ではない。AI 評価の精度が上限になる
- **spec とテストの乖離を自動検知しない**：ID 紐付けをやめた代償。テスト不足が機械的に分からず、AI レビュー頼み
- **AI レビューへの依存が大きい**：AI が弱いと全体が弱い
- **図表ツール依存**：mermaid レンダラ前提。描けない環境だと価値が半減する
- 緩和策として、spec を「ユーザーが観測可能な振る舞いのみ」に絞る。実装変更で更新不要な層に置き、腐りにくさを部分回復する
