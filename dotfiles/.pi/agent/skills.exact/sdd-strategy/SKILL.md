# SDD Strategy

ロジックを伴う成果物は **spec（＝観測可能な振る舞いの仕様書）** を唯一の仕様ソースとして開発する。オーナーは spec だけ読んで go/no-go を出し、実装コードやテストの詳細は読まない。要件文書と spec を分離して二重管理しない。

本スキルは、spec の作成だけを行う場合を含め、SDD の入口と収束フローを一つに定める。背景・判断経緯・トレードオフは `sdd-strategy/note.md` に置く。spec の書き方はこのファイル、spec・テスト・実装の適合性レビューは `sdd-review` が担う。

## 依頼モード

依頼文に明示された完了範囲を次の表で決める。明示がないロジック変更は、spec-only か実装まで行うかを確認してから進める。

| 依頼 | 実行する範囲 | 変更してよいもの | 停止条件 |
| --- | --- | --- | --- |
| specだけ作成・specを整理 | 要件確認 → spec作成・修正 → specセルフチェック | specのみ | specを出力し、実装・テスト・レビューを行わず停止 |
| 実装して | 要件確認 → spec → go/no-go → 実装・テスト → `sdd-review` | spec、テスト、本番コード | `sdd-review` のギャップレポートと修正案を提示して停止 |
| 適合性をレビューして | `sdd-review` による spec・テスト・実装の照合 | 変更しない | ギャップレポートのみを出力して停止 |
| 指摘を直して収束して | 承認済み `sdd-review` 結果に基づく修正 → 検証 → `sdd-review` | 承認された範囲のspec、テスト、本番コード | blocking 指摘が0件になり、検証が通る |

spec-only モードでは、要件が曖昧・欠落している場合に推測で spec を完成させず、追加質問で停止する。spec の変更は要件変更に相当するため、実装中に spec を変更した場合は go/no-go をやり直す。

## 全体フロー

1. **要件合意** — 会話で対象、利用者、観測可能な振る舞い、適用範囲を確定する。
2. **spec 整備** — 下記の spec 作成規約に従い、`SPEC.md` または `spec/<feature-name>.md` を新規作成・修正する。
3. **go/no-go** — オーナーが spec を読み、要件を承認する。spec-only モードはここで停止する。
4. **実装** — 承認済み spec に対応するテストと本番コードを作る。テストは AI の収束作業用で、オーナーは内容を確認しない。
5. **適合性レビュー** — `sdd-review` を使い、spec・テスト・実装を照合する。レビューでは編集・テスト実行をしない。
6. **収束** — オーナーがレビュー結果を承認した後、承認範囲のギャップを修正し、通常の検証と `sdd-review` による再レビューを繰り返す。blocking 指摘0件で完了する。

設定ファイル群だけの変更は、このフローの対象外とする。ただし、設定がユーザーに観測可能なロジックを持つ場合は対象に含める。

## 収束ルール

- `sdd-review` による初回レビューは指摘のみとし、テスト・本番コード・specを編集せず、テストも実行しない。
- 初回レビューの出力は、ギャップの場所・種別・重要度と、修正案までに限定する。修正を適用せず停止する。
- オーナーが収束実行を承認した場合は `/new-session` で切り替えてから、specと現状コードを入力として収束を開始する。前段の会話ノイズを持ち込まない。
- 収束実行では、承認済みの修正範囲だけを変更し、format・lint・typecheck・testなどプロジェクトの検証を実行してから再レビューする。
- specを変更する修正は要件変更である。変更後はオーナーの再承認なしに実装・再レビューを続けない。
- 適合性レビューの照合軸・指摘種別・出力形式は `sdd-review/SKILL.md` に従う。
- informational 指摘は残っていても blocking 指摘0件なら完了条件を満たす。ただし、残した理由を完了報告に記載する。

## 乖離検知

- commit/PRなどの変更確認では、変更ファイルに対応する spec セクションを差分ベースで AI に一致チェックさせる。全文一致は行わない。
- spec とテストをIDで機械的に紐付けない。specとテストの対応、テストと実装の忠実性、実装のspec外振る舞いは、`sdd-review` が照合する。
- 最終防波堤は AI レビューである。テストの実行成功だけを、specとの一致の証拠として扱わない。

# Spec 作成規約

## spec の定義

spec は **ユーザーが観測可能な振る舞いのみ** を記載した仕様書である。

- **書く**：ユーザーが直接・間接に観測できる入出力、状態、エラー、振る舞い、パフォーマンス特性。
- **書かない**：結果が同じなら観測できない内部最適化、関数・クラス名、モジュール構造、DBスキーマ、内部データ構造、APIシグネチャ。
- 内部処理でも、結果としてユーザーに現れるものは書く。

## 独立した仕様書

specは1ファイルで完結し、過去の仕様・要件文書・会話履歴なしで理解できるようにする。冒頭で対象の名称・目的・適用範囲・利用者の役割を示す。

- 現在形で書く。廃止・削除・変更前後・「新規に追加」などの履歴を書かない。
- 仕様の対象と、機能を識別する用語を文書内で定義する。
- 仕様に含める対象と振る舞いを肯定形で記載する。候補・却下案・非目標を持ち込まない。
- 「今回」「前述の要件」「先ほどの案」「既存のもの」など、文書外の文脈を参照しない。
- 変更理由・意思決定の経緯を書かない。背景は `note.md` の責務である。

## 重複の排除

各振る舞いは1箇所にのみ定義する。同じ振る舞いを複数のセクション、図、テーブルに重複して書かない。別角度から触れる場合は定義を再掲せず、該当セクションを参照する。具体例の再掲は、直近の定義を理解するために必要な場合だけ許可する。

## 入力と配置

会話で合意した内容から、観測可能な振る舞いだけを抽出する。観測可能な具体値が定まらない場合は推測せず、ユーザーへ質問する。

- 単一機能・小規模：`SPEC.md`
- 複数機能：`spec/<feature-name>.md`
- 1プロジェクト内で `spec/` と `SPEC.md` を混在させない。既存の配置があれば維持する。
- 機能は実装モジュールではなく、ユーザーが認識する単位で切る。
- 要件文書・設計書を別ファイルで作らない。specを唯一の仕様ソースにする。

## フォーマット

Markdownで記述し、分岐・状態・時系列・順序を視覚的に構造化する。フラットな自然言語による分岐の羅列は避ける。

| 構造 | 記法 |
| --- | --- |
| 条件で結果が変わる分岐 | マトリクステーブル |
| 状態の変化 | Mermaid `stateDiagram-v2` |
| 時系列のやり取り | Mermaid `sequenceDiagram` |
| 順序付き手続き | Mermaid `flowchart` |

Mermaidは1図1主題とし、ノード名は意味のある名詞・動詞句、矢印ラベルは短い条件・イベント名にする。状態遷移は `LR`、シーケンスは既定の縦方向、フローは内容に応じた `TD` / `LR` を使う。

`flowchart` のノード形状は次のとおりとする。分岐は必ずひし形にする。

| 役割 | 形 | 記法 |
| --- | --- | --- |
| 開始 / 終了 | 丸（スタジアム） | `id([開始])` |
| 処理 | 四角 | `id[処理]` |
| 分岐 | ひし形 | `id{条件?}` |
| 入出力 | 平行四辺形 | `id[/入力/]` |

分岐を条件と結果の表にできる場合は、flowchartではなくマトリクステーブルを使う。

## spec セルフチェック

- [ ] すべてユーザーが観測可能な振る舞いか
- [ ] 観測不能な内部最適化や実装構造がないか
- [ ] 分岐・状態・時系列・手続きが適切な視覚表現に委ねられているか
- [ ] 各振る舞いが1箇所にのみ定義されているか
- [ ] Mermaidの各図が1主題で、ノード名・矢印ラベルが意味を持つか
- [ ] flowchartの分岐がすべてひし形か
- [ ] 冒頭だけで対象・目的・適用範囲・利用者を特定できるか
- [ ] 用語が定義され、会話中だけ通じる省略語がないか
- [ ] 履歴、文書外の文脈、候補・却下案・非目標、変更理由が混入していないか
- [ ] 配置がプロジェクト内で統一され、既存specを重複作成していないか
- [ ] 要件文書と別管理せず、specが唯一の仕様ソースになっているか
