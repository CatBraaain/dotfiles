# Readable Docs

唯一の指標は **読者が文書だけで目的を果たすまでにかかる時間**。
理解したとは「読者が問いへの答えを文書内で見つけ、次の行動を誤らず決められる状態」になったこととする。

文書は、正確でも冗長なら読まれない。まず減らし、次に読みやすくする。

## 適用条件

- 適用する: ドキュメント（README・設計書・spec・報告書・ガイドなど）を書く・直す・整理する・レビューするとき。
- 適用しない: コードとそのコメント（readable-code-standard）。指示テキスト固有の品質契約（Forbidden・Output Contract・Verify）は instruction-standard、spec の内容規則（観測可能な振る舞い・照合単位）は sdd-standard が所有する。本標準は、それらの文書にも共通する文書としての可読性の規則を所有する。

## 適用の順序（下のレベルに逃げる前に、上で済ませられないか）

1. **削る** — 重複・冗長を先に消す。消せる文は、どの修辞より読みやすい。
2. **構造** — セクションを読者の質問順に並べる。1セクション1主題。
3. **記法** — 分岐・状態・時系列は図表へ預ける（下記「記法の選択」）。
4. **文** — 具体名・肯定形・短文で語らせる（下記「具体性」）。

強調や装飾で誤魔化したくなったら、上のレベルに戻る。強調は最後の手段。

## 重複の排除（効果が最大）

重複は読み手の解釈を分岐させ、片方だけ更新されたとき嘘になる。「症状 → 直し方」で読む:

- 同じ主張が複数箇所にある → 正本を1箇所に集約し、他は参照するか削る。
- 同じことを言う別セクションがある → 1セクションに統合する。読者が先に読む方へ統合し、残りを参照か削除にする。
- 前置き・要約・結論が本文の繰り返し → 役割を1つに絞る。冒頭は目的と結論だけにして、詳細は本文へ置く。
- 図や表が本文と同じ内容を二重に説明 → どちらかに寄せる。図に任せたら本文は読み取り方の結論だけを書く。
- 具体例の再掲 → 直近の定義を理解するために必要な場合だけ許可する。
- 空セクション・定型文のためだけのセクション → 消す。

## 記法の選択

判断や構造は性質に応じた記法へ預ける。フラットな箇条書きで分岐を羅列しない。記法を間違うと、解釈のズレがそのまま誤読になる。

| 性質 | 記法 |
| --- | --- |
| 単純な真偽 | 条件文 |
| 条件で結果が変わる分岐 | マトリクステーブル |
| 対象の対比・対応関係 | 表 |
| 状態のライフサイクル | 状態遷移図 |
| 時系列のやり取り | シーケンス図 |
| 順序付き手続き | フロー図（線形なら番号付きリスト） |
| 検証項目の羅列 | チェックリスト |

複数の記法が該当するときは、より構造を縛れる方（状態遷移図 > シーケンス図 > フロー図 > マトリクステーブル > 条件文）を選ぶ。

症状 → 直し方:

- ネストした条件が3段以上 → 状態遷移や優先順位リストで平坦に。
- 箇条書きなのに順序が意味を持つ → 番号付きリストへ。
- 同じ条件が2箇所以上 → マトリクスで正規化。
- 「場合による」で終わっている → 軸を摘出して表に。

## 表と箇条書きの選択

表は「同じ軸で並べて比べる」仕事に強く、箇条書きは「項目ごとに違う形で述べる」仕事に強い。

- **表を選ぶ**: 複数の項目が同じ属性を持ち、読み手に項目同士・属性同士を比べさせたいとき。各項目が「ラベル: 値」の同じ型で並ぶなら、ラベルを列見出しにして行を項目へできる。
- **箇条書きを選ぶ**: 項目ごとに述べる構造が違い、行を揃えると無理があるとき。各項目が一文に収まらず説明的なとき。

セルには比べるための値だけを置き、長い説明は本文へ切り出す。

症状 → 直し方:

- 箇条書きの各行が同じ語彙・同じ型で並んでいる → 共通語彙を列見出しにした表へ。
- 表のセルが折り返して行の高さが崩れている → 説明を本文へ切り出し、セルは値だけにする。それでも崩れるなら箇条書きへ戻す。
- 行ごとに列の意味が揃わず、比べる軸がない表 → 箇条書きへ。

## 図表の作法

状態遷移図には `stateDiagram-v2`、シーケンス図には `sequenceDiagram`、フロー図には `flowchart` を使う。Mermaid は1図1主題とし、ノード名は意味のある名詞・動詞句、矢印ラベルは短い条件・イベント名にする。状態遷移図は `LR`、シーケンス図は既定の縦方向、フロー図は内容に応じた `TD` / `LR` を使う。

flowchart のノード形状は次のとおりとする。分岐は必ずひし形にする。

| 役割 | 記法 |
| --- | --- |
| 開始 / 終了 | `id([開始])`（スタジアム） |
| 処理 | `id[処理]`（四角） |
| 分岐 | `id{条件?}`（ひし形） |
| 入出力 | `id[/入力/]`（平行四辺形） |

条件と結果の表にできる分岐は、フロー図ではなくマトリクステーブルにする。

## 文書の自己完結

文書は1ファイルで、過去の文書や会話履歴なしで理解できるようにする。

- 冒頭で対象の名称・目的・適用範囲・読者を示す。
- 現在形で書く。廃止・変更前後などの履歴や変更理由を書かない。背景は判断記録の責務である。
- 「今回」「前述の」「先ほどの」など、文書外の文脈を参照しない。
- 用語を文書内で定義し、会話中だけ通じる省略語を使わない。

## 具体性

- 「適切に」「簡単に」などの主観語には判断者と基準を添えるか、観測できる条件へ置き換える。
- 数値・名前は具体値で書く。「いくつかの」より実数、「関係各所」より名前。
- 形を一意にしたい出力には、具体例を1つ添える。
- 例の題材は読者の既知度で選び、書き手の手近さで選ばない。直前の会話や編集中リポジトリの固有名を例に流用すると、一般則を特定の状況だけの話に見せ、例の理解に文書外の知識を要求する。規則を説明する例は `backend` / `frontend` のように読者一般に通じる題材に置き換える。説明対象そのものを実名で示すときはこの限りではない。

## レビュー時の使い方

読んでいて「立ち止まった」「戻って読み直した」「同じ話がまた出てきた」箇所が、本スキルの適用対象。
その箇所を上の症状リストに当てはめ、直し方を一つ選ぶ。

## セルフチェック

書いた・直した文書が次を満たすか。判定文言の正本は参照先セクションとし、ここでは再掲しない。

- [ ] 同じ主張の正本が1箇所に集約されているか（§重複の排除）
- [ ] 同じことを言うセクションが1つに統合されているか（§重複の排除）
- [ ] 空セクション・定型文のみのセクションがないか（§重複の排除）
- [ ] 分岐・状態・時系列・順序が適切な記法に委ねられているか（§記法の選択）
- [ ] 比べる軸が揃う一覧が表になり、セルが値だけに保たれているか（§表と箇条書きの選択）
- [ ] 各図が1主題で、ノード名・ラベルが意味を持ち、本文と重複していないか（§図表の作法）
- [ ] 冒頭だけで対象・目的・適用範囲・読者を特定できるか（§文書の自己完結）
- [ ] 履歴・文書外の文脈・会話中だけの省略語が混入していないか（§文書の自己完結）
- [ ] 主観語に判断者と基準があり、具体値・具体例が添えられているか（§具体性）
- [ ] 例が直前の文脈の固有名に引きずられておらず、読者一般に通じる題材になっているか（§具体性）
