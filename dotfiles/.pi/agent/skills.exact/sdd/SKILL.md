# SDD

## 前提と知識

### 用語

- specは、ユーザーが観測可能な振る舞いを定める仕様書である。oracleは、適合性レビューで真実の基準にするspecである。
- SDD適合性レビューは、spec・テスト・実装を照合する4軸のギャップレポートである。乖離検知は、差分に現れた観測可能な振る舞いだけをspecへ対応付ける確認である。

## 契約

### 責務境界

- `sdd/SKILL.md`はSDDを適用する条件、spec作成、SDD適合性レビュー、乖離検知、SDD収束時の引継ぎを所有する。
- `../review/SKILL.md`は一般の契約・原則の評価、`../converge/SKILL.md`は一般の修正・検証・再評価の反復を所有する。SDDの4軸をreviewへ移さず、反復ループをsddへ複製しない。
- SDDの作業順は、要件合意、spec整備、オーナーのgo/no-go、明示された実装、SDD適合性レビュー、必要時のconvergeによる収束である。

### 仕様ソースとoracle

- specは唯一の仕様ソースであり、要件文書・設計書と二重管理しない。適合性レビューではspecをoracleとする。
- オーナーはspecだけを読んでgo/no-goする。実装コードとテストの詳細はgo/no-goの判断材料にしない。

### 観測可能な振る舞い

- specにはユーザーに現れる入出力、状態、エラー、結果、パフォーマンス特性だけを書く。観測不能な実装構造は書かない。

### 適用条件

- 適用対象は、ユーザーが観測できる振る舞いを持つロジックを伴う成果物と、そのようなロジックを持つ設定である。
- 振る舞いを変えないリファクタ、静的な設定値、コード以外の文書、設計判断だけにはspecを新設しない。

### specの作成・修正

- specは1ファイルで自己完結させ、対象と振る舞いを肯定形で書く。候補、却下案、非目標は入れない。各振る舞いは1箇所だけで定義する。文書の自己完結は`../readable-docs/SKILL.md`の「文書の自己完結」、一般的な重複排除は同Skillの「重複の排除」を正本とする。
- 合意済み内容から観測可能な振る舞いだけを抽出する。観測可能な具体値が未確定なら推測せず質問して止まる。
- 単一機能は`SPEC.md`、複数機能は`spec/<feature-name>.md`に置く。プロジェクト内で両形式を混在させず、既存配置があれば維持する。機能は実装モジュールではなくユーザーが認識する単位で分ける。
- Markdownで書き、分岐・状態・時系列・順序は、関係を最も直接に表せる視覚構造にする。記法の選択は`../readable-docs/SKILL.md`の「記法の選択」を正本とする。

### 振る舞いの照合単位

次の表を1回だけ置き、spec作成とSDD適合性レビューで共用する。

| spec構造 | 1振る舞い | Given / When / Then |
|---|---|---|
| マトリクステーブル | 1行 | 列を条件・状態・入力 / 操作 / 結果として読む。結果を変える行は分ける。 |
| 状態遷移図（`stateDiagram-v2`） | 1遷移 | 遷移元 / イベント / 遷移先として読む。 |
| シーケンス図（`sequenceDiagram`） | 観測点群 | 時系列の観測点を1シーケンスまたは観測点ごとの振る舞いへ分ける。1テストは1振る舞いにする。 |
| フロー図（`flowchart`） | 分岐から観測可能な終端までの1経路 | 開始時の状態と分岐条件 / 経路上の操作 / 終端の観測可能な結果として読む。観測不能な内部ノードだけの経路は数えない。 |

### spec作成・修正時の出力

- 完了報告はspecのパス、`Verify: n/n 合格`、各セルフチェックの観点・判定（合格または適用外）・spec内根拠を含める。未実行の確認を合格と報告しない。
- セルフチェックは、観測可能性、内部構造の不混入、候補等の不混入、`../readable-docs/SKILL.md`の「セルフチェック」、配置と重複、唯一の仕様ソースを個別に確認する。

### SDD適合性レビュー

#### 入力と不足時の扱い

spec、既存テスト、既存本番コードを読む。テストはテストランナー設定と既存命名規則を確認し、`tests/`、`test/`、本番コードと同じディレクトリの`*.test.*`・`*.spec.*`を読む。複数frameworkの混在を許容する。本番コードは、テストが参照する実装と、公開入口を持つ`src/`・`lib/`等の慣習上の本番コードを読む。

- specがなければ質問して停止する。
- テストがなければcoverageで全振る舞いを漏れとして出し、fidelityをskipする。
- 本番コードがなければcoverageだけを行い、fidelityと余剰をskipする。
- spec外の実装詳細を推測で補完しない。

#### 実装の分解

公開入口、入口ごとの観測可能な結果分岐を抽出し、観測不能な内部最適化は除外する。各抽出結果をspecへ対応付け、対応がなければ余剰実装とする。

#### 照合単位と4軸

4軸を1コンテキストで連続して照合する。spec起点のcoverageと実装起点の余剰を必ず両方行う。種別と重要度は次の表だけで定義する。

| 軸 | 照合 | 種別と重要度 | 判定規則 |
|---|---|---|---|
| coverage | spec ↔ テスト | 漏れ（高）、過剰（低）、順序ズレ（低） | specの全振る舞いにテストがあるかを確認する。テストがspec外を検証すれば過剰。specの文書上の順序と対応テストの順序が異なれば順序ズレ。spec外テストは対応テスト群の後ろに置く。 |
| fidelity | テスト ↔ 実装 | 偽陽性（高）、主語ズレ（高） | 実装を読み、モック等で実装経路を叩かない、恒真、要求経路と異なるテストを偽陽性とする。Thenが実装でなく外部依存値を主語にするときは主語ズレとする。 |
| 余剰 | 実装 → spec | 余剰実装（高） | 実装の観測可能な入口または結果分岐にspecの対応記述がなければ余剰実装とする。テストだけのspec外検証である過剰とは区別する。修正案はspec追記と実装削除の選択肢を示せるが、適合性レビューでは採否を決めない。 |
| 逆指摘 | 実装・テスト → spec | 曖昧（低） | 複数の実装またはテストが異なる解釈で動けるspec記述を曖昧とする。specに記述がない実装は余剰であり、逆指摘にしない。 |

#### 出力とセルフチェック

- 対象を編集せず、テストを実行せず、コードの可読性・設計品質を審査しない。各指摘は`[軸 / 種別 / 重要度] 要約`、場所、問題、影響、修正案を含める。
- 指摘がなくても4軸すべてについて確認観点、`問題あり`・`問題なし`・`skip`の判定、根拠を出す。`skip`は入力不足と未評価の軸を根拠に書く。`n/n`または「適合している」だけで完了を報告しない。
- 実装起点の全振る舞いとspec対応、spec全構造のテスト有無、全漏れ、順序、モック等の偽陽性、Thenの主語、指摘4要素、問題なし軸の根拠を個別に確認する。

### SDD収束時の引継ぎ

1. ロジックを実装する明示依頼では、対象、利用者、観測可能な振る舞い、適用範囲を合意し、specを整備してオーナーのgo/no-goを受けてから実装へ進む。specだけの依頼はgo/no-go後に止まる。
2. SDD適合性レビューは、spec・テスト・本番コードを入力に上記の4軸を実施し、編集・テスト実行なしでギャップレポートを出して止まる。
3. ギャップの修正・検証・再評価を依頼されたときは、`../converge/SKILL.md`を適用する。修正後の4軸再レビューを省略しない。
4. 修正でspecを変える場合は、変更後specのgo/no-goを受けるまで実装・SDD適合性レビューを再開しない。
5. SDD適合性の収束完了は、convergeの収束条件を満たし、最終のSDDギャップレポートに高重要度の指摘がなく、実行すべき検証が通ったときだけ報告する。

### 差分の乖離検知

commit・PRなどの差分確認では全文照合をせず、差分で変わった観測可能な振る舞いだけを確認する。

1. 差分、変更前後の公開入口、既存specを読む。公開入口または観測可能な振る舞いを特定できなければ質問して停止する。
2. 各振る舞いをspecの節、表行、図の遷移または経路へ対応付ける。ファイルパスや実装モジュール名だけで対応付けない。
3. 次の表を振る舞いごとに出す。`spec に対応なし`または`照合不能`が1件でもあれば一致完了を報告しない。specとテストをIDで機械的に紐付けず、テスト実行成功だけを一致の証拠にしない。
