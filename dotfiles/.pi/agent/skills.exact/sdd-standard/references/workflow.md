# SDD ワークフロー手続き（any-workflow 用）

any-workflow が sdd-standard と組み合わせるときに適用する、SDD 固有の依頼モード・フェーズ・収束ルール・乖離検知。手続きの骨格（完了範囲の決定、規則セットの組み立て、承認と収束の一般規則）は any-workflow が所有し、ここでは上書きしない。

## 適用条件

ロジックを伴う成果物の開発に適用する。設定ファイル群だけの変更は対象外とする。ただし、設定がユーザーに観測可能なロジックを持つ場合は対象に含める。

## 依頼モード

依頼文に明示された完了範囲を次の表で決める。明示がないロジック変更は、spec-only か実装まで行うかを確認してから進める。

| 依頼                     | 実行する範囲                                               | 変更してよいもの                         | 停止条件                                                      |
| ------------------------ | ---------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------- |
| specだけ作成・specを整理 | 要件確認 → spec作成・修正 → specセルフチェック             | specのみ                                 | specを出力し、実装・テスト・レビューを行わず停止              |
| 実装して                 | 要件確認 → spec → go/no-go → 実装・テスト → 適合性レビュー | spec、テスト、本番コード                 | `references/review.md` の形式でギャップレポートを提示して停止 |
| 適合性をレビューして     | any-review + `references/review.md` による照合             | 変更しない                               | ギャップレポートのみを出力して停止                            |
| 指摘を直して収束して     | 承認済みレビュー結果に基づく修正 → 検証 → 再レビュー       | 承認された範囲のspec、テスト、本番コード | 「高」指摘が0件になり、検証が通る                             |

spec-only モードでは、要件が曖昧・欠落している場合に推測で spec を完成させず、追加質問で停止する。spec の変更は要件変更に相当するため、実装中に spec を変更した場合は go/no-go をやり直す。

## 全体フロー

1. **要件合意** — 会話で対象、利用者、観測可能な振る舞い、適用範囲を確定する。
2. **spec 整備** — sdd-standard の spec 作成規約に従い、`SPEC.md` または `spec/<feature-name>.md` を新規作成・修正する。
3. **go/no-go** — オーナーが spec を読み、要件を承認する。spec-only モードはここで停止する。
4. **実装** — 承認済み spec に対応するテストと本番コードを作る。テストは AI の収束作業用で、オーナーは内容を確認しない。
5. **適合性レビュー** — any-review + `references/review.md` で spec・テスト・実装を照合する。レビューでは編集・テスト実行をしない。
6. **収束** — オーナーがレビュー結果を承認した後、承認範囲のギャップを修正し、通常の検証と再レビューを繰り返す。「高」指摘0件で完了する。

## 収束ルール

- 初回レビューは指摘のみとし、テスト・本番コード・specを編集せず、テストも実行しない。
- 初回レビューの出力は `references/review.md` のギャップレポートに限定する。各指摘は場所・問題・影響・修正案を含め、対象を編集せず停止する。
- オーナーが収束実行を承認した場合は、specと現状コードを入力として収束を開始する。
- 収束実行では、承認済みの修正範囲だけを変更し、format・lint・typecheck・testなどプロジェクトの検証を実行してから再レビューする。
- specを変更する修正は要件変更である。変更後はオーナーの再承認なしに実装・再レビューを続けない。
- 適合性レビューの照合軸・指摘種別・出力形式は `references/review.md` に従う。

## 完了報告

各フェーズの完了報告は、実行した確認を観点ごとに列挙する。`n/n` は集計として併記してよいが、単独で完了を表してはならない。

| 報告するフェーズ | 必須の内訳                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| spec 整備        | SKILL.md の「spec 作成・修正時の出力」に従い、適用したセルフチェックごとの判定と根拠                       |
| 適合性レビュー   | `references/review.md` に従い、4軸それぞれの確認観点・判定・根拠                                           |
| 収束             | 承認済み指摘ごとの解消結果、実行した format・lint・typecheck・test の結果、再レビューの4軸ごとの判定と根拠 |

未実行または入力不足で評価できない観点は `skip` と理由を記載し、問題なしとして数えない。

## 乖離検知

commit/PR などで変更を確認するときは、全文照合をせず、差分に現れた観測可能な振る舞いだけを次の手順で照合する。

1. **入力を集める** — 差分、変更前後の公開入口、既存 spec を読む。公開入口または観測可能な振る舞いを特定できなければ、質問して停止する。
2. **対応を決める** — 変更した各振る舞いを spec の節・表行・図の遷移または経路へ対応付ける。ファイルパスや実装モジュール名だけで対応付けない。
3. **結果を報告する** — 振る舞いごとに次の表を出力する。

| 変更した振る舞い     | spec の対応箇所             | 判定 | 根拠                                        |
| -------------------- | --------------------------- | ---- | ------------------------------------------- |
| 無効メールを拒否する | `spec/auth.md` の入力検証行 | 一致 | 差分と状態400・`invalid_email` が対応する。 |

`判定` は `一致`、`spec に対応なし`、`照合不能` のいずれかとする。後者2つがあれば一致確認を完了と報告せず、対象と不足情報を記載する。

spec とテストをIDで機械的に紐付けない。specとテストの対応、テストと実装の忠実性、実装のspec外振る舞いは、適合性レビュー（`references/review.md`）が照合する。テストの実行成功だけを spec との一致の証拠として扱わない。
