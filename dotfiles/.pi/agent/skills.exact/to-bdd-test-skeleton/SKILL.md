# To BDD Test Skeleton

合意した **シナリオ** を BDD テストスケルトンに変換する。テストタイトル = 要件（不変）、テスト実装 = 検証（可変）。タイトルまで作り、実装と本番コードは後続セッションで書く。

## テストタイトル = 唯一の要件

このスキルが作るテストは実装を空（`() => {}` / `pass`）にする。ゆえに後続セッションが実装のために読める情報はテストタイトル以外になく、会話履歴・設計書・このスキルの実行時文脈にもアクセスしない前提で動く。タイトルは後続セッションへ渡す唯一の要件であり、欠落・曖昧を許さず、自己完結した仕様として書く。

## 入力

会話で合意した内容から **シナリオのみ** を抽出する。実装の詳細（関数名/クラス名/モジュール構造、DBスキーマ/内部データ構造、APIエンドポイント/シグネチャ等）は切り捨てる。

抽出対象は「**ユーザーが観察する振る舞い**」= Given（前提）/ When（操作）/ Then（結果）のみ。

シナリオが曖昧・欠落している場合はユーザーへ追加質問する。**タイトルに観測可能な具体値を埋めようとして不足に気づいた場合も、推測せず質問に戻る。**

## 出力

1 Feature（シナリオ群）= 1ファイル。

**配置**: `tests/` 直下に置く。種別分け（`e2e/`/`unit/`/`acceptance/`）のサブディレクトリは作らない。**ドメイン単位のサブディレクトリを作り、その下に Feature 単位で1ファイル** を置く。

**命名・拡張子**: `tests/` 配下の既存ファイル慣習を検出して従う。なければ FWデフォルト（vitest/bun-test: `*.test.ts`、pytest: `test_*.py`）。

## テストタイトルの書き方

ルール:

- **言語**: `tests/` 配下の既存テストの言語に従う。なければチャットで使っている言語（デフォルト日本語）。テスト識別子（`test_*` 等）は英字のまま、シナリオ本文は文字列/docstring に書く。
- **構造**: 自然な文で Given-When-Then を表現する。`Given:`/`When:`/`Then:` のマーカーは使わない。
- **観測可能な具体値を必ず含める**: 抽象語を許さない。以下をタイトルに明記する —
  - **Then**: エラー種別/ステータスコード/返却値の形状/状態変化の観測方法（例: 「拒否される」→「状態409・エラーコード `email_taken` で拒否される」）
  - **Given**: 入力の具体的な値と**何がその条件を満たすか**（例: 「不正メール」→「空文字」「`@` のない文字列」「255文字超」）
  - **When**: 操作経路が判別できる語（UI 操作か、API のメソッド+パス相当か）
- **1テスト = 1振る舞い**: 1つの When-Then ペアにする。**結果を変える Given は別テストに分ける。** 結果が変わらない補助的な前提だけ1テストに畳む。
- **グループ = Feature**: 機能/ドメイン単位でグループ（describe/クラス）を作り、その下にテストを並べる。

## セルフチェック

各タイトルを書き終えたら、次の手順で曖昧さを潰してから検証に進む:

1. **抽象語を具体値に展開する** —「不正」「エラー」「拒否」「成功」「有効」等を見つけたら、観測可能な値（ステータス/コード/形状/境界値）へ置き換える。
2. **別解釈を意図的に2つ挙げる** — そのタイトルだけで実装したとき、別の結果になりうる解釈を2つ探す。挙がったら具体値か追加質問で潰す。
3. **実装の詳細を掃除する** — クラス名/DB/エンドポイント等が Given/Then に紛れていないか確認し、観測可能な振る舞いへ差し替える。

各タイトルが以下のすべてを満たすか。1つでも満たさなければ修正するかユーザーへ質問する:

- [ ] Then に観測可能な具体値（ステータス/コード/形状）が含まれる
- [ ] Given に具体的な入力値と「何がその条件を満たすか」が含まれる
- [ ] When に操作経路（UI/API）が判別できる語がある
- [ ] 誰が読んでも、実装の解釈が1通りに定まる
- [ ] 実装の詳細（クラス名/DB/エンドポイント）が混入していない
- [ ] 結果を変える Given を別テストに分けた

## 完成イメージ

vitest:

```ts
describe("ユーザー登録", () => {
  it("未登録のメールアドレスで登録すると、その後そのメールアドレスでサインインできる", () => {});
  it("既に存在するメールアドレスで登録すると、状態409・エラーコード email_taken で拒否される", () => {});
});
```

pytest（クラス=Feature、メソッドは機能の省略名、docstring=シナリオ、実装は `pass`）:

```python
class TestUserRegistration:
    def test_register(self):
        """未登録のメールアドレスで登録すると、その後そのメールアドレスでサインインできる"""
        pass

    def test_register_duplicate(self):
        """既に存在するメールアドレスで登録すると、状態409・エラーコード email_taken で拒否される"""
        pass
```

## このスキルがやらないこと

- テスト実装（Given/When/Then のコード化、assertion）は書かない。
- 本番コード（src/ 等）は一切触らない。
- テストを実行して通すことはしない（全テストは赤で正常）。
- 要件文書・設計書・シナリオ一覧ドキュメントは作らない。
