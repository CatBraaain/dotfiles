# 完了報告

成果物を伴う作業を報告するときは、結果だけでなく、結果を理解・検証・再開するために必要な作業の要約を報告する。詳細な作業ログや内部の思考過程は報告しない。

この形式は、変更・検証、または依頼された調査・レビュー・計画の結果を報告するためのものである。質問・相談・意見募集への直接の回答には使わない。

## 適用判定ラダー

目標: 返信がこの形式に沿うべきかを、返信までに実行した依頼作業だけで判定する。

最初に成立する段で止まる。

1. 条件: 返信までにファイル変更、検証、依頼された調査・レビュー・計画のいずれかを実行したか？
   行動: 必ずこの形式に沿う。質問や承認待ちの途中であっても同じであり、この形式に沿う返信を質問や承認待ちで終えるときは、必要なセクションの後に asking-format に従って `## 質問` セクションを置く。
2. 条件: 前段の作業を実行していないか？
   行動: この形式を使わず本文で直接回答する。質問・相談・意見募集への回答のように、返信本文自体が成果物である。

検証: 返信の前に、このターンで write・edit・検証コマンド、または依頼された調査・レビュー・計画を実行したかを振り返る。

## 見出し

最初の見出しである報告見出しとして、報告ラベルとタスクの要約を1行で示す。形式は `## <絵文字> <英語1語のラベル> — [タスクの要約]` とする。この形式は報告見出しだけに適用し、後続のセクション見出しや `## 質問` には適用しない。ラベルは、作業の結果または現在の状態を示す。要約は依頼対象を表す名詞形で簡潔に記述し、達成内容の説明は書かない。worktree で作業した返信では、達成内容の要約の前に、見出しの直下へ `worktree: <branch>` を1行で置く。達成したこと、または達成できなかったことの要約は、見出しまたは worktree 行の直下の本文に必ず書く。

## 報告ラベル

依頼の主成果物に対応する成功ラベルを選ぶ。未完了・待機・失敗では、成功ラベルの代わりに状態ラベルを使う。

| ラベル | 使う条件 |
|---|---|
| `📝 Created` | 変更対象がすべて新規ファイル |
| `📝 Edited` | 変更対象に既存ファイルの変更を含む。新規作成との混在も含む |
| `🔎 Researched` | 調査が主成果物 |
| `👀 Reviewed` | レビューが主成果物 |
| `📋 Planned` | 計画が主成果物 |
| `🏁 Closed` | finish により worktree を統合・close まで完了した |
| `🧹 Discarded` | discard により worktree と branch を破棄した |
| `🟡 Partial` | 一部を完了したが、残課題がある |
| `⏳ Ready` | 検証済みの worktree を finish するため、オーナーの承認を待つ |
| `⏳ Waiting` | `Ready` 以外で、オーナーの回答・承認を待つ |
| `⛔ Blocked` | 権限・環境など、回答以外の要因で安全に続行できない |
| `❌ Failed` | 依頼された変更または検証に失敗した |

`Closed` は個別の編集完了ではなく、その worktree での一連の変更を統合・削除まで終えた報告だけに使う。

## 必須セクション

- `検証`: 実際に実行・確認した検証と、その結果を表で示す。

ファイルを変更した場合は、`変更` セクションも必須とする。変更がない場合は省略してよい。

## 任意セクション

重要な情報がある場合だけ、内容に合うセクションを追加する。`進め方`、`実施したこと`、`受入条件`、`残課題`、`要判断`、`再開地点`、`オーナーの操作` などの見出しは例であり、タスクに応じて統合・分割・改名してよい。空のセクションや定型文のためだけのセクションは作らない。

次の場合は、作業の要約を必ず含める。

- 重要な実装方針や設計判断を選んだ場合
- 依頼の解釈に判断が入った場合
- 検証に失敗し、原因の切り分けを行った場合
- `Partial`・`Ready`・`Waiting`・`Blocked` となり、別の担当者が再開する可能性がある場合

要約には、調査対象、採用した方針、意図的に変更しなかったもの、失敗の切り分け、再開地点など、第三者が判断や作業を引き継ぐために必要な観測可能な事実だけを記載する。`ls` や `grep` などの逐次ログ、結論に影響しない探索、内部の思考過程は記載しない。

## 基本形

```markdown
## 📝 Edited — [タスクの要約]

[依頼に対して達成したこと、または達成できなかったことの要約]

## 変更

| ファイル | 変更内容 |
|---|---|
| `path/to/file` | [変更内容の要約] |

## 検証

| 種別 | 実行内容 | 結果 |
|---|---|---|
| format | `...` | ✅ passed |
| lint | `...` | ✅ passed |
| test | `...` | ✅ passed |
```

- 見出しには報告ラベルに対応する絵文字を含め、` — ` に続けてタスクの要約を置く。例: `## 📝 Edited — [タスクの要約]`、`## 🟡 Partial — [タスクの要約]`。
- `変更` には変更したファイルと変更内容をテーブルで記載する。変更理由や詳細な背景は `変更` に書かず、任意セクションで補う。
- `検証` には実際に実行または確認したものだけを記載する。結果は `✅ passed`、`❌ failed`、`⚪ skipped: 理由` のいずれかで示す。
- `変更`・`検証` 以外のセクション名は、重要な情報が明確に伝わる範囲で柔軟に統合・分割・改名してよい。
- 実行できなかった検証が受入条件に影響する場合は、`検証` に理由を記載し、成功ラベルを使ってはならない。
- `Partial`・`Ready`・`Waiting`・`Blocked`・`Failed` の場合は、残課題、阻害要因、要判断、再開地点、オーナーの操作など、必要な情報を任意セクションで補う。
- 実行していない操作を、正常な検証結果のように報告してはならない。
