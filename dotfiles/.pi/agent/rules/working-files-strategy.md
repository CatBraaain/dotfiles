# ファイルベース作業戦略

作業の入力と成果物はチャット出力で完結させず、ワークファイルとして残してパスで受け渡す。セッションやサブエージェントをまたいで参照でき、同じ内容を再出力するトークンを節約できる。単発の質問・相談、ファイル変更1件で終わる作業では作成しない。

## 置き場

ワークファイルは常に `~/.pi/agent/work/{project}/` に作る。

- `{project}` は作業中リポジトリのルートディレクトリ名。リポジトリ外ではカレントディレクトリ名とする。
- 複数リポジトリにまたがる作業は、作業を主導するリポジトリの `{project}` に置く。
- work は使い捨てにせず、後から見返せる前提で置く。

## 表へのファイル作成

通常はワークファイルだけをworkに作る。オーナーが「specファイルを作って」「計画ファイルを作って」のように、ファイル作成を明示したときだけは、workには作らずリポジトリルートに `{name}.{type}.md` の実ファイルを作る。シンボリックリンクは作らない。

「spec作って」「計画作って」のようにファイル作成を明示しない依頼では、workにだけ作る。

## 命名

ファイル名は `{yyyymmdd-hhmmss}-{name}.{type}.md` とする。`name` は対象を表す kebab-case、`type` は次の6種に固定する。

| type | 作成するタスク | 中身 |
| --- | --- | --- |
| `interview` | オーナーへの質問・ヒアリングをするとき | 質問、回答、決定事項 |
| `plan` | 複数ステップの計画を立てるとき | 作業分解、順序、完了条件 |
| `research` | 対象同定・事実収集・比較の調査をするとき | 事実、出典、結論 |
| `review` | 成果物をレビューするとき | 指摘（場所・種別・重要度・修正案）。レビュー対象は編集しない |
| `report` | タスクの実行結果を残すとき | 結果、検証、残課題 |
| `spec` | オーナーの go/no-go 用に新規specを整備するとき | 観測可能な振る舞いと適用範囲 |

## review のカバレッジ記録

git リポジトリ内で `review` ワークファイルを作るときは、実際にレビューしたファイルの frontmatter スナップショットを記録する。ファイル内容ごとの ID（git blob hash）により、セッションをまたいで「この内容はレビュー済みか」を判定するための正本とする。対象ファイルの選び方はこの規則の対象外。リポジトリ外では省略する。

```yaml
---
snapshot:
  files:
    src/a.ts: 07d44e579bbd9318d1fd6c91d387248d8ab8b120
    lib/util.ts: 2ce75e2a24f7d6841a504cf3616ef5a59edb3a2d
---
```

blob hash はレビュー時に読んだ内容（作業ツリーの実ファイル）から `git hash-object <file>` で取得する。ID は内容のみで決まり、パス変更や rebase でコミットハッシュが変わっても同一内容なら同一 ID になる。

## 受け渡し

- サブエージェントへの委譲では、出力先ファイルパスを委譲文に指定する。本文を委譲文に貼らない。
- 前段のワークファイルを入力にするときも、パスを渡して読ませる。
- チャットへの報告は要約とファイルパスだけにする。本文をチャットに複製しない。
