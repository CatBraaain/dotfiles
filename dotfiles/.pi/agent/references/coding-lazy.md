# コーディング規範（lazy）

動く最小コードを優先する。上書きより削除、賢いより退屈、自作より標準。コーディング全般（実装・修正・リファクタ・レビュー・設計、依存選定）に適用する。

## ラダー

実装前に必ず問題を把握してから（対象ファイルと実際の流れを追う）、下位の段で解決できるならそこで止める。

1. **本当に必要か？** — 投機的需要なら書かず、1行で理由を述べる（YAGNI）
2. **既にこのコードにあるか？** — 近くの helper/util/type/パターンを再利用する。探さずに再実装するのが一番よくある無駄
3. **標準ライブラリでできるか？**
4. **ネイティブ機能で足りるか？** — `<input type="date">`、CSS over JS、DB制約 over アプリコード
5. **既存の依存で解決するか？** — 新しい依存を増やさない
6. **1行で書けるか？**
7. **それでも無理なら** 動く最小コード

バグ修正は根本原因を直す。触ろうとする関数の呼び出し元をすべて grep してから。共有関数にガードを1つ置く方が、各呼び出し元にガードを置くより diff も小さい。

## ルール

- 要求されていない抽象を作らない（1実装のインターフェース、1製品のファクトリ、不変値のための設定）
- 後のためのスキャフォールドをしない。後は後で作れる
- 追加より削除。退屈さは正義
- ファイル数と diff は最小 — ただし問題を理解した上で。間違った場所の最小変更は lazy ではなく2つ目のバグ
- 複雑な要求なら lazy 版を出しつつ同じレスポンスで確認する（「X やった。Y で足りる？ フル X が要る？」）。決め打ちできる答えなら止まらない
- 既知の上限がある簡略化（グローバルロック、O(n²)、素朴なヒューリスティック）には `ponytail:` コメントで上限とアップグレード path を併記する（`# ponytail: グローバルロック、スループット問題が出たら per-account ロックへ`）

## 出力

コードを先に出す。続く説明は最大3行（何を省いたか、いつ足すか）。説明がコードより長くなるなら説明を削る。ユーザーが明示的に求めた説明（レポート、ウォークスルー、フェーズ毎のメモ等）は省略せず全て出す。

パターン: `[code] → skipped: [X], add when [Y]`

## 怠ってはいけないこと

信頼境界での入力バリデーション、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティの基本、明示的に要求されたものは簡略化しない。ユーザーが完全版を望めば作る、再議しない。

問題を理解することを怠らない。ラダーは解を短くするもので、読むことを短くするものではない。触れるファイルと実際の流れを、段を選ぶ前に追う。実世界は紙上の理想とは違う（実クロックはドリフトする等）ので、キャリブレーションの余地を残す。
