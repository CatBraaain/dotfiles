# コミット作成

ローカルの変更を確認し、意味の異なる変更ごとに分割して、適切なコミットメッセージでコミットしてください。

## 今回の依頼（最優先）

以下は、今回の `/commit` 呼び出しで渡された生の依頼内容です。

```text
/commit $@
```

この依頼に明示された対象・方針・例外は、後述の標準手順およびデフォルトルールより優先して適用してください。依頼に指定されていない事項には、標準手順とデフォルトルールを適用してください。

## 安全制約（常に適用）

- ユーザーが明示していない既存の変更を編集・削除・破棄しない。
- 機密情報、生成物、意図しない変更をコミットしない。
- 判断できない変更や危険な変更がある場合は、コミットせず、作業を停止して確認を求める。
- 明示なく作業対象のブランチを変更しない。

## 標準手順

1. `git status` と `git diff HEAD` で、ステージ済み・未ステージ・未追跡を含むすべての変更を確認する。
2. `git branch --show-current` で現在のブランチ名を確認する。以降の作業とコミットは、そのブランチ上で行い、ブランチを移動しない。
3. 変更がある場合のみ、現在の `HEAD` を `backup/<現在のブランチ名>-<yyyyddmmhhmmss>` という名前のバックアップブランチへ保存する。`git branch <バックアップブランチ名> HEAD` で作成し、バックアップのためにブランチを移動してはならない。
4. 変更を目的や意味の単位でグループ化する。機能追加、バグ修正、リファクタリング、設定変更、ドキュメント変更など、独立してレビュー・revert できる単位に分ける。
5. 各グループについて、変更内容と既存のコミット履歴を確認し、Conventional Commits に準拠したコミットメッセージを決める。
6. グループごとに必要なファイルだけをステージし、`git diff --cached` で内容を確認してからコミットする。
7. すべてのグループをコミットした後、`git status` と `git log -n <作成したコミット数>` で結果を確認する。

## デフォルトルール

- コミットメッセージは Conventional Commits に準拠する。
- `type` は変更の意味に合わせて `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `test`, `build`, `ci`, `perf` などから選ぶ。
- コミットメッセージの言語は、`git log` で確認した過去のコミット履歴に合わせる。履歴で特定の言語が優勢ならその言語を使う。
- 1つのコミットに複数の目的を混在させない。ただし、分割すると変更が成立しない密接な変更は同じコミットにまとめる。
- 変更のないファイルや、ユーザーが明示していない既存の変更を勝手に編集・削除・破棄しない。
- `git add .` や `git add -A` で無関係な変更をまとめてステージしない。対象ファイルを明示してステージする。
- 既存のコミットを amend、rebase、reset、squash しない。新しいコミットだけを作成する。
- コミット前に、機密情報、生成物、意図しない変更が含まれていないか確認する。
- 変更がない場合はバックアップブランチも作成せず、コミットせず、その旨を報告する。
- コミット作成前に確認を求めず、上記の安全条件を満たす範囲で実行する。判断できない変更や危険な変更がある場合は、コミットせず、作業を停止して確認を求める。
- バックアップブランチは現在の `HEAD` を保存するために作成するだけで、ブランチの移動や別ブランチでの作業は行わない。

## 完了報告

作成したコミットごとに、コミットハッシュ、コミットメッセージ、含めた変更の概要を簡潔に報告する。未コミットの変更が残っている場合は、その理由も報告する。
