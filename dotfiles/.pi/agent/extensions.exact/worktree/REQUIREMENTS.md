# Session worktreeメタデータの要件

本書は、pi の session が作業に使う Git worktree を管理し、その関連データを供給する拡張の課題・目的・重要制約を定める。読者は本拡張の保守者と、連携するエージェント管理ツールの開発者である。

## 課題と目的

同じリポジトリを複数の session で扱うとき、worktree を作成・検出した事実だけでは、各 session がどこを作業に使うか分からない。session は作業先を明示してから書き込み、外部ツールは同じ宣言をレビュー対象の選択に使えるようにする。サブworktree の作成と片付けは専用ツールに集約し、作業内容や別の作業先を誤って失わないようにする。

## 期待する成果

- エージェントは session 開始時のリポジトリ、または指定したプロジェクトのサブworktree を名前で利用宣言できる。既存の作業先を再利用するか、新しいブランチと作業先を作成する。1つの session でリポジトリをまたぐ複数の作業先を宣言できる。
- エージェントは管理対象のサブworktree と対応するローカルブランチを一緒に片付けられる。通常の片付けでは未統合のコミットや作業先に残る変更を保護し、成果を捨てる場合は明示的に区別する。
- 管理対象のサブworktree を親フォルダ単位で書き込み許可せず、利用宣言で追加する許可は呼び出し元の session が宣言した作業先だけに限る。利用宣言では確認ダイアログを出さず、開始 `cwd` 配下の既存許可は維持する。
- 外部ツールは session JSONL から、明示的に宣言された worktree の名前と絶対パスを取得できる。Bash 操作の自動追従は宣言と区別し、書き込み許可を発生させない。

## 重要な制約

- データ供給側の pi拡張として、pi本体を変更せずに実現する。
- 更新する関連は操作を実行した session のものに限り、現在の関連として扱うのは現存する worktree だけとする。
- pi のメモリ上と session ファイル上で関連データを整合させる。保存には標準の customエントリ追記API を使い、既存の session header と履歴本文を保持する。
- 指定先とリポジトリの対応を確認できる作業先だけを扱う。管理操作と宣言は Guardrails の明示的な拒否と機密ファイルの保護を上書きしない。main worktree と session の開始位置は削除から保護する。
- エージェントによる finish・discard の承認運用は維持し、専用ツールでは追加の確認ダイアログを出さない。
- 宣言を保存できなかった場合は書き込みを許可しない。既存の作業内容を上書きせず、操作が途中で失敗した場合は残った状態を伝える。
