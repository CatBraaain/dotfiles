# tmux-handoff の要件

この文書は、通常の対話CLI起動を専用tmux へ引き渡すグローバルpi拡張 `tmux-handoff` の課題・目的・期待する成果・重要な制約を定める。読者は、実装前や変更時に判断する開発者・保守担当者と agent である。

具体的な入出力・状態・失敗時の振る舞いは `SPEC.md` で定める。

## 課題と目的

起動元端末を閉じた後も作業を継続するには、保存会話を別プロセスで再開するだけでは足りない。進行中のエージェントループと、その実行端末を保持する必要がある。

通常の対話用 `pi` の起動時に専用tmux へ引き渡し、利用者が起動方法を変えずに、端末の寿命から実行中の処理を切り離せるようにする。

## 期待する成果

- 専用tmux配下で開始した同じpiプロセスが、起動元端末の終了や接続クライアントの切断後も、進行中のエージェントループを継続する。再接続では同じ実行PTY へ戻り、保存会話の再実行とは区別できる。
- cwd・起動条件・必要な環境・選択済み会話・初期入力を引き継ぎ、起動元と同じ実行条件で作業を始められる。初期入力には、ファイル・画像の指定と編集中の入力を含む。
- 会話ID と実際の tmux接続先の対応を、VS Code拡張など外部の読み手が参照できる。

## 重要な制約

### 起動と引き継ぎ

- PATH上の `pi` コマンドの入口・shell wrapper・pi本体を変更せず、グローバル拡張として成立させる。
- 引き渡す対象は、専用tmux の管理外で開始された対話起動とする。稼働中のエージェントループの途中移管は扱わない。
- 起動元の pi はエージェントループへ進めない。引き渡しに失敗した場合も、起動元の pi で初期依頼を続行する代替動作は行わない。
- 会話の再開選択・fork・初期依頼の実行を、引き渡しによって二重に行わない。
- 専用管理下の起動は、利用者の任意の tmux内での起動と区別する。専用管理下の pi を再度引き渡す二重ラップや再帰を防ぐ。

### 専用管理先と互換性

- 専用tmuxサーバーは必要時に自動起動する。利用者が通常使うtmux のソケット・設定・稼働状態は変更しない。
- print・RPC・JSON等の非対話用途は従来どおり維持する。拡張を無効化した起動の自動tmux化は保証対象外とする。
- `create_detached_session` の承認付き・独立したmain起動・自動表示しない性質を維持し、通常起動と同じ専用管理先を使う。
- 外部連携の範囲は会話ID と接続先の情報提供までとし、VS Code拡張のコード変更は含めない。
