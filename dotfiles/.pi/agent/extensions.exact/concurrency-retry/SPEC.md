# concurrency-retry

プロバイダの同時実行制限エラーに対して、待機してから再試行を繰り返す拡張。

## 対象

検出は fail-closed である。最終 assistant エラーの `errorMessage` に、同時実行を明示する証拠がある場合だけ対象とする。判定は `dsh` の `dotfiles/.dsh/plugins.exact/concurrency-retry` と同じ方針で、プロバイダごとの専用証拠とプロバイダ非依存の共通証拠を使う。

| プロバイダ / detector | concurrency と確定する証拠 |
| --- | --- |
| `zai`、`zai-coding-cn` | code `1302`（"Rate limit reached for requests"）、code `1305`（"The service may be temporarily overloaded"）。生 JSON ボディの code フィールドでも文言のみでもよい |
| その他のプロバイダ | `concurrent request(s)`、`concurrency limit`、`too many concurrent`、`connection limit reached` |

除外規則:

- quota・billing・usage-window の証拠は positive 判定より先に除外する。code `1113`・`1308`〜`1321`、`quota`、`billing`、`balance`、`credit`、`insufficient_quota`、usage limit/window、monthly/weekly/daily limit、`reset` が errorMessage に含まれる場合は対象外とする
- 専用 detector を持つプロバイダ（`zai`、`zai-coding-cn`）は専用証拠だけを扱い、共通文言に一致しても対象外とする
- HTTP 429、`rate limit` 系文言、quota 系はそれ単独では concurrency 証拠にならず、専用・共通の証拠がなければ対象外として推測しない
- errorMessage に証拠が現れない同時実行エラー（provider adapter が内部吸収するもの）は対象外である

`agents` 拡張との関係: `zai` / `zai-coding-cn` の同時実行系エラーは `agents` 拡張の model-fallback 対象外である（判定は `shared/zai-concurrency.ts` の共有判定）。その他のプロバイダの concurrency 証拠文言は rate-limit 系の文言を含まないため `agents` 拡張の fallback 判定には一致せず、待機リトライだけが動く。ただし HTTP 429 を伴った場合は `agents` 拡張が従来どおり即時 fallback を行う（本拡張は react しない）。

## ターン内リトライ

同時実行エラーの assistant エラーを受けたら、待機してから pi 本体の自動リトライに再試行させる（エラー文言を再試行可能な形式へ置き換える）。

| 入力                                                                 | 操作             | 結果                                                                        |
| -------------------------------------------------------------------- | ---------------- | --------------------------------------------------------------------------- |
| 同時実行エラーを受けた                                               | 待機時間だけ待つ | エラー文言を再試行可能な形式へ置き換え、pi 本体が同じリクエストを再試行する |
| 待機中にユーザーが abort した                                        | 待機を中断する   | エラー文言を置き換えない。ターンは元のエラーで終了する                      |
| 同時実行エラー以外の結果でメッセージが確定した（成功・abort を含む） | —                | 連続エラー回数を 0 に戻す                                                   |

pi 本体のリトライ回数上限（`settings.json` の `retry.maxRetries`）に達するとターンはエラー終了する。続きは「ターン確定後の再実行」が担う。

## 待機時間

連続エラー回数 `n` に対し `5s × 2^(n-1)`（上限 60s）に ±20% のジッタを加えた値を待つ。連続エラー回数はターンをまたいで引き継ぎ、成功で 0 に戻る。ターン確定後の再実行の待機も同じ回数に数える。

直前の HTTP 429 が `Retry-After` ヘッダーを伴った場合、ターン内リトライの待機はヘッダーの値（秒数または HTTP-date、過去の日時は 0）をプロバイダを問わず優先する。ヘッダーは次の 1 回の待機で消費する。ターン確定後の再実行の待機には使わない。

## ターン確定後の再実行

ターンが（pi 本体のリトライを含めて）完全に終了したとき、最後のエラーが同時実行エラーなら、待機してから同じターンを再実行する。再実行は上限なく繰り返す。

| 状態                                                    | 操作             | 結果                                                                                              |
| ------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------- |
| ターンが同時実行エラーで確定した                        | 待機時間だけ待つ | `<provider> concurrency limit; retrying in <秒>s (attempt <回数>)` を通知する                     |
| 待機完了時点で idle である                              | —                | 非表示のカスタムメッセージでターンを再実行する（ユーザーメッセージの履歴は増えない）              |
| 待機完了時点で idle でない（ユーザーが入力した）        | —                | 再実行しない                                                                                      |
| ターンが同時実行エラー以外（abort、他エラー）で確定した | —                | 再実行しない                                                                                      |
| 保留メッセージがある                                    | —                | 再実行しない                                                                                      |

## 表示

| 状況                       | 表示                                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| ターン内リトライの待機中   | ステータス領域に `<provider> concurrency limit; retrying in <秒>s (attempt <回数>)` を表示し、待機後に消す       |
| ターン確定後の再実行の待機 | 通知（info）で上記と同文言を出す                                                                                |

`<provider>` はエラーのプロバイダ ID（例: `zai`、`openai-codex`）。カスタムメッセージ・ステータスの識別子は `concurrency-retry` である。
