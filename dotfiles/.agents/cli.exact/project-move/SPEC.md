# project-move の仕様

本書は、プロジェクトの改名・移動に伴い pi の保存済みセッションとプロジェクト別の調査資料・tickets を移行する `project-move` の入出力とファイル状態を定める。利用者が実行内容を判断し、実装・検証の担当者が成否を判断するために読む。上流正本は同じディレクトリの [REQUIREMENTS.md](./REQUIREMENTS.md) とする。

## コマンドと実行前提

```text
project-move <old-cwd> <new-cwd>
project-move --execute --pi-stopped <old-cwd> <new-cwd>
project-move --help
```

| 入力 | 振る舞い |
| --- | --- |
| `old-cwd`、`new-cwd` | それぞれ旧・新プロジェクトの作業ディレクトリ。必須の位置引数2個 |
| オプションなし | preview。対象・変更予定・停止条件を調べ、表示する |
| `--execute --pi-stopped` | preview と同じ事前検証を行い、移行する。`--pi-stopped` は利用者が停止前提を確認したことを表す |
| `--execute` のみ、または `--pi-stopped` のみ | 引数エラー |
| `--help` のみ | 使用方法、preview が既定であること、停止前提、対応する保存範囲を表示して正常終了する。ファイルを調べない |
| 不明なオプション、重複オプション、引数の過不足 | 使用方法と理由を表示して引数エラー |

`--` 以降は位置引数として扱う。標準入力による確認は行わない。

利用者は、旧・新プロジェクトの対象セッションを利用する pi と、対象セッション・調査資料・tickets およびそれらの保存経路を更新する処理を停止し、コマンド終了まで停止状態を維持する。CLI はプロセスの停止・稼働判定を行わない。preview はファイルやディレクトリを作成・変更・削除しない。

本書の変更範囲と保持条件は、この停止前提が維持される場合の保証とする。停止前提が破られた場合は、後述する各検査時点で検出した不整合について後続の変更を停止する。検査とファイル操作の間に生じる非協調な差替えについて、検出および対象外への変更防止は保証しない。

## パスと保存範囲

### 作業ディレクトリ

`old-cwd` と `new-cwd` は、実行時の作業ディレクトリを基準に絶対パス化し、実行OS の規則で `.`、`..`、余分な区切りを正規化する。symlink の実体パスへの置換や大文字小文字の統一は行わない。空文字列は引数エラーとする。`~` の展開はシェル側で行う。

旧cwd は存在しなくてもよい。新cwd は存在するディレクトリであることを確認する。正規化後の旧・新cwd が同じ場合は停止する。ヘッダー内の `cwd` の照合にも同じ字句上の正規化を使い、ヘッダーの `cwd` 自体は絶対パスを必須とする。

### セッションの場所

agent dir は、環境変数 `PI_CODING_AGENT_DIR` が設定されていればその値、未設定なら `~/.pi/agent` とする。空の設定値は入力不整合として停止する。agent dir の先頭の `~` 単独または `~/` はホームディレクトリへ展開し、Windows では `~\` も同じように扱う。相対指定は実行時の作業ディレクトリを基準に絶対パス化する。sessions root は `<agent-dir>/sessions` とする。

旧・新cwd に対応する保存先フォルダ名は、正規化した絶対cwd の先頭の `/` または `\` を1個除き、残る `/`・`\`・`:` をすべて `-` に置換し、前後を `--` で囲んだものとする。フォルダ名から cwd を逆算しない。

| 区分 | 原本 | 移行先 |
| --- | --- | --- |
| 通常 | `<sessions-root>/<旧フォルダ名>/*.jsonl` | `<sessions-root>/<新フォルダ名>/<同じファイル名>` |
| archive | `<sessions-root>/<旧フォルダ名>/archive/*.jsonl` | `<sessions-root>/<新フォルダ名>/archive/<同じファイル名>` |

この2箇所の直下にある、名前が `.jsonl` で終わる通常ファイルを候補とする。他のサブディレクトリは走査しない。`subagents/` 配下や、pi の `--session-dir` で指定した任意の保存先は移行範囲に含まれない。CLI は custom session dir の指定を受け付けず、`PI_CODING_AGENT_SESSION_DIR` と pi設定の `sessionDir` も参照しない。

sessions root、旧保存先、archive が存在しない場合、その場所のセッション候補は0件とする。既存の場所を読み取れない場合や、存在する場所の種類が期待と異なる場合は停止する。セッション候補0件でも cwd とセッション保存先経路の妥当性は検証するが、新保存先の既存セッションは読み取らない。調査資料・tickets の判定・処理は続ける。

### 調査資料と tickets の場所

research root は `~/.agents/research`、tickets root は `~/.agents/tickets` とし、ホームディレクトリを使って絶対パス化する。旧・新プロジェクト名は、それぞれ正規化した絶対cwd のbasenameとする。旧cwd の存在にかかわらず、この規則で調査資料は `<research-root>/<旧名>` を原本、`<research-root>/<新名>` を移行先に、tickets は `<tickets-root>/<旧名>` を原本、`<tickets-root>/<新名>` を移行先に対応させる。名前はリテラルのパス成分として扱う。

通常のプロジェクトルートの改名・移動を対象とする。Git情報によるmain worktree名やサブディレクトリの所属プロジェクトの推定は行わない。ルートディレクトリなど、旧・新cwd のいずれかから有効な末尾フォルダ名を得られない場合は、書き込み前に停止する。

以下は上から順に判定する。判定は調査資料と tickets それぞれに対して独立に適用する。保存先の比較には正規化した絶対パスを使い、Windows では比較に限り大文字小文字を区別しない。存在判定では symlink 自身も既存エントリとして扱い、存在の有無を判定できない場合は停止する。

| 条件 | 調査資料・tickets の扱い |
| --- | --- |
| 旧・新保存先が同じ | 移動不要。その場所を走査・検証・バックアップ・変更しない |
| 旧保存先が存在しない | 原本なし。その移行先を調べたり作成したりしない |
| 旧保存先が存在し、旧・新保存先が異なる | フォルダ全体を移行対象とし、空フォルダも対象に含める |

調査資料・tickets が移動不要または原本なしの場合も、セッション移行は続ける。セッション候補0件かつ調査資料・tickets の移行対象もない場合は、それぞれの判定結果を表示し、実行モードでもバックアップや移行先を作らず正常終了する。

## 対象と互換性の事前検証

preview と実行は、セッションと移行対象の調査資料・tickets の事前検証をすべて満たす場合にだけ有効な移行計画を表示する。いずれかを満たさなければ、原因と該当パスを表示して停止する。実行モードでも、この事前検証が終わるまで書き込まない。

以下の表はセッションに適用する。

| 検証対象 | 受け付ける状態 |
| --- | --- |
| 旧・新保存先の対応 | 異なる保存先パスに対応する。異なるcwd が同じフォルダ名になる符号化衝突は停止する |
| 候補の先頭行 | UTF-8 のJSONオブジェクトであり、BOM と重複キーを含まない |
| 候補のヘッダー | `type` が `session`、`id` と `timestamp` が空でない文字列、`cwd` が絶対パスの文字列である |
| 候補のヘッダーの `version` | 未指定、または整数の `1`・`2`・`3`。未指定は旧形式として受け付ける。値も未指定の状態もそのまま保持する |
| 候補のヘッダーの `parentSession` | 未指定、または空でない絶対パスの文字列 |
| 候補の `cwd` | 正規化後に旧cwd と一致する。フォルダ名だけが一致し、ヘッダーが別cwd を表す場合は停止する |
| ID | 全候補のID が通常・archive を通して一意であり、新保存先の通常・archive 直下の既存セッションID とも重複しない |
| 既存の新保存先 | 候補が1件以上ある場合、通常・archive 直下の既存 `.jsonl` の先頭行をUTF-8 のJSONオブジェクトとして読める。`type` が `session`、`id` が空でない文字列、`cwd` が絶対パスの文字列であり、これら3キーに重複がない。`cwd` は正規化後に新cwd と一致する |
| 移行先ファイル | すべて未存在である。同じ内容のファイルも既存ファイルとして停止する |
| ファイルの種類と経路 | 候補および既存の新保存先の `.jsonl` は通常ファイルである。sessions root、旧・新保存先、使用する archive、バックアップ先とそれらの経路構成要素に symlink がない |

移行候補のヘッダー以降のデータは形式変換せず保持する。`version` の移行や本文のJSON解釈は行わない。移行候補の対応外の `version` は、同じヘッダー構造と保持条件で扱えることが確認され、対応範囲が更新されるまで停止対象とする。

既存の新保存先ファイルの `timestamp`、`version`、`parentSession`、その他のヘッダーフィールドと後続データは、検証・変更の対象にしない。

以下の表は、移行対象となる調査資料・tickets に適用する。

| 検証対象 | 受け付ける状態 |
| --- | --- |
| 原本フォルダと配下の全エントリ | 原本はディレクトリであり、配下は読取り可能な通常ファイルまたはディレクトリである。隠しファイル・空ディレクトリも対象とし、symlink やその他の種類があれば停止する |
| 移行先 | フォルダ自体が未存在である。空フォルダ、通常ファイル、symlink を含め、既存エントリがあれば停止し、上書き・統合しない |
| 経路 | 原本・移行先・バックアップの経路構成要素に symlink がなく、既存の親はディレクトリである |
| 処理範囲 | 調査資料・tickets の原本・移行先・バックアップと、セッションの原本・移行先・バックアップの経路が同一または包含関係になって処理範囲が重ならない。調査資料・tickets の原本・移行先・バックアップ同士も互いに重ならない |

## 変更と保持

### セッション

移行前の原本パスと移行先パスの対応は、全セッション候補について確定する。

| データ | 移行後の状態 |
| --- | --- |
| ファイル名と区分 | 元と同じファイル名を使い、通常・archive の区分を保つ |
| ヘッダーの `cwd` | 正規化した新cwd に置き換える |
| ヘッダーの `parentSession` | 字句上の正規化後の絶対パスが、いずれかの原本パスと一致する場合だけ、その原本に対応する移行先の絶対パスに置き換える。通常・archive をまたぐ参照にも同じ規則を使う |
| それ以外の `parentSession` | 元の値、または未指定の状態を保つ |
| その他のヘッダーフィールド | `id`、`timestamp`、`version`、未知のフィールドを含め、元のJSON値とフィールドの有無を保つ。ヘッダー内の空白やキーの並びは保持条件に含めない |
| ヘッダー行の後続データ | 元とバイト単位で一致する。行区切り、末尾改行の有無も保つ |
| ファイルの更新日時 | 元の `mtime` を保つ。保存先ファイルシステムで同じ値を保持できない場合は停止する |

ヘッダー行は先頭から最初の改行直前までとし、CRLF の場合はそのCRも行区切りに含める。行区切りとそれ以降のバイト列をそのまま保つ。改行のないヘッダーだけのファイルは、改行を追加せずに移行する。

セッションの変更範囲はこの表の保存場所と2つのヘッダーフィールドに限る。後続データ中の旧パス、custom entry、worktree metadata、対象外セッションからの逆参照は元のままとする。対象外からの参照修復は保証しない。

### 調査資料と tickets

移行先とバックアップは、原本フォルダ内の全エントリの種類、階層構造、相対名を保持する。空ディレクトリと隠しファイルも保持し、各通常ファイルの全内容をバイト単位で一致させる。変更するのは保存場所だけで、本文中の旧パスを置換しない。調査資料・tickets のファイル・ディレクトリの更新日時は保持条件に含めない。

プロジェクト本体、Git worktree、pi-mux の復元設定には書き込まない。

## バックアップと実行時の状態

バックアップは `<agent-dir>/project-move-backups/<run-id>/` に置く。`run-id` は実行ごとに新規のディレクトリ名で、既存パスを再利用しない。セッションのバックアップは、このディレクトリの下に sessions root からの相対パスを保って配置する。調査資料は、このディレクトリの下の `research/<旧名>/` に、tickets は `tickets/<旧名>/` にフォルダ全体を保存する。sessions root 配下や調査資料・tickets の原本・移行先配下にバックアップを置かない。

セッションのバックアップは、原本の全バイトと `mtime` を一致させる。調査資料・tickets のバックアップには「変更と保持」の調査資料・tickets の条件を適用する。POSIX環境では実行単位のバックアップディレクトリを所有ユーザーだけがアクセスできる状態にする。バックアップと移行先のセッションファイル、および調査資料・tickets のファイル・ディレクトリの権限は原本より広げない。

移行単位は、セッション1ファイルを1件、調査資料・tickets の原本フォルダ全体を1件とする。移動不要・原本なしは移行単位に含めない。各段階ではセッションを sessions root からの相対パスの昇順で処理した後、調査資料、tickets の順に処理する。

| 段階 | 成功したときの状態 | 失敗したときの状態 |
| --- | --- | --- |
| 1. 事前検証 | 全移行単位の対象と対応パス、変更内容、保持すべき原本の状態が確定する | 書き込みなしで終了する |
| 2. 全原本のバックアップ | 全移行単位のバックアップが存在し、それぞれの保持条件が確認できる | 原本をすべて残し、作成したバックアップの状態を表示して終了する |
| 3. 全移行先の作成と確認 | 全移行単位の移行先について「変更と保持」の条件が確認できる | 原本をすべて残し、作成した移行先とバックアップの状態を表示して終了する |
| 4. 原本の削除 | 確認済みの全移行単位の原本が削除され、全件の移行が完了する | 削除済みを完了として残し、残る原本と作成物の状態を表示して終了する |

各セッション原本のバックアップ前、対応する移行先の作成前、原本の削除直前に、その原本の同一性、全バイト、`mtime` が事前検証時から変わっていないことを確認する。各段階の開始時とセッション原本削除直前にはセッション候補集合の追加・削除も確認し、この実行自身による削除済み原本は比較から除く。

調査資料・tickets は、バックアップ前、移行先作成前、原本削除開始前に、原本フォルダと配下の同一性・種類・相対パス集合・各ファイルの全バイトが事前検証時から変わっていないことを確認する。原本の削除中も、各エントリの削除直前にその原本の同一性・種類・内容と、残る原本の相対パス集合を確認する。この実行自身による削除済みエントリは比較から除く。

いずれの原本も、各検査時点で差替え、消失、内容変更、対象集合の追加・削除を検出した場合は後続の変更を停止する。原本削除直前の検査では、そのバックアップと移行先が確認済みの保持条件を保ち、種類も変わっていないことを確認する。

調査資料・tickets は原本フォルダ自体の削除まで済んだ時点で完了とする。原本削除中に失敗した場合は未完了とし、削除済みエントリがあれば一部削除済みと表示する。確認済みの移行先・バックアップ全体と、残る原本を残す。

移行先やバックアップのパスが他の処理によって使用されたことを検出した場合は、上書きせず停止する。各検査時点で経路やファイルの symlink への差替えを検出した場合も、後続の変更を停止する。

バックアップは成功・失敗のどちらでも残す。失敗時は既に作成したファイルと削除済み原本を自動で巻き戻さない。停止前提下では、CLI は対象外のファイル・ディレクトリを削除せず、成功後も空になったセッションの旧保存先や archive は残す。

## 表示と終了コード

パスは絶対パスで表示する。空白や改行などを含むパスも、パスの境界を識別できる表記にする。以下は表示すべき情報であり、装飾や文言の完全一致は要求しない。

| 場面 | stdout に表示する情報 |
| --- | --- |
| 有効なpreview・実行計画 | モード、正規化後の旧・新cwd、sessions root、旧・新セッション保存先、通常・archive の各件数、各ID と原本→移行先の対応、`cwd` と `parentSession` の変更値、停止前提 |
| 調査資料・tickets の計画 | 旧・新プロジェクト名、それぞれの root、原本→移行先の対応、移行対象・移動不要・原本なしの判定。移行対象なら配下のファイル数とディレクトリ数。未走査ならその旨 |
| preview | 書き込んでいないこと、実行時のバックアップの配置規則 |
| 実行開始 | この実行のバックアップディレクトリ |
| 実行の正常終了 | セッションの完了件数と調査資料・tickets の結果、各完了対象の原本・移行先・バックアップパス。対象0件や移動不要・原本なしも明示する |
| 途中失敗 | セッションの完了・未完了件数と調査資料・tickets の結果、各移行単位の原本・移行先・バックアップパスとその状態 |

途中失敗時の「完了」は、移行先とバックアップが確認済みで原本削除まで済んだ移行単位とする。「未完了」には、未着手、バックアップや移行先だけが作成済み、調査資料・tickets の原本が一部削除済みの状態を含め、それらを区別して表示する。調査資料・tickets が一部削除済みなら、残る原本エントリの絶対パスも表示する。セッションが完了し調査資料・tickets が未完了の場合も、それぞれの結果を表示する。

作成物は未作成・作成済み未検証・検証済みを区別し、再確認できない状態は確認不能と表示する。バックアップがまだなければ、その旨を表示する。調査資料・tickets の移動不要・原本なしは未完了件数に含めず、バックアップを作成していないことも明示する。

エラーは stderr に、失敗した段階、原因、該当パスを表示する。事前検証で計画が確定できなかった場合は、移行対象の全件が確定したかのように表示しない。捕捉可能な失敗では、停止時点で確認できる状態を表示する。

| 終了コード | 意味 |
| --- | --- |
| `0` | help、正常なpreview、対象0件、または全件の移行完了 |
| `1` | 入力データ・保存先・保持条件の不整合、原本変更、I/O失敗などによる停止。途中失敗を含む |
| `2` | 引数エラー |

## 要件との対応
