作業とticket更新は skill `tickets` に従う。修正に入る前に、次を確認する。

- 同じproject の他ticket と、解決しようとする問題・対象範囲が重複していないか。完了済みの関連ticket も確認する。
- 現在の実装・仕様・利用状況でも問題が存在するか。解決済みや意図した挙動ではないか。
- 実害や目的に照らして取り組む価値があるか。既存機能や運用で足りるか、変更の効果と負担が見合うか。

判断結果は、関連ticket ID・実装・仕様・再現結果などの根拠とともにチャットで伝える。重複・対応不要・見送りを推奨する場合や、判断材料が不足する場合は、修正に入らず、推奨する扱いと確認事項を示し、必ずuser の承認を待つ。承認前にticket を取り下げたり、`closed`・`cancelled` にしたりしない。修正すべきと判断した場合は、適用中の承認手順に従って進める。

user はticketを読んでいない前提で、対象の機能・利用場面から説明する。ticket のタイトルや内部用語だけで話を進めず、次をチャットで伝える。

- 最初：何の機能で、どの操作・状況で何が起き、何に困るのか。そのうえで今回何を調べ、何を直すのか。記録上の指摘と確認済みの事実を区別する。
- 判断を求めるとき：対象の問題を短く述べ直し、今回決めること・選択肢・推奨理由・user がすることを示す。
- 終了時：何がどう改善したか、検証で分かったこと、残件、user の対応要否を説明する。

例えば「テストをAPIへ追従させる」ではなく、「pi拡張の動作を確かめるテストが、pi更新後の呼び出し方と合わず失敗している。テスト側の呼び出し方を合わせる」のように説明する。

`closed` にするとセッションが終了するため、必要な承認・記録・説明を済ませて最後に更新する。
