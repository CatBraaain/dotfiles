ticket {{ TICKET_ID }} に対応する。作業とticket更新は skill `tickets` に従う。

user はticketを読んでいない前提で説明する。ticket のタイトルや内部用語だけで済ませず、各メッセージだけで問題と対応が分かるようにする。

ticket本文を読んだら、調査を始める前に、次をチャットで伝える。記録上の指摘と確認済みの事実を区別する。

- 対象の機能と利用場面。
- どの操作・状況で何が起き、何に困るのか。
- 今回何を調べ、何を直すのか。

例えば「テストをAPIへ追従させる」ではなく、「pi拡張の動作を確かめるテストが、pi更新後の呼び出し方と合わず失敗している。テスト側の呼び出し方を合わせる」のように説明する。

修正に入る前に、次を確認する。

- 同じproject の他ticket と、解決しようとする問題・対象範囲が重複していないか。完了済みの関連ticket も確認する。
- 現在の実装・仕様・利用状況でも問題が存在するか。解決済みや意図した挙動ではないか。
- 実害や目的に照らして取り組む価値があるか。既存機能や運用で足りるか、変更の効果と負担が見合うか。

問題が再現した場合は、再現したこと自体の報告・確認を挟まず、適用中の承認手順に従って修正・検証を進める。

再現せず、取り下げを推奨する場合は、確認した条件・結果と取り下げを勧める理由を示し、user の承認を待つ。再現しないことだけを解決済みの根拠にしない。

重複・対応不要・見送りを推奨する場合は、関連ticket ID・実装・仕様などの根拠と、推奨する扱い・確認事項を示し、修正に入らずuser の承認を待つ。承認前にticket を取り下げたり、`closed`・`cancelled` にしたりしない。

- 判断を求めるとき：対象の問題を短く述べ直し、今回決めること・選択肢・推奨理由・user がすることを示す。
- 終了時：何がどう改善したか、検証で分かったこと、残件、user の対応要否を説明する。
