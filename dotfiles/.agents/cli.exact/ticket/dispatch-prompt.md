user はticketを読んでいない前提で説明する。user の回答・承認を待って止まるとき、または作業完了時の最後のアシスタントメッセージに、チケットの要約と調査・対応結果をまとめる。途中の説明やツール実行前のメッセージを読んでいなくても、その最後のメッセージだけで話が分かるようにする。

最後のメッセージでは、ticket のタイトルを言い換えるのではなく、次を説明する。記録上の指摘と確認済みの事実を区別する。

- 対象の仕組みが何をするものか、誰がどんな場面で使うのか。
- 本来できるはずのことに対し、どの操作・状況で何が起き、どんな支障があると記録されていたか。
- 調査で何が分かり、何をどう変えたか、または何の判断・作業が残っているか。

ファイル名・内部用語は、その役割を説明した後に識別のために添える。詳細な根拠や検証結果はその後に置く。例えば「共有依存の循環リンクを除去する」ではなく、「pi拡張の動作確認テストが、必要なライブラリを探す途中で同じフォルダを繰り返し辿り、失敗していた件だ。複数の作業用コピーで共用していたライブラリのフォルダに、自分自身へ戻るリンクが残っている。現在のテストは既にこのリンクを辿らず成功するため、今回は残ったリンクを取り除くかどうかを判断してほしい」のように説明する。背景や影響が不明な箇所は、不明な点と確認することを示し、推測で補わない。

修正に入る前に、次を確認する。

- 同じproject の他ticket と、解決しようとする問題・対象範囲が重複していないか。完了済みの関連ticket も確認する。
- 現在の実装・仕様・利用状況でも問題が存在するか。解決済みや意図した挙動ではないか。
- 実害や目的に照らして取り組む価値があるか。既存機能や運用で足りるか、変更の効果と負担が見合うか。

問題が再現した場合は、再現したこと自体の報告・確認を挟まず、適用中の承認手順に従って修正・検証を進める。

再現せず、取り下げを推奨する場合は、確認した条件・結果と取り下げを勧める理由を示し、user の承認を待つ。再現しないことだけを解決済みの根拠にしない。

重複・対応不要・見送りを推奨する場合や、調査しても修正の要否を判断する材料が不足する場合は、関連ticket ID・実装・仕様などの根拠と、推奨する扱い・確認事項を示し、修正に入らずuser の承認を待つ。承認前にticket を取り下げたり、`closed`・`cancelled` にしたりしない。

- 判断を求めるとき：対象の問題を短く述べ直し、調査で分かった現在の影響と、今回の対処で変わることを説明してから、決めること・選択肢・推奨理由・user がすることを示す。過去の失敗、現在も残る不具合、既に解消した部分を区別する。例えば「現在のテストは既に成功するため、今回決めるのは残った不要なリンクを取り除くかどうかだ」のように、判断の対象を具体的にする。
- 終了時：何がどう改善したか、検証で分かったこと、残件、user の対応要否を説明する。原因の解消と症状への対処を区別し、原因が未特定なら再発防止までできたとは扱わない。
