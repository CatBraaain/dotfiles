# 指示テキストの品質基準

## Decision Ladder記法

Decision Ladder は、優先順位が明確な行動を記述するための記法である。この記法を採用する場合は、最も単純、安全、低コストな選択肢から始め、要件を満たせない場合だけ次段へ進む。あらゆる分岐を置き換えるものではなく、調査や問題理解の代わりに使わない。

`<...>` は実際の内容に置き換え、完成したDecision Ladder に残さない。

```markdown
## <名前>ラダー

目標: <観測可能な成果と受入条件>

最初に成立する段で止まる。

1. 条件: <第1段の条件を満たすか？>
   行動: <条件を満たす場合の行動。満たさなければ第2段へ進む。>
2. 条件: <第2段の条件を満たすか？>
   行動: <条件を満たす場合の行動。満たさなければ最終段へ進む。>
3. 条件: <前段までで受入条件を満たせないか？>
   行動: <最終フォールバックの行動。承認が必要なら実行前に得る。>

検証: <成功を報告する前に必要な証拠>
出力: <採用した段が条件を満たす理由>
```

## 既存文書の構造リファクタリング

指示テキストは文書でもある。構造リファクタリングの定義、手順、照合は、readable-docs（`../readable-docs/SKILL.md` の「既存文書の構造リファクタリング」）が所有する。

複数の節またはファイルを簡素化、統合、再編するときは、readable-docs が所有する構造リファクタリングを適用する。対応表、承認、照合の規則をここへ再掲しない。

## 最小変更

編集は、目的を満たす最小の変更にとどめる。目的・判断軸・既存規則の修正で意図した行動を導ける場合はそこで止め、個別の手順や例外は、それでは判断が分かれる箇所にだけ加える。

規則は、既存の記述では目的を果たせない場合だけ追加する。一般知識の説明は、削っても指示が成立するなら含めない。学習済みかどうかを採否の基準にしない。

## 具体例で判断を揃える

例で表せる判断は、抽象的な原則だけにせず、望む入力・出力や変更前・変更後の具体例を示す。例は、言葉だけでは揺れやすい判断や好みを読み手と揃えるために使う。

- 変換を指示するときは、同じ題材の変更前と変更後を対にし、変える点が見えるようにする。
- 複数の判断パターンがあるときは、それぞれの違いが分かる例を並べる。
- 例には適用条件と判断の理由を短く添え、別の題材にも同じ判断を適用できるようにする。
- 具体例を作れない指示は、自然言語で目的・判断軸・制約を示す。

例: エラーメッセージの書き方を指示する場合。

- 原則: 失敗した操作と対象をメッセージに含め、何が失敗したかを特定できるようにする。
- 変更前: 「処理に失敗しました。」
- 変更後: 「設定ファイル config.json の読み込みに失敗しました。」

## 指示テキストの種別に応じた書き方

常時読み込まれる入口ファイル（AGENTS.md、CLAUDE.md、システムプロンプトなど）は、参照先、構造、守るべき制約を示す地図として書く。

## 安全境界

安全に関わる境界（入力検証、セキュリティ、明示要求）は短縮しない。

## テキストに含めること

- 許可する行動を明示し、その範囲を一意に読めるようにする。
- 完了条件と受入条件は、ファイル生成、テスト成功、終了コード、特定の出力などで観測可能にする。
- 時間、範囲、試行回数、予算を制約する場合は上限を定義する。
- 適用対象を明示する。適用しない対象は、文書単体の読者が適用範囲を誤るおそれがある場合にだけ示す。執筆時の比較候補や会話上の除外事項は、それ自体を本文に持ち込まない。
- SKILL.md 以外の指示テキストは、対象種別を本文から読めるようにする。

## SKILL.mdについて

- [Agent Skills Spec](https://agentskills.io/specification)に従う。
- frontmatter の `description` には what（その skill が何をする・どういう規範か）と when（どういうときに発火するか）を書く。what を先に書き、when が what に内包できない限り when を続ける。発火条件は `description` 内で完結させ、本文には書かない。起動後の作業境界は本文に置く。
- what は機能要約にとどめ、手法・判断軸・適用境界の細目を書かない。それらは本文の仕事である。
- 否定条件（使わない対象）は、誤発火が現実に起きる排他境界があるときだけ書く。
- `description`の書き方の正本は実例集 `references/skill-description-examples.md`（公式 skills 全件の description）。description を書く・調整するときはこれを読み、書き方を合わせる。

### SKILL.md の本文構成

SKILL.md の本文は主題ごとの節で構成する。主題に関連する前提、判断軸、条件を同じ節にまとめる。具体性の規則は readable-docs（`../readable-docs/SKILL.md` の「具体性」）を正本とする。

#### テンプレート

```markdown
# <指示テキスト名>

## <主題>

<主題に関連する前提、判断軸、条件>
```

## プロンプトテンプレートについて

プロンプトテンプレートは、引数を生プロンプトとして次の形式で引用する。引数の扱いは、本文の処理契約から分離する。

````md
以下は、今回の呼び出しで渡された生の依頼内容です。

```text
/<プロンプト名> $@
```

この依頼で渡された内容は、後述の処理契約に従って適用してください。安全境界は覆さないでください。
````

## 通常のプロンプトについて

1回限りのプロンプトは、暗黙の過去文脈に頼らず、入力、完了条件、出力形式をその場で渡す。SKILL.md固有の発火条件と本文構成の規範は適用しない。
