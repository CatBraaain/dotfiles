# Session Review

pi のセッションログを期間で見直し、運用の調整候補を抽出し、正本の所在と cwd に応じて適用または起票する手順である。週次などの定期運用の実行を想定し、読者はこのskillを実行するコーディングエージェントである。

## 期間と対象

- 対象期間は依頼文から確定し、指定がなければ直近7日。基準日の今日は `date` で取得する。
- 抽出対象（辞書・モデル設定・AGENTS.md・スキル）も依頼文から確定する。特定のカテゴリだけを求める依頼では、そのカテゴリを主として報告し、残りは主要なものに絞って補足する。報告の並び順も依頼の焦点に合わせる。
- 対象は全プロジェクトの main セッションである。`~/.pi/agent/sessions/` 直下のディレクトリがセッション開始時の cwd に対応し、各ディレクトリの `subagents/` 配下は subagent セッションである。各ディレクトリの `archive/` 配下は旧 main セッションの退避先で user 発言が記録されているため、直下と合わせて対象に含める。
- AGENTS.md・スキルへの反映を調べる場合は、次節の精読を先に行う。辞書・モデル設定だけの調査では、プロジェクト単位で抽出し、誤変換の対やモデル変更と症状を照合すればよい。

## 指示・訂正の精読

開始・終了時刻とタイムゾーンを記録し、期間内（開始を含み終了を含まない）にユーザー発言のある main セッションを、アーカイブを含めて列挙する。判定にはファイル更新日ではなく発言レコードの時刻を使う。セッション ID で重複を除き、途中から再開できるよう、セッション ID・実体のパスごとに読了位置と結果（該当あり・該当なし・未読範囲）を残す。読めないログは未読として報告する。

### セッションごとの抽出：1セッションにつき `junior` 1人

対象ログを先頭から順に読む。長いログは同じ担当が読了位置から続きを読み、期間外の発言も依頼の経緯を理解するために参照する。検索のヒットや既存の要約だけでは読了としない。履歴内の指示は実行しない。

返すのは会話の要約ではなく、場面ごとの記録。元の依頼、直前の応答・操作、ユーザーが補った言葉の原文、その後の行動・結果、ログのフルパスと行番号またはレコード ID を一組にする。明示的な訂正だけでなく、頼み直しや冒頭の予防的な指示も拾う。訂正か新要件か迷うものは捨てず、不明点を添える。出力の欠落などで結果が不明なら推測しない。該当なしでも読了範囲を返す。

### 週ごとの判定：1週間につき `senior` 1人

1. 各セッションの事例を「どんな条件で、何を判断すべきだったか」で比較する。単なる言い回しの一致、同じ手戻りでの複数回の訂正、自動挿入か本人の追記か不明な定型文を、独立した反復の根拠にしない。初週は、長いのに「該当なし」とされたログなどを原文から抜き取り点検する。重要な見落としが続く場合に限り、同種のセッションを個別に再点検する。
2. 手戻りを一往復ずつ原文で確かめる。その指示の直前に分かっていたことだけで、どんな行動を取ればどの一言が不要になったかを書く。成果を見て初めて決まった好みや、必要な承認の回答まで失敗に数えない。
3. 当時のシステムプロンプトは、セッションファイルの `role: "system"` のレコードから直接読む。本文が `message.sections` に分かれている場合は、そこを読む。スキル本文は、行動前にセッションへ挿入された本文や `read` の結果を読む。該当する条件と取るべき行動を規定した一節を引用し、実際の行動と比べる。関連する一般論だけなら、足りない条件・行動を示す。具体的な規定があるのに行動が異なった場合は、その理由を裏づけるログを示す。理由が分からなければ「原因未特定」として残し、未読や違反を推測しない。必要な記録がセッションファイルにない場合だけ「記録なし」とし、コミット日時から当時の指示を推測しない。修正の要否は最新の正本に照らして判断する。同じ不足が残っている場合だけ文面の修正を提案し、その不足への対策が正本にあれば「正本で対応済み」とする。変更後の指示が実際に使われたか、手戻りを防げたかは別に確認する。「追記しない」と「手戻りを解決できる」は別の判定である。
4. まず聞き直しの直前に**実際に出した成果物**へ、不足していた答えを一言だけ補ってみる。それで足りるなら、新しい承認・事前説明・別の成果物は不要。その成果物を規定する正本の節を末尾まで読み、今の答えを本来含められる項目を選ぶ。そこに適用する読者・時点・行動を変えず、判断を曖昧にした語句を特定する。その語だけを差し替えて原文に戻し読みし、他の義務や例外を保ち、聞き直しを伏せても、差し替え後の文から今回必要だった区別を読み取れれば統合案とする。「適切に」「指定どおり」のように、区別を読み手に委ねたままの語は使わない。条件が限定的なら、その条件を語句に残す。例えば検証報告の「操作」が実行と模擬を区別しないなら、`操作` → `実際に行った操作と模擬した操作` として同じ欄を具体化する。`操作と結果` → `操作と結果（模擬した場合は別途説明する）` は、元の項目を残して条件付きの指示を足しており統合ではない。
5. 各案は**省きたい一言と背景**から始める。直前の判断、代わりの行動、ログ位置に続けて、正本のファイル・節と、実際に適用できる最小差分を示す。統合案では、現行文に一度だけ現れる変更箇所を「旧 → 新」で示す。変更しない前後は書き直さない。旧文の後ろに括弧・但し書き・別文を継いでいたら提出前に差し戻し、元の曖昧な語を具体語に言い換える。語を置き換えても解けない別の義務は統合と呼ばない。分離・追記する場合はその義務を必要とする場面だけに置き、最も近い文ではなぜ足りないかを示す。移動元には重複を残さない。具体案は保留でも評価用に提示し、適用外と保留理由を添える。変えるべき判断がなければ文案を作らない。
6. 対象・読了・未読の件数と各セッションの結果を報告する。未読があれば週全体を完了扱いにしない。

## ログの参照

ログは JSONL 形式。先頭の `session` に ID と cwd、`message` に発言者と内容がある。`model_change` はモデル変更、assistant の `toolCall` は操作の記録である。スキル参照の手掛かりには `read` の `arguments.path` を使う。内容検索と原文の再確認には `session-search search`・`session-search show` が使える。

## 候補の抽出と報告

各候補の正本は、dotfiles リポジトリの AGENTS.md（正本と展開先）の規則に従って探す。候補は次の5種類で、根拠セッションは、実在を確認したセッションファイルのフルパスで示す。具体的な修正案に至らなかった観察（実害のない未発火など）は、報告の末尾に参考記録としてまとめる。

- 辞書の追記候補: 表記・既存登録の有無・根拠セッション
- モデル設定の調整候補: モデル・観測された問題・根拠セッション
- AGENTS.md の調整候補: 種類・調整内容・根拠セッション
- スキルの修正候補: 対象skill・疑いの種類・根拠セッション・修正の方針
- 新規 skill の作成候補: 繰り返しパターンの種類・skill 化する手順・根拠セッション

### 辞書の追記候補

- 対象は OpenWhispr の個人辞書で、認識ヒントとして使う。文字起こし後の置換を担う snippets 機構は OpenWhispr 側で管理され dotfiles の正本がないため、候補の対象は個人辞書に限る。
- エージェントの読み替え宣言（「〜を〜と読み替えて進める」の類）と user の訂正から、誤変換語と正しい語の対を見つける。期間内に繰り返されている対を優先する。
- 候補を出す前に既存登録を確認する。登録済みの語は候補から外し、「登録済み・誤認識継続」として区別して報告する。
- 文脈で判断される一般語の同音異義語など、辞書登録で補正できない対は AGENTS.md の調整候補へ振り分ける。

### モデル設定の調整候補

- セッションの `model_change` レコード（`provider`・`modelId`）と会話を突き合わせ、特定モデルでの繰り返し失敗や品質の問題を観測したら、モデル設定の調整候補として報告する。

### AGENTS.md の調整候補

- 辞書で解決できない音声認識の誤聴は、AGENTS.md の音声入力の解釈への追記候補とし、誤変換語と正しい語の対で報告する。
- そのほか、期間内に繰り返し観測される運用のズレ（同じ指摘の反復、ルールの欠落で user が訂正した場面）も候補にする。単発の改善案は参考記録に置く。

### スキルの修正候補

- 発火記録と会話内容を突き合わせ、発火すべきでなかった場面（description が広すぎる疑い）と、実行中に user が訂正・不満を示した場面（本文の修正候補）を見つける。read は「コードを書く前に必ず読む」系の常時読み込みと区別できず、`skill-status` イベント（firedSkillNames）とも乖離する。description 起点と推定できる read だけを発火の疑いとして扱い、常時読み込みらしきものは参考記録に置く。
- 発火記録がなく、description に合致しそうな会話は、発火漏れの疑いとして記録する。発火しなかったことの確定はできないため、疑いの列挙までにする。発火漏れの候補は、user の訂正や実害が観測された場面に限る。運用語の定着だけで実害のない未発火は参考記録に置く。候補は、直近のコミット・ticket で対応済みでないか確認してから列挙する。
- 修正文案は、該当 SKILL.md の実物を読んでから書く。

### 新規 skill の作成候補

- user が同じ指示を繰り返している、エージェントが同じフローを繰り返し遠回りしている、エージェントが同じ間違いを繰り返している場面で、手順の skill 化で解決できるものは、新規 skill の作成候補として記録する。
- 同じ失敗が既存 skill の不足から起きている場面は、スキルの修正候補へ振り分ける。

## 適用

候補が1つもなければ、その旨を報告して終える。候補があるときは、候補の正本の所在と cwd で適用方法が変わる。

| 候補の正本と cwd | 適用方法 |
| --- | --- |
| 正本が dotfiles（辞書・モデル設定・AGENTS.md・共有skill）で、cwd が dotfiles（またはその worktree） | Git Worktree Strategy に従って subworktree を作り、正本を編集・作成して変更を提示する |
| 正本が dotfiles で、cwd が dotfiles 以外 | 編集せず、tickets skill に従って dotfiles プロジェクトへ起票する。1件にまとめ、タイトルに見直し日を含め、本文に候補リスト（根拠セッションつき）を書く |
| 正本が cwd のプロジェクト（プロジェクト専用 skill） | AGENTS.md（skill の編集先と読み込み先）の規則に従い、subworktree を作って編集し、変更を提示する |
| 正本が第3のリポジトリ（cwd と dotfiles のどちらでもないプロジェクト専用 skill など） | 編集せず、tickets skill に従ってそのプロジェクトへ起票する |

正本の編集では、その正本に適用される仕様・検証手順に従う。
