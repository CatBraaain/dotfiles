# Coding Standard

## 指標

唯一の指標は **他人が完全に理解するまでにかかる時間**。理解したとは「バグを見つけ、安全に修正できる状態」になったこととする。骨格は Dustin Boswell & Trevor Foucher『The Art of Readable Code』。

指標に二段階で働く。まず理解・修正の対象を減らし、次に残った行の読解コストを下げる。

## 原則

個別のルールはこの原則の適用例である。ルールが判断を与えない場面、またはルール同士が競合するときは、原則に戻って判断する。

- **保守対象を小さく。** 将来の読み手・直し手が触る対象が、そのまま理解時間になる。
- **最小化は道具。** 目的は要件と安全境界の充足であり、最小化は明示要求、信頼境界での入力検証、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティに優先しない。省略・簡略化は、確認・記録・明示のいずれかで外から見えるようにする。
- **名前が中身を語る。** 読み手は名前から中身・単位・状態・制約を予測して読む。検証前後など安全に関わる区別は、名前で分ける。予測が外れると読み直しが起きる。
- **一度に頭に置く量を減らす。** 読み手が保持しながら読む量が、そのまま理解時間になる。
- **予測どおりに読める。** 主語の逆転、末尾の条件、名前と異なる振る舞いなど、予測を裏切る形が読み直しを生む。
- **情報は変更と共に保守される場所へ。** 理由は、変更後に同期しなくなる場所（コメント）ではなく、名前・構造・型、設計記録、コミットメッセージに置く。

## 最小の選択

指標の第1段「理解・修正の対象を減らす」の適用。選択判断は「保守対象を小さく」「最小化は道具」に従う。

### 最小の実装

動作要件と安全境界を満たす、保守対象が最も小さいコードを選ぶ。賢いコードより退屈なコードを優先する。

同じ要件を満たせるなら、変更しない・削除する、既存の helper・型・パターンを再利用する、標準ライブラリを使う、プラットフォーム機能を使う、導入済みの依存を使う、必要最小限の固有コードを足す、の順に軽い選択肢を優先する。この優先度は探索順や実装を固定するものではなく、保守対象、既存設計、安全境界を踏まえて選ぶための目安である。

現時点の動作に寄与しない抽象、設定、拡張点は避ける。ただし、明示要求または既存設計との整合のために必要なものは、その理由を優先する。

### 選択と調査

最小化を調査や問題理解の代替にしない。変更の必要性、受入条件、実際のデータ・制御の流れを踏まえて変更範囲を選ぶ。バグ修正では、必要に応じて呼び出し元も調べ、症状ではなく根本原因に働きかける。

### 境界・上限・出力

- 最小版と完全版の境界が曖昧な場合は、ユーザーに最小版の範囲と省略範囲を示して確認する。確認前は、最小版・完全版のいずれも実装しない。
- 既知の上限を持つ簡略化を選ぶときは、上限と移行条件を設計記録に残す。置ける設計記録が無いときだけコメントに残す。
- コードをチャットに出力するときは、コードブロックの直後に、各1文の `省略: ...` と `追加条件: ...` を添える。

### 承認が必要な変更

明示要求のない新規依存、またはデータ損失・セキュリティ境界の変更・外部状態の不可逆な変更を伴う操作は、追加・実行前に承認を得る。

### コメント

コメントは書かない。1行でも書きたくなったら順に他の置き場を試す:

1. 名前・構造・型 — 意図を語れる形にコード側を直す。意図説明のコメントは説明変数に置き換える。
2. 設計記録 — リポジトリ内でコードとともに保守される文書。置けるなら選択の理由はここに書く。
3. コミットメッセージ — その変更で入った理由は変更のコミットに書く。

「公式サンプルにもコメントがある」「読み手が仕様を知らないかもしれない」は書く理由にならない。サンプルや docs に書かれた情報も、名前・構造で語せるならコメントには置かない。

コメントを書いてよいのは出典付きの1行だけ:

- 上流（ライブラリ、OS、API、言語処理系）のバグ・欠陥や制約を回避する非自明なコードに、理由と出典（issue URL等）を1行で書く。上流が修正されたときに外せるように。

出典のないコメントは書かない。

## 読みやすさの技法

選択を終えて残った行を、原則「名前が中身を語る」「一度に頭に置く量を減らす」「予測どおりに読める」で読みやすくする。

- 名前は中身・単位・状態・真偽・範囲・意図が読める形にする（例: `timeoutSeconds`、`safeUrl`、`isEmpty`）。小スコープなら短い名前でよい。
- 複雑な条件は一度変数で受け、名前が意味を語らせる。
- ガード節・早期 `return` で平坦にする。
- 左辺に調べる対象、右辺に定数を置く（`while (bytes < maxBytes)`）。
- 関数は「する」か「答える」かの一方にする。`get` なのに状態を変えない。
- スコープを最小に、宣言は使う直前、再代入は避ける。
- ファイルは冒頭に高抽象度の概要、末尾に細部。配置変更では依存関係と初期化順を保つ。
- テストは仕様書。テスト名は振る舞いを文章で言い、1テスト1振る舞い、失敗メッセージに input / 実際値 / 期待値を載せる。

### 適用の順序

1. 構造 — 関数は一つのコトだけ。無関係なサブ問題は切り出す。
2. 名前 — 具体名で語らせる（上記「名前」）。
3. 型 — ドメイン概念に専用の型を。magic string より enum、boolean 3値より enum。

実装の理解しにくさをコメントで埋めようとしたら、上のレベルに戻る。

### レビュー時の適用手順

読んでいて「立ち止まった」「戻って読み直した」箇所を本スキルの適用対象にする。原則に戻って直し方を選ぶ。
