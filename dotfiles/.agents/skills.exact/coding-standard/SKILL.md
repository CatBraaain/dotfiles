# Coding Standard

## 二つの軸

唯一の指標は **他人が完全に理解するまでにかかる時間**。理解したとは「バグを見つけ、安全に修正できる状態」になったこととする。骨格は Dustin Boswell & Trevor Foucher『The Art of Readable Code』。

指標に二段階で働く。まず書く量を減らし、次に残った行を読みやすくする。

- 適用する: コードの実装・修正・リファクタ・設計・依存選定・レビュー。
- 適用しない: コードを変更・評価しない調査、文書、設定だけの作業。

## 最小の選択

### 最小の実装

動作要件と安全境界を満たす、保守対象が最も小さいコードを選ぶ。上書きより削除、賢いコードより退屈なコード、自作より既存の仕組みを優先する。最小化は、明示要求、信頼境界での入力検証、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティの基本に優先しない。

### 選択と調査

最小化を調査や問題理解の代替にしない。変更の必要性、受入条件、実際のデータ・制御の流れを踏まえて変更範囲を選ぶ。バグ修正では、必要に応じて呼び出し元も調べ、症状ではなく根本原因に働きかける。

### 選択肢の優先度

同じ要件を満たせるなら、変更しない・削除する、既存の helper・型・パターンを再利用する、標準ライブラリを使う、プラットフォーム機能を使う、導入済みの依存を使う、必要最小限の固有コードを足す、の順に軽い選択肢を優先する。この優先度は探索順や実装を固定するものではなく、保守対象、既存設計、安全境界を踏まえて選ぶための目安である。

### 将来性と共有

現時点の動作に寄与しない抽象、設定、拡張点は避ける。ただし、明示要求または既存設計との整合のために必要なものは、その理由を優先する。

### 境界・上限・出力

- 最小版と完全版の境界が曖昧な場合は、オーナーに最小版の範囲と省略範囲を示して確認する。確認前は、最小版・完全版のいずれも実装しない。
- 既知の上限を持つ簡略化を選ぶときは、上限と移行条件を、その簡略化を採用するコードのコメントまたは変更の設計記録に残す。
- コードをチャットに出力するときは、コードブロックの直後に、各1文の `省略: ...` と `追加条件: ...` を添える。

### 承認が必要な変更

明示要求のない新規依存、またはデータ損失・セキュリティ境界の変更・外部状態の不可逆な変更を伴う操作は、追加・実行前に承認を得る。

## 読みやすさの技法

選択を終えて残った行を、次の技法で読みやすくする。

### 読み順

ソースファイルは新聞記事のように読めること（newspaper metaphor。Robert C. Martin『Clean Code』）。

- 冒頭に高抽象度の概要 — そのファイルが何を提供するか（公開 API、エントリポイント、主要な流れ）。
- 下へ行くほど抽象度を下げる。末尾に低レベルな細部（下請け関数、定数）を置く。
- 読み手は冒頭だけ読んで大意を掴み、詳細は必要になったら下へ読み進める。

### 名前

「症状 → 直し方」で読む:

- 抽象名（`data` `info` `value` `tmp`）→ 入っている中身を具体的に言う。
- 単位が読めない（`timeout`）→ 単位を添える（`timeoutSeconds`）。
- 安全性/状態が読めない（`url`）→ 修飾して明示（`safeUrl` / `unsafeUrl`）。
- 真偽が読めない（`flag` `status`）→ `is/has/can/should` 接頭辞。
- 二重否定（`!isNotFound`）→ 肯定形（`isEmpty`）に。
- 範囲の包含が不明 → 上限下限は `max/min`、両含は `first/last`、含/不含は `begin/end`。
- 意図が一意でない（`filter` = 残すのか除くのか）→ 一意な語に（`select` / `exclude`）。

小スコープなら短い名前（`i`, `k`）で良い。スコープが広いほど長く具体的に。

### 式に名前を付ける

複雑な条件をそのまま `if` に書かず、一度変数で受ける（explaining variable / summary variable）:

```
# 悪
if (user.age > 18 && user.hasSubscription && !user.isBanned) { ... }

# 良
const canAccessPremium =
  user.isAdult && user.hasActivePlan && !user.isAccountFlagged
if (canAccessPremium) { ... }
```

真偽の意味を名前が語る。条件が込み入っているなら De Morgan の法則で整理してから。

### 制御フロー

- 左辺 = 調べる対象、右辺 = 定数/比較値（`while (bytes < maxBytes)`）。読み手の「主語と述語」になる。
- ネストは深くしない → ガード節・早期 `return` で平坦に。深い `else` より `return` で抜ける。
- `do/while` は避ける（条件が末尾にあり見逃しやすい）。
- 三項演算子は「両肢が値」の単純なときだけ。副作用や複数行になるなら `if`。

### 副作用

関数は「する」か「答える」かのどちらか一方（Command-Query Separation）。`get` なのに状態を変える、`check` なのに書き込むは、名前への裏切り。

### コメント

- **what（何をしているか）は書かない。** コードか名前が語るべき。書きたくなったら名前/構造に戻る。
- **why（なぜこうしたか）だけ書く。** 外部仕様・回避策・非自明な制約・ハマりどころ。
- コードと同じことを言うコメントは消す。時間が経つと腐り、嘘になるだけ。
- `TODO` / `FIXME` / `HACK` / `XXX` は意図が一意なので可。

### 変数を減らす・狭める

- スコープを最小に。宣言は使う直前で。
- 再代入を避ける。一度決まった値は変わらない方が追いやすい（write-once）。
- 役に立たない中間変数は消して直接返す。

### テストの可読性

テストは仕様書。読みやすさを最優先し、上記の名前とコメントの規則も適用する。

- テスト名は振る舞いを文章で言う（`returns empty when no rows match`）。
- 1 テスト 1 確認。複数ケースは分ける。
- assert は説明変数で。「何と何を比べてどうなるか」が自然言語で読めるように。
- 失敗メッセージに input / 実際値 / 期待値を載せる。

### 適用の順序

1. 構造 — 関数は一つのコトだけ。無関係なサブ問題は切り出す。
2. 名前 — 具体名で語らせる（上記「名前」）。
3. 型 — ドメイン概念に専用の型を。magic string より enum、boolean 3値より enum。
4. コメント — 残った「なぜ」だけを書く（上記「コメント」）。

理解しにくさをコメントで埋めようとしたら、上のレベルに戻る。コメントは最後の手段。

### レビュー時の適用手順
