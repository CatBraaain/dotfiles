# CSDD

## 用語

- CSDD（Canonical Source-Driven Development）は、観測対象を正本へ定め、実装を正本へ適合させる手法である。正本（canonical source）は、ユーザーが観測できる振る舞いまたは見た目を定め、実装が従う基準となる成果物である。ユーザーが観測できる振る舞い・見た目を観測対象と呼ぶ。oracleは、適合性レビューで真実の基準にする正本である。
- CSDD適合性レビューは、正本・テスト・実装を照合する4軸のギャップレポートである。乖離検知は、差分に現れた観測対象だけを正本へ対応付ける確認である。

## 正本の種別

| 種別 | 定める観測対象 | 例 |
|---|---|---|
| spec | 振る舞い（入出力、状態、エラー、結果、パフォーマンス特性） | `SPEC.md`、`spec/<feature-name>.md` |
| デザイン | 見た目（色、タイポグラフィ、間隔、レイアウト、コンポーネント構造） | `DESIGN.md`、html、テーマファイル |

- 各観測対象は1種別の正本にだけ定義する。振る舞いはspecへ、見た目はデザイン正本へ寄せる。要件文書・探索的なデザイン案（`designs/`等）は正本にしない。
- 適合性レビューでは、観測対象ごとに、その種別の正本をoracleにする。
- オーナーは正本だけを読んでgo/no-goする。実装コードとテストの詳細はgo/no-goの判断材料にしない。

## 責務境界

- `csdd/SKILL.md`はCSDDを適用する条件、正本の確定・整備、CSDD適合性レビュー、乖離検知、CSDD収束時の引継ぎを所有する。
- `../review/SKILL.md`は一般の契約・原則の評価、`../converge/SKILL.md`は一般の修正・検証・再評価の反復を所有する。CSDDの4軸をreviewへ移さず、反復ループをCSDDへ複製しない。
- デザイン正本の内容の作成・更新は、`../frontend/SKILL.md`と`../taste-skill/SKILL.md`を適用する。CSDDは、正本の確定、go/no-go、照合の枠組みを所有する。
- CSDDの作業順は、要件合意、正本の確定・整備、オーナーのgo/no-go、明示された実装、CSDD適合性レビュー、必要時のconvergeによる収束である。

## 観測対象

- specには、ユーザーに現れる入出力、状態、エラー、結果、パフォーマンス特性だけを書く。
- デザイン正本には、ユーザーに現れる見た目と、実装が写す値（トークン、構造の参照先）を書く。
- 正本には、観測不能な実装構造とテスト方法は書かない。

## 適用条件

次のいずれかに該当するときにCSDDを適用する。

- ユーザーが観測対象を変更するロジック、設定、またはスタイルを実装・修正する。
- ユーザーが正本の作成・修正、CSDD適合性レビュー、差分の乖離検知、CSDD収束、または「csddで作って」「sddで作って」のようなCSDDの適用を明示的に依頼する。
- 差分に観測対象の変更が含まれるため、乖離検知が必要である。

次の依頼は、CSDDの明示依頼がなく、観測対象を変更する追加要件もない限り、CSDDを開始する根拠にならない。

- ファイルの移動、改名、整理、分類、カタログ化などの手続き的な操作
- 振る舞いも見た目も変えないリファクタ、静的な設定値、コード以外の文書、設計判断だけの変更
- 調査、計画、相談、または手続きの実行だけを求める依頼

適用対象か判定できず、観測対象の変更の有無が依頼文から確定しない場合は、正本を作成せず、確認を質問して停止する。

## 正本の確定

- 着手時に既存正本を確認する。観測対象の種別に正本があれば、それをoracleにする。正本がない種別だけ整備する。
- specの作成・修正は「specの作成・修正」の規則に従う。デザイン正本の整備は、内容を`../frontend/SKILL.md`と`../taste-skill/SKILL.md`に従って作り、オーナーのgo/no-goを受けて正本にする。
- 合意済み内容から観測対象だけを抽出する。観測可能な具体値が未確定なら推測せず質問して止まる。

## specの作成・修正

- specは1ファイルで自己完結させ、対象と振る舞いを肯定形で書く。候補、却下案、非目標は入れない。各振る舞いは1箇所だけで定義する。文書の自己完結は`../readable-docs/SKILL.md`の「文書の自己完結」、一般的な重複排除は同Skillの「重複の排除」を正本とする。
- workと表のどちらへ置くかは`~/.pi/agent/AGENTS.md`の「ファイルベース作業戦略」内「置き場の判定ラダー」に従う。表へ置く場合、単一機能は`SPEC.md`、複数機能は`spec/<feature-name>.md`に置く。プロジェクト内で両形式を混在させず、既存配置があれば維持する。機能は実装モジュールではなくユーザーが認識する単位で分ける。
- 共有リポジトリ（OSS上流など）へは、その規約に合わないファイルを残さない。specを表へ置けないリポジトリでは、specをworkに置いて正本とし、振る舞いの実装だけを通常のdiffとして納品する。
- Markdownで書き、分岐・状態・時系列・順序は、関係を最も直接に表せる視覚構造にする。記法の選択は`../readable-docs/SKILL.md`の「記法の選択」を正本とする。

## 照合単位

次の表を1回だけ置き、正本の整備とCSDD適合性レビューで共用する。

| spec構造 | 1振る舞い | Given / When / Then |
|---|---|---|
| マトリクステーブル | 1行 | 列を条件・状態・入力 / 操作 / 結果として読む。結果を変える行は分ける。 |
| 状態遷移図（`stateDiagram-v2`） | 1遷移 | 遷移元 / イベント / 遷移先として読む。 |
| シーケンス図（`sequenceDiagram`） | 観測点群 | 時系列の観測点を1シーケンスまたは観測点ごとの振る舞いへ分ける。 |
| フロー図（`flowchart`） | 分岐から観測可能な終端までの1経路 | 開始時の状態と分岐条件 / 経路上の操作 / 終端の観測可能な結果として読む。観測不能な内部ノードだけの経路は数えない。 |

| デザイン正本の構造 | 1照合単位 | 照合の読み方 |
|---|---|---|
| トークン表・値の定義 | 1トークン（1値） | 正本の値と、実装の適用箇所の値が一致するか。 |
| コンポーネント・レイアウトの規定 | 1コンポーネントまたは1領域 | 構造・配置・状態ごとの見た目が正本に一致するか。 |
| html正本 | 1要素または1領域 | 実装がhtmlの構造と見た目を写しているか。 |

## spec作成・修正時の出力

- 完了報告はspecのパス、`Verify: n/n 合格`、各セルフチェックの観点・判定（合格または適用外）・spec内根拠を含める。未実行の確認を合格と報告しない。
- セルフチェックは、「観測対象」、「specの作成・修正」、「正本の種別」の各規則と、`../readable-docs/SKILL.md`の「具体性」を個別に確認する。

## CSDD適合性レビュー

### 入力と不足時の扱い

oracleとなる正本、既存テスト、既存本番コードを読む。テストはテストランナー設定と既存命名規則を確認し、`tests/`、`test/`、本番コードと同じディレクトリの`*.test.*`・`*.spec.*`を読む。複数frameworkの混在を許容する。本番コードは、テストが参照する実装、公開入口を持つ`src/`・`lib/`等の慣習上の本番コード、見た目の照合ではスタイル・コンポーネント実装を読む。

- oracleとなる正本がなければ質問して停止する。
- spec種別でテストがなければcoverageで全振る舞いを漏れとして出し、fidelityをskipする。デザイン種別はテストを要せず、coverageを正本↔実装で行う。
- 本番コードがなければcoverageだけを行い、fidelityと余剰をskipする。
- 正本外の実装詳細を推測で補完しない。

### 実装の分解

公開入口、入口ごとの観測可能な結果分岐、見た目の適用箇所を抽出し、観測不能な内部最適化は除外する。各抽出結果を正本へ対応付け、対応がなければ余剰実装とする。

### 照合単位と4軸

4軸を1コンテキストで連続して照合する。正本起点のcoverageと実装起点の余剰を必ず両方行う。重要度は、放置すると正本・テスト・実装の適合の達成を妨げる指摘を高、それ以外を低とする。種別と重要度は次の表だけで定義する。

| 軸 | 照合 | 種別と重要度 | 判定規則 |
|---|---|---|---|
| coverage | oracle ↔ テスト。テストを持たない照合単位は oracle ↔ 実装 | 漏れ（高）、過剰（低）、順序ズレ（低） | oracleの全照合単位にテストがあるか、テストを持たない照合単位は実装に反映されているかを確認する。テストが正本外を検証すれば過剰。正本の文書上の順序と対応テストの順序が異なれば順序ズレ。正本外テストは対応テスト群の後ろに置く。 |
| fidelity | テスト ↔ 実装 | 偽陽性（高）、主語ズレ（高） | 実装を読み、モック等で実装経路を叩かない、恒真、要求経路と異なるテストを偽陽性とする。Thenが実装でなく外部依存値を主語にするときは主語ズレとする。 |
| 余剰 | 実装 → oracle | 余剰実装（高） | 実装の観測可能な入口、結果分岐、見た目に正本の対応記述がなければ余剰実装とする。テストだけの正本外検証である過剰とは区別する。修正案は正本追記と実装削除の選択肢を示せるが、適合性レビューでは採否を決めない。 |
| 逆指摘 | 実装・テスト → oracle | 曖昧（低） | 複数の実装またはテストが異なる解釈で動ける正本の記述を曖昧とする。正本に記述がない実装は余剰であり、逆指摘にしない。 |

### 出力とセルフチェック

- 対象を編集せず、テストを実行せず、コードの可読性・設計品質を審査しない。各指摘は`[軸 / 種別 / 重要度] 要約`、場所、問題、影響、修正案を含める。
- 指摘がなくても4軸すべてについて確認観点、`問題あり`・`問題なし`・`skip`の判定、根拠を出す。`skip`は入力不足と未評価の軸を根拠に書く。`n/n`または「適合している」だけで完了を報告しない。
- 4軸表の全判定規則、指摘の4要素、問題なしとskipの根拠を個別に確認する。

## CSDD収束時の引継ぎ

1. 観測対象を変更する実装依頼では、対象、利用者、観測対象、適用範囲を合意し、必要な種別の正本を整備し、そのパスを示してオーナーのgo/no-goを受けてから実装へ進む。正本の文面をチャットへ貼ってgo/no-goを求めない。go/no-goの質問には「実装→CSDD適合性レビュー→収束（高重要度指摘ゼロまたは明示した収束条件）まで一括で進んでよいか」を含め、正本の修正を指示する選択肢を残す。正本だけの依頼はgo/no-go後に止まる。ファイルの移動・改名・整理・分類・カタログ化などの手続き的な計画に対する了承（例:「進めて」「go ahead」）は、正本またはCSDD一括実行の承認として解釈しない。手続き的な依頼では、オーナーがCSDD収束または一般の収束を明示的に依頼するか、CSDD一括実行を承認するまでconvergeを開始しない。
2. CSDD適合性レビューは、正本・テスト・本番コードを入力に上記の4軸を実施し、編集・テスト実行なしでギャップレポートを出して止まる。
3. ギャップの修正・検証・再評価を依頼されたときは、`../converge/SKILL.md`を適用する。修正後の4軸再レビューを省略しない。
4. 修正で正本を変える場合は、変更後正本のgo/no-goを受けるまで実装・CSDD適合性レビューを再開しない。
5. CSDD適合性の収束完了は、convergeの収束条件を満たし、最終のCSDDギャップレポートに高重要度の指摘がなく、実行すべき検証が通ったときだけ報告する。

## 差分の乖離検知

commit・PRなどの差分確認では、差分に観測対象の変更が含まれる場合、またはCSDD適合性の確認が明示された場合に限り、全文照合をせず、差分で変わった観測対象だけを確認する。手続き的な差分だけを確認する依頼では、この節を適用しない。

1. 差分、変更前後の公開入口、既存正本を読む。公開入口または観測対象を特定できなければ質問して停止する。
2. 各観測対象を正本の節、表行、図の遷移・経路、トークン・コンポーネントの定義へ対応付ける。ファイルパスや実装モジュール名だけで対応付けない。
3. 次の表を観測対象ごとに出す。`正本 に対応なし`または`照合不能`が1件でもあれば一致完了を報告しない。正本とテストをIDで機械的に紐付けず、テスト実行成功だけを一致の証拠にしない。

| 変更した観測対象 | 正本の対応箇所 | 判定 | 根拠 |
|---|---|---|---|
