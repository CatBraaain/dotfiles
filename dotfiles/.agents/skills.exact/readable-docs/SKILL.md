# Readable Docs

## 可読性の指標

唯一の指標は **読者の認知負荷**。読者が文書だけで目的を果たせることを必要条件とし、必要な情報を見つける手間と誤読のしやすさで評価する。

## 技法カタログ

文書を下のカタログの全項目と漏れなく照合する。カタログの項目をレビューに使うときは、指摘に項目ID（例: Self2）を添える。

各 after は「合格の一例」であり、唯一の正解ではない。

### Form 記法の選択

段落、リスト、表、図のうち、情報の関係を最も直接的に読める記法を選ぶ。構造を散文より明確にできない場合は、記法を増やさない。

#### Form1 最も直接読れる記法

散文で書いた手順・条件・列挙を、関係が最も直接読める記法へ置き換える。

##### before

```markdown
初めに設定ファイルを読み、次に存在チェックを行い、なければ作成して、最後に結果を出力する。
```

##### after

```markdown
1. 設定ファイルを読む
2. 存在を確認し、なければ作成する
3. 結果を出力する
```

#### Form2 表は行と列の対応で読める情報に使う

表は、条件・属性ごとの値など、行と列の対応で読める情報に使う。

##### before

```markdown
モードが simple のとき出力は1行、verbose のときは詳細形式、json のときは構造化形式である。
```

##### after

| モード | 出力 |
| --- | --- |
| simple | 1行 |
| verbose | 詳細形式 |
| json | 構造化形式 |

#### Form3 図は関係の主表現

図にすることで他の記法より関係・構造を明確にし、読者の判断を容易にできる場合は、図を主表現に選び、本文は図に置けない前提・判断だけに絞る。1つの図表は1つの問いに答え、本文には図表の読み上げではなく結論を置く。図は htmlshot で HTML ベースで作る。

##### before

```markdown
未注文は注文待ちへ移り、注文待ちは支払い完了で発送済みへ移る。キャンセルは注文待ちからのみ可能である。
```

##### after

図(htmlshot で生成した `.html.png` を本文に置く):

```html
<div class="flow">
  <div class="state">注文待ち</div>
  <div class="transition">支払い完了</div>
  <div class="state">発送済み</div>
</div>
```

#### Form4 強調装飾は最終手段

Markdown の bold・italic などの強調装飾は原則使わない。
見出し・リスト・コードなどの構造で情報を伝える。本当に強調しないと誤読や安全上の見落としが生じる場合だけ、最終手段として使う。

##### before

```markdown
**設定**を**必ず**保存すること。
```

##### after

```markdown
設定を必ず保存すること。
```

#### Form5 表の同じ列は同じ型で書く

表は、上から下へ行を比較して読まれる。同じ列のセルの文型・語順・動詞・用語・表記が行ごとに揺れると、読者は差ではなく揺れを読み直すことになる。同じ列のセルは、比較したい差だけが残る同じ型で書く。

##### before

```markdown
| 項目 | 説明 |
| --- | --- |
| タイムアウト | 30秒がデフォルト |
| リトライ回数 | 初期値は3回 |
```

##### after

```markdown
| 項目 | 説明 |
| --- | --- |
| タイムアウト | 既定値は30秒 |
| リトライ回数 | 既定値は3回 |
```

### Mini 最小完全性

読者が目的を果たすために必要な情報を、不足なく、それ以上に含めない。背景や経緯が読者の目的に含まれる文書(意思決定の記録など)では、その目的に必要な範囲の背景を含める。

#### Mini1 量でなく判断を測る

行数・文字数・削減量ではなく、読者が正しく判断できることを成果とする。読者の判断に背景が要る文書では、その背景も判断材料に含める。

##### before

```markdown
## 概要

本プロジェクトは2019年に始まり、当時の要件定義では手動運用を前提としていた。その後の運用負荷の増加を受け、今回の変更が計画された。
```

##### after

```markdown
## 概要

この変更は、ログイン失敗の通知先を設定可能にする。
```

### Dup 重複の排除

主張・定義・手順は一箇所にだけ置く。

#### Dup1 残す場合の例外

他の節の要約、同じ意味の別節、本文を写した図表、空節は、読者の判断に必要な独自情報を増やす場合だけ残す。

##### before

```markdown
## エラー処理

エラーはログに出力する。

## ログ出力

エラーはログに出力する。
```

##### after

```markdown
## エラー処理

エラーはログに出力する。
```

### Del 削除

定義、適用範囲、必要な境界、参照される記述は、削除後も解釈が一意に定まる場合だけ削る。

#### Del1 自明な定義の言い換え

読者が文書の他の部分から意味を復元できる定義・言い換えは、削除しても解釈が変わらないなら削る。

##### before

```markdown
編集する。ただし編集とは、ファイルの内容を変更する操作のことである。
```

##### after

```markdown
編集する。
```

### Self 文書の自己完結

文書は、過去の会話、変更履歴、執筆過程、編集中のリポジトリに関する知識なしに理解できる最小前提を含める。読者はその文書だけで目的を果たせる。そのために、文書は他の文書・過去の文脈・管理側の事情のいずれにも依存せず、独立に保つ。

#### Self1 他文書の内容を写さない

定義・手順は、それを正本として持つ文書にだけ書く。他の文書は参照し、内容を写さない・要約しない。同じ内容が複数の文書にあると、更新が片方にだけ反映されて独立が壊れる。

##### before

ツールの README:

```markdown
## 設定

既定のタイムアウトは30秒、再試行回数は3回。設定仕様書にも同じ値を記載する。
```

##### after

ツールの README:

```markdown
## 設定

既定値については、設定仕様書を参照する。
```

#### Self2 依存は依存する側の文書にだけ書く

文書Aが文書Bを使うとき、その依存の記述はAにだけ置く。BにAの使い方・Aとの使い分け・Aへの言及を書かない。BはAを知らなくても独立して成立する。

##### before

共通ライブラリの SPEC:

```markdown
## 出力

`report-generator` はこのライブラリの出力をMarkdownへ変換して使う。
```

##### after

共通ライブラリの SPEC:

```markdown
## 出力

出力はJSONで返す。
```

変換の記述は、report-generator 側の文書にだけ置く。

#### Self3 変更経緯と管理事情を持ち込まない

変更の依頼や経緯は、読者の目的に必要な現在地の記述へ変換してから採用する。「旧仕様のAではなく新仕様のBにする」のような比較形は、正本ではB単独の記述へ置き換える。変更履歴・検討過程・却下記録は報告・ワークファイル・ticket へ置く。取り込み・ビルド・正本の保管構成など管理運用側の事情は、配布先の読者の行動に影響しない限り本文に書かない。

##### before

ユーザーガイド:

```markdown
## インストール

旧バージョンでは `setup.py` を実行していたが、現在はパッケージマネージャーでインストールする。
```

##### after

ユーザーガイド:

```markdown
## インストール

パッケージマネージャーでインストールする。
```

#### Self4 除去・改名のあとに参照を残さない

名前・パス・機能・運用を除去・改名するときは、その語の文書内の全出現を確認し、参照先のない記述を残さない。1箇所だけ置き換えて残りを残すと、読者は実在しない参照を読むことになる。

##### before

オプションを1つ廃止したあとのリファレンス:

```markdown
| オプション | 説明 |
| --- | --- |
| --output | 出力先を指定する |
| --verbose | 詳細ログを出力する |
```

##### after

```markdown
| オプション | 説明 |
| --- | --- |
| --output | 出力先を指定する |
```

#### Self5 現在の完成状態だけを書く

将来の検討・未実装の機能・予定を、現行の仕様や手順の文書に混ぜない。読者は現在の状態だけを読む。将来案は roadmap やワークファイルへ置く。

##### before

ツールのリファレンス:

```markdown
## 入力

入力はファイルパスのみ。将来のバージョンではプロンプト入力も受け付ける予定である。
```

##### after

ツールのリファレンス:

```markdown
## 入力

入力はファイルパスのみ。
```

#### Self6 文書の対象だけを書く

その文書の対象・読者に関係しない関心を書かない。横断的な運用原則や別の対象の規則は、それを所有する文書へ置く。対象は文書の冒頭で特定した範囲で判定する。

##### before

検索機能の REQUIREMENTS:

```markdown
## 検索条件

検索語はキーワードとフィルターを組み合わせられる。

## 運用

エージェントは破壊的操作の前に user の承認を得ること。
```

##### after

検索機能の REQUIREMENTS:

```markdown
## 検索条件

検索語はキーワードとフィルターを組み合わせられる。
```

運用規則は、運用を定める文書にだけ置く。

### Term 冒頭と用語

冒頭で対象・目的・適用範囲・読者を特定し、用語を文書内で定義する。

#### Term1 冒頭で対象と用語を特定する

文書の冒頭に、対象・目的・適用範囲・読者を置き、本文で使う用語を文書内で定義する。

##### before

```markdown
# 設定ガイド

## タイムアウト
```

##### after

```markdown
# 設定ガイド

このガイドは report-generator の設定項目を、運用管理者に向けて説明する。

## タイムアウト
```

### Norm 本文と規範の形式

本文の各記述は、文書単体の読者が対象を理解・判断・実行するために直接必要である。規範は肯定形を基本にする。

#### Norm1 本文の各記述は直接必要

依頼時の会話で示された除外、経緯、既知の前提は、読者の目的に必要な情報へ変換した場合だけ採用する。文書の対象に属さない作業メモや経緯は、依頼された場合を除き本文へ持ち込まない。省略や範囲外の明示は、読者がその箇所で持つ問いに答えるときだけ書く。成果物には、読者が目的を果たすための文書だけを置く。例は読者一般に通じる題材を選ぶ。

##### before

```markdown
## 仕様

前回の依頼ではCSV出力だったが、今回はJSONに変更した。
```

##### after

```markdown
## 仕様

出力はJSONである。
```

#### Norm2 規範は肯定形を基本にする

規範は、行うこと・適用条件・保持する状態を示す肯定形を基本にする。

- 同じ行動制約を肯定形で明確に表せる場合は、肯定形を選ぶ。
- 除外・禁止は、肯定形への置換で安全または判断の境界（禁止対象・適用範囲・停止条件など）が曖昧になる場合に限って残す。
- 確認時は、各除外・禁止について肯定形への置換可否を点検し、残す場合は曖昧になる境界を特定する。置換した場合は、元の行動制約が保持されていることを確認する。

##### before

```markdown
- テストをスキップしないこと。
```

##### after

```markdown
- すべての振る舞いをテストで検証する。
```

## 編集手順

編集は、削る・統合する・記法を直すといった最小の介入から試し、文の書き直しは最後の手段にする。削除・統合した内容ごとに、保持・統合・削除のいずれかと、読者が失う意味を確認する。

## 既存文書の構造リファクタリング

複数の節またはファイルを簡素化・整理・統合する場合に適用する。局所的な誤字修正、明白な重複の削除、記法修正だけには適用しない。

分類単位は、1つの操作の対象として識別できる最小の節またはファイルとする。親ファイルとその内部の節は重複して分類しない。

### 操作

- `keep`: 変更しない。
- `merge`: 複数の分類単位を1つの正本に統合する。
- `move`: 本文を変えずに移動する。
- `delete`: 正本を残さず削除する。
- `rewrite`: 1つの分類単位の本文を再記述する。

1. 編集前に、対象の各分類単位を操作へ分類する。
2. 各非`keep`操作について、変更ブロックを1操作に1つ作り、編集作業用のワークファイルへ記録する。変更ブロックには、変更元のファイルパスと節見出し（ファイル全体なら `ファイル全体`）および編集前の本文を書く。`merge` では統合元をすべて記録する。この記録は報告に転載しない。
3. 分類した操作を実施する。
4. 完了後、自己照合用の記録と成果物を比較する。各変更ブロックへ正本または移動先のファイルパスと節見出し、編集した理由を追記してから、報告へ載せる。`delete` では正本なしと記録する。
5. 行数・文字数・削減率を受入条件や委譲条件にしない。改行削除、言い換え、散文の圧縮だけでは構造リファクタリングの完了としない。
6. 規則を原則へ統合するときも、許可・禁止、停止条件、承認、出力形式など読者の行動を直接分ける契約は明示的に残す。

### 照合

編集後、自己照合用の記録、各変更ブロック、成果物を照合する。変更元、操作、正本・移動先または正本なし、保持した意味、意図的に失った意味と理由が対応し、安全または判断の境界が失われず、構造変更の結果を報告できることを確認する。
