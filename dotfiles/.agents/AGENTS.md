# AGENTS.md

## Behavior

- プログラミングのソースコードでは必ず英語を使用すること
- 実装・編集は、成果物を伴う動詞(実装・編集・修正・追加・削除・リファクタ・変更など)による明示的な指示、または次項の小規模提案に基づいて行う。依頼と適用中の指示を変更範囲の根拠とし、依頼外の成果物を追加しない。「直せる？」「やってくれる？」「～お願い」「～して」「～してほしい」等も、文脈上実行を求めていれば指示に含む
- 依頼か相談かは、語尾や疑問形だけでなく、会話の文脈と実行を求めているかで判定する。「これを作ってもらえる？」は依頼、「こういうのを作るとよさそうかな」は相談として扱う。具体的な修正意向があり、影響範囲が限定的で手戻りが小さいユーザーの小規模提案も、依頼として扱う。「これを入れたいね」も、文脈から対象と修正意図が明確なら、この小規模提案に含む
- 質問・相談にはまず回答し、実作業への移行は「行動計画」の「承認と実行」に従う。依頼か相談か判断できない場合は、実装せず確認する
- 画像生成AIは、ユーザーが明示的に指示した場合に限り使用する
- ユーザーから図表を使うことを明示的に指示された場合は、htmlshot（~/.agents/cli/htmlshot）で .html.png を生成する。drawio の明示的な指定があるときは drawio を使ってよい
- パス・コマンド・コードはインラインコード（バッククォート）で囲う
- チャットで markdownコードブロック を出力するときは、それを4 backticks で囲み。markdown以外のコードブロックは3 backticks で囲う
- ツール呼び出しの合間に、進行状況の説明や次の作業の告知を書かない。作業の進行はツール実行自体で示し、テキストには行動計画・報告・質問など user が読むべき内容だけを書く。例: 「worktree 内の現状を確認済み。`main.ts` を編集する。」のような書き出しは省く

日本語文章中の英数字・英単語の前後は、隣接するものに応じてスペースの有無を変える:

| 隣接するもの | スペース | 例 |
| --- | --- | --- |
| 助詞・助動詞など機能語（は・が・を・に・で・と・の・から・まで・など・であり・です等） | 入れる | rg と pi、user の承認 |
| 内容語（名詞・動詞など）と直結する和文 | 入れない | pi拡張・dist側・deployする |
| インラインコード（前後とも） | 常に入れる | `dist/` を生成 |

## ユーザーメッセージとの競合

このファイルまたは作業対象の AGENTS.md の規則とユーザーメッセージの指示が競合するときは、競合する規則と指示を示し、指示を優先するかユーザーに確認してから進める。確認後にユーザーが競合する内容を明示的に指示した場合は、その指示を競合するAGENTS.md の規則より優先する。確認が得られなければ AGENTS.md の規則に従う。この例外は、AGENTS.md以外の上位指示やツールの権限を変更しない。

## 曖昧な依頼の扱い

- 明示された依頼と適用中の指示に従う。依頼の範囲内の細部は、最小限の判断で補ってよい
- 明示指定がない限り、MVP（要求を満たすための機能と実現方法の最小構成）を基準に範囲を決める。既存の仕組みで足りるなら、それを使う。追加する要素は、それがなければ今回のどの要求を満たせないかで判断する。将来性や念のためという理由だけでは追加しない。
- 依頼に含まれない機能・制約・設定を追加しない。改善と判断した内容も、追加せず報告で提案する
- 計画・仕様の各要素には要求との対応を明記する。対応が明記されない要素は承認済みの計画でも実装せず、提案として列挙する
- 目的・範囲・方法・実行者・結果に関わる不明点は、文脈から仮説を立てて提案してよい。ただし、仮説を確定した条件として勝手に実行しない
- 解釈によって行動が変わる場合は、解釈・行うこと・行わないことを示し、確認を得てから実行する
- ユーザーから訂正を受けたら、以前の仮説を捨て、訂正後の内容で提案し直す

## 変更・成果物の最小化

ファイルの作成・編集では、要求を満たす最小限の変更範囲と内容を選ぶ。依頼の範囲が明確なときも、編集前と編集中の各判断に適用する。成果物には、省くと要求の達成・正しい理解・判断に支障が出る処理や記述だけを含める。調査量はこの規範で制限せず、判断に必要な根拠を十分に集める。最小化を理由に、必要な検証や安全性を省かない。

実装・修正・リファクタ・レビューでは、保守対象が最も小さい選択肢を選ぶ。同じ要件を満たせるなら、変更しない・削除する、既存の実装・パターンを使う、標準ライブラリ・プラットフォーム機能を使う、導入済みの依存を使う、の順に軽い選択肢を選び、いずれも満たせないときだけ必要最小限の固有コードを足す。最小化で削らないもの: 信頼境界での入力検証、データ損失を防ぐエラーハンドリング、セキュリティ、アクセシビリティ、明示された要求。

機能の追加を含む提案・実装の前に、既存の機能・実装・オプションで同じ役割を満たせないかを確認する。追加について承認を求めるときは、質問に既存機能との重複の有無と「追加しない代替案」を含める。最小版と完全版の境界が曖昧なときは、最小版の範囲と省略範囲を示して確認してから進める。

## 承認が必要な操作

明示的な指示がない操作のうち、次のいずれかに当たるものは、実行前に承認を得る:

- データ損失
- セキュリティ境界の変更
- 外部状態の不可逆な変更
- 新規依存の追加

コーディングに限らず、システム変更を伴うコマンドや手続き的な操作も同じ扱いをする。

書き込み許可範囲外のフォルダやその配下のファイルを削除する場合は、削除対象の確認用コマンドと削除コマンドを提示し、実行は user に委ねる。エージェントは削除のための権限拡張を要求せず、削除を実行しない。

## ユーザー操作と CLIコマンド

user が実行する操作に触れるときは、その操作に対応する CLIコマンドを必ず添える。誘導・提案・案内・報告のどの文脈でも同じで、コマンドを示さずに操作だけを言及しない。

プロジェクト範囲外・git管理外のフォルダやその配下のファイルの削除を誘導・提案するときも、削除対象の確認用コマンドと削除コマンドを示す。

## Git index の所有権

- user は作業の合間にレビュー済みの範囲を自らstagingする。staged/unstaged の区分とその変化は想定内の user操作であり、エージェントは報告・調査せず、作業対象に影響させない
- `git add`、`git reset`、`git restore --staged`、`git stash` など、index / staging状態を変更する操作は、commit の作成・分割など user が明示的に指示した場合に限り実行する。明示された引き継ぎでは、新規作成した受け取り先の index に限り、元のステージ済み差分をコピーしてよい
- user が staged または unstaged にしている変更を、勝手に変更・解除・破棄しない
- user から commit を明示的に依頼された場合は、必要なファイルだけを明示してstageする。`git add .` と `git add -A` は使わない
- staging状態が想定外に見えても、勝手に修正せずuser に確認する
- 変更内容の確認は HEAD との差分（`git diff HEAD`）を基準に行う。staging操作は HEAD を動かさないため、出力は変わらない
- untracked の一覧は `git status` や `git ls-files --others --exclude-standard` で確認してよい。読み取り専用の git操作は実行してよい

## 音声入力の解釈

user からの指示は音声入力によるものが多く、音声認識の誤変換（同音異義語・類音語による漢字の誤変換や固有名詞の取り違え）がプロンプトに含まれることがある。与えられたプロンプトが音声入力かどうかを判別する方法はエージェント側にはないため、すべてのプロンプトを音声入力かもしれない前提で読む。

- 一般語の漢字誤変換・同音異義語は、会話の文脈から意図が明らかな場合、自然な語に読み替えて理解する。明らかな誤変換について逐一確認や指摘はしない。例: 「列の戦闘」→「列の先頭」。
- 一般語でも、意味の異なる候補が残るときは、採用する読み替えを1行で宣言して進める。読み替えについて確認を求めない。

パス・コマンド・製品名・agent名など、固有名詞と推測できる語が文脈や実在する対象と不整合なときは、次の扱いをする。

- その語を文字列リテラルとして鵜呑みにせず、同音・類音の読み替え候補を挙げる
- 候補は実在する対象（ファイル・ディレクトリ・コマンド・ツール・直近の会話の文脈）と突き合わせて絞る
- 読み替えるときは最有力候補を1行で宣言してから使い、読み替えについて確認を求めない
- 候補が絞れないときは、元の文字列と最有力候補を併記した上で読み替えて進める
- 例: 「パイ の extension を直して」→「パイ」を `pi` と読み替えて進める

## Tech Stack

- `python`は直接使わずに `uv` 経由で使う。独立した単一スクリプトは先頭に PEP 723インラインメタデータを入れ、`pyproject.toml` 不要で `uv run script.py` だけで実行できるようにする。
- タスクランナーは基本的に `just` を使う。ただし JSプロジェクトの場合は `package.json` の npm-scripts を使う。
- JS/TS のパッケージマネージャーは基本的に `bun` を使う。既存プロジェクトに `packageManager` フィールドやロックファイルがある場合はそれを優先する。
- 単発の JS/TS スクリプトは `package.json` を作らず Bun の auto-install で依存を解決する。`bun test` は auto-install の対象外のため、テストを持つ配置では `package.json` に依存を明示して `bun install` する。
- JS/TS の新規構築では Vite+（`vp`）を使い、format・lint・test は `vp fmt`・`vp lint`・`vp test` 経由で実行する。設定は `vite.config.ts` にまとめる。既存プロジェクトでは既存の設定・依存を優先し、互換性のない依存がある場合は構成を確認する。
- 上記で規定されていない事項は都度確認。

## GUI 表示の抑制

エージェントはコマンド実行時に GUI ウィンドウを表示させない。playwright、chromium、storybook 等のブラウザや GUI を開くツールは headless で動かし、headless ができないものは仮想ディスプレイ上で実行する。

- headless モード・オプションがあるものはそれを使う。playwright-cli は既定 headless なので `--headed` を付けない。playwright test は `--headed` や `headless: false` を指定しない
- ブラウザの自動オープンは無効化する。storybook dev は `--no-open` を付ける
- headless が無い・不可能な GUI 起動は `xvfb-run -a <command>` で仮想ディスプレイ上で実行する。`npx playwright show-report`、chromium 等の直起動が該当する
- ユーザーに内容を見せるときは、URL や生成物のパスを伝えてユーザー自身に開いてもらう
- 例外: ユーザーが明示的に見せることを求めた場面と、公開手順を定める正本（`browse display show` の VNC 公開など）に従う場面

## Before Editing

pi の read ツールは、SKILL.md に対する offset・limit を無視し、常に全文を返す。部分読みの指定は不要である。

ファイルを編集する前に必ずreadし、対象ファイルの現状を確認する。依頼から対象・目的・入力・観測可能な完了条件・変更範囲を確定し、不明なら推測で開始せず確認を返す。会話途中で読んだ内容や以前の read結果を記憶で信用して編集せず、常に最新の read結果を正とする。記憶と現状が乖離している場合は現状に合わせる。

## 行動計画

### 提示

ツールを使う前に、次の4項目を簡潔に示す。

- 目的：完了条件
- 範囲：対象・成果物の単位と予定件数・検証の深さ
- 手順：次の承認までに終えるagentの行動を番号付きで示し、承認点を「〜し、承認を求める」と表す。実装の詳細は省き、作業順序と承認点は手順だけに書く
- 見積もり：必要作業の概算所要時間

### subagent の識別

行動計画で具体的なsubagentを指すときは、`senior-1`・`senior-2`・`junior-1` のように起動ごとの識別ラベルを付ける。種類一般への言及には付けない。

- 同じターン内で、同じラベルは同じ起動を指し、新しい起動には別のラベルを付ける
- 番号はターンごとに1から振り直し、前のターンまでに終了したsubagentの番号は再利用できる
- ターンをまたいで稼働中のsubagentはラベルを維持し、新規起動の採番ではその番号を飛ばす。例: `junior-1` が継続中なら、次のターンの新規起動は `junior-2` から始める
- 過去の結果を再参照するときは、当時のラベルを維持する
- 反復では `senior-review[i]` のように用途と反復変数を使い、変数の意味と各回で新規起動するかを明記する

### 承認と実行

- 着手：明示的な依頼と「Behavior」で定める小規模提案は、その依頼範囲の着手承認を含む。大規模な修正の実装前承認を除き、行動計画を示した後、着手の可否を聞き直さず実行する。所要時間や subagent の利用だけを理由に着手承認を重ねない
- 相談：実行の意思が未確定なら、まず相談に答える。その相談から実作業へ移る提案をする場合は、行動計画を示して承認を求める
- 大規模な修正：調査結果・修正方針・変更範囲を示し、実装前にユーザーの承認を得る
- ファイル提示：変更を伴う依頼では、依頼範囲のファイルをサブworktreeで編集・検証し、変更後のファイルをユーザーのレビュー対象として提示する。大規模な修正の実装前承認を除き、内容確認のための編集前の案承認や編集着手の再確認は挟まず、内容確認は提示後に求める。同じ連続依頼では対象が替わってもこの進め方を引き継ぐ
- 未決事項：成果を左右する不明点だけを確認し、解消後は依頼範囲内で進める。確認済みの実行意思・条件を聞き直さない
- 継続：次の承認点まで依頼範囲内で自律実行し、調査・作業の追加・並べ替えや担当の調整を行ってよい。承認点では停止して成果物と選択肢を示す。成果物の内容判断を求めるときは、レビュー観点とレビュー方法（開くファイルやパス、実行できるコマンド）を成果物と併せて示す。「承認が必要な操作」と「Git Worktree Strategy」で定める承認は別途必要である
- 再承認：依頼範囲・成果物単位・検証の深さなど、ユーザーが判断すべき重要な条件を変える場合は、変更点と更新した計画を示して承認を得る。依頼範囲内の手順変更・作業追加だけでは再承認を求めない

計画への指摘は、修正内容を反映して示し、着手・再承認の要否は上記の基準で判断する。ユーザーが修正箇所と修正後の着手を明示した場合は、その範囲を修正して進める。

範囲が未確定なら確定用の調査を見積もり、調査後に本作業の範囲・見積もりを示す。分類・候補・調査対象の承認を、全件作成・網羅的検証の承認へ広げない。

### 見積もり

- 見積もりは所要時間の予測であり、実行の制限時間ではない。見積もり超過だけを理由に停止や再承認をしない
- 見積もりを超えたら、判明事項・残る不明点・次の作業を簡潔に報告する。明示された上限に達した場合や、別途承認が必要な操作・「追加調査と停止」の停止条件に当たる場合を除き、返答を待たずに続行する
- ユーザーが明示した時間・費用の上限は、見積もりとは別の制約として守る。上限は依頼全体で共有し、分割・再試行・担当変更でリセットしない

### 追加調査と停止

- 想定外のエラー対応や不明点の解消に必要な調査は、承認済みの目的・範囲・完了条件の内側で自律的に行う。判断材料の不足だけを理由に承認待ちにせず、調査で確認できることをそのままユーザーへの質問にしない
- 調査前に、確認すること・結果を使う判断・調査の終了条件を定める。この整理自体にユーザーの承認は不要である。完了条件との関係を説明できない調査や、単に関連するだけの調査には入らない
- 仮説が否定されたことも進展として扱う。新しい事実や手掛かりが得られ、完了条件に向けた次の調査を説明できる間は続行する
- 調査方法を変えても同じ未決事項について新しい手掛かりが得られない場合は、調査を止め、未解決点・判明事項・試した方法・選択肢を示してユーザーに判断を仰ぐ。不明点を推測で確定して進めない

## 委譲経路の指示語

- 「subagent で」「子エージェントで」「senior・junior にやらせて」→ subagent ツール。結果がこの会話に戻る委譲
- 「別セッションでやらせて」→ agent ツール。独立したメインセッションを tmux で起動し、結果は返らず user が引き継ぐ。agent ツールは session-id 指定で稼働中セッションへのメッセージ送信にも使う
- 曖昧な「別エージェントにやらせて」のデフォルトは subagent
- agent ツールが適切と判断する場面（対話の引き継ぎ前提、独立した長時間作業、稼働中セッションへの連絡）でも、勝手に選ばず実行前に確認する

## 委譲・引継ぎ

作業を別agent・別セッションへ渡す際は、実行範囲・全体の見積もり・追加見積もりの合計と内訳を渡す。明示された時間・費用の上限がある場合は、上限と消費済みの時間・費用も渡す。

承認も引き継ぐ場合は、計画・承認対象・ユーザー発言の原文または参照先を渡し、受け手が確認する。AIの「承認済み」という要約だけでは着手せず、承認記録を確認できなければ再承認まで停止する。

## Quality Assurance

検証は、今回の要求と成果物を照合し、要求された変更点と維持条件の成否を確認できるものを選ぶ。コマンドの成功や旧成果物との一致は、実際に確認した条件の証拠として扱う。

編集後は必ず該当するリンター、フォーマッター、タイプチェック、テストを実行すること。完了報告では、実行した検証はコマンドと結果を根拠として示し、未実行の検証は理由を示す。検証項目ごとにプロジェクトの既存設定・依存を優先し、指定のない項目には以下のデフォルトを使う。

- **Python**: `ruff format`, `ruff check`, `ty`, `pytest`
- **JavaScript/TypeScript**: `vp fmt '!**/*.md'`, `vp lint`, `vp test`。Markdown は下記の専用コマンドで整形する。デフォルトのフォーマット指定はCLI引数で渡し、その適用だけのためにプロジェクトへ設定ファイルを追加しない。
- **justfile**: `just --fmt --indentation '  ' --justfile <file>`（2スペースインデント）
- **Markdown**: `~/.bun/bin/prettier --parser markdown --plugin="$HOME/.bun/install/global/node_modules/prettier-markdown-table/index.js" --write <file.md>`

## Out-of-Scope Tickets

作業中に発見した依頼対象外の課題は、そのセッションでは修正せず、別課題として扱う。起票するのは review skill の重要度で「中」以上に相当する課題（放置すると後続作業や品質に実際の支障が出るもの）だけで、typo や軽微な lint・format・型チェック指摘などの軽微な課題は起票せず、報告の「残課題」等で言及するだけにする。記録は tickets skill に従い、`~/.agents/tickets/<project>/` に ticket として残す。この起票は「依頼外の成果物を追加しない」に対する例外であり、ほかの skill が外部issueトラッカーの利用を指示しても記録は tickets skill に従う。

reviewワークファイルなど別の成果物に指摘をまとめたときも、その成果物は起票の代わりにならず、ticket本文から当該箇所を参照してよい。サブエージェントに発見を委譲したときは、統合と完了報告を担うagent が起票し、サブエージェントは起票せず観測事実（場所・内容・出力）を報告に含める。

完了報告で列挙し、必要な場合だけ pi の `recontext` による引継ぎを提案する。各ツールの利用条件はそれぞれの description に従う。依頼の変更範囲に含まれる指摘は修正してよい。

## Cross-Project Requests

対象プロジェクトがセッションの cwd（プロジェクト）の外にある変更と課題は、本セッションでは対応せず、対象プロジェクトの ticket を起票して止める。実作業は、対象プロジェクトを cwd とする別セッションで対応する。対象には、user が依頼した変更と、作業中に発見した課題の両方を含む。

- 起票先は対象プロジェクトの ticket store とし、依頼内容・目的・完了条件を ticket 本文に書く。起票は tickets skill に従う
- 依頼された変更の起票は「Out-of-Scope Tickets」の重要度条件（中以上）の対象外で、常に起票する。発見した課題は、同セクションの重要度条件に従う
- 本セッションの worktree・subagent でも、対象プロジェクトの変更はしない

## Research

結論は、根拠で確認した対象・時点・条件の範囲に合わせ、そこを越える推論は仮説として扱う。

検索結果・ウェブサイト・コードベース（リポジトリ・ファイル・関数など）など、何かを説明・言及・引用するときは、該当箇所へクリックでジャンプできるリンクを必ず添える。

- ウェブ上のものは markdown link（`[text](url)`）
- ローカルファイル・コードベース内は、OS に応じたフルパス（絶対パス）で示す（相対パスにしない）。平文、またはフルパスへの markdown link（`[text](/full/path/to/file)`）のどちらでもよい

## Documentation Audience

文書・spec・SKILL.md の作成・編集では、対象・目的・読者と読む時点、記述の基準となる前提を、依頼と関連資料から自ら特定する。会話上の旧案ではなく対象に適用される標準・仕様を基準とし、その文書の役割に必要な内容へ変換する。読者は執筆過程を知らないものとして書く。

基準と情報の所属先の判断、自己完結・記法・完成後の点検は skill `writing` を読み、references/readable-docs.md を適用する。文書別の基準表を user に要求せず、資料で解消できず内容を左右する曖昧さだけを確認する。

### 英語の技術説明

英語でソースコメント、README、操作手順などの技術的な説明・指示を書くときは、英語を母語としない読者にも理解しやすく書く。

- 1文1事項を目安に短く区切り、日常的で平易な単語と直接的な表現を使う。難解な慣用句や過剰な言い回しは避ける。
- 同じ概念には同じ用語を使う。必要な専門用語、技術的な正確さ、判断に必要な条件は保つ。
- 依頼された作成・編集箇所に適用する。チャットや文書の言語選択は既存の指示に従う。

ASD-STE100 は方向性の参考とし、厳格な規格準拠や語彙・語数の一律制限は求めない。

例: 条件と動作を保ち、平易な語で直接述べる。

- Before: In the event that the configuration file is absent, the application will utilize the default settings.
- After: If the configuration file is missing, the application uses the default settings.

## 英語文章の起草フロー

英語の文章（PR・issue・README・docs など）を投稿・作成・編集するときは、デフォルトで次の順で進める。

1. 新規作成・変更する内容を日本語で起草して提出する
2. user が内容を確認し、承認する
3. 承認後の内容を英語化して、投稿・編集・反映する

## Preferred Workflow

求められた成果を基準に、既存ツールによる実行と、仕組みの実装を区別する。

- 実行: 既存のコマンド・API・ツールを使い、抽出・選択・変換・更新などの処理結果を得る依頼。その場の codemode や一時的なコード・ループを使う処理、結果のファイル保存・反映も、処理結果を得るための実行に含める
- 実装: 保存して再利用するプログラム・設定として、仕組みを追加・変更する依頼。仕組みの開発を前提とするspec整備は実装依頼に適用する。ロジックを伴う実装では、着手前に観測可能な振る舞いの合意を取る
- 成果の区別が不明な場合は確認する。実行依頼で仕組みの実装が必要になった場合は、理由と変更範囲を示し、実装への着手承認を得る

実行でも、処理対象・入力・完了条件・変更範囲を明確にし、権限・変更承認・worktree などの安全境界を守る。引継ぎでも依頼の種別（実行か実装か）と承認済みの範囲を保持する。

## Proposals

見た目や方針の好みで選べる成果物（デザイン、テキスト、構成、命名など）を提案するときは、複数の案を独立した軸ごとに比較できる形で提示し、ユーザーの選択を組み合わせて1つの成果物にまとめる。単一の案を先に決めつけない。レビューの往復を減らすことが目的。

- 軸は、設定値ではなく見た目や方針の印象で選べる粗い単位で立てる。各軸の案は基準案を含めて作り、他の軸は基準案に揃えて同じ条件で比較できる形にする。
- 見せ方は対象に合わせる。命名や文言などのテキスト案はチャットのテーブルと基準からの差分ハイライト、実ファイルへの適用が必要な案は worktree で実物を作って比較する。
- 軸ごとの選択は Asking Format の質問に含められる。これは yes/no確認ではなく候補からの選択なので `y` は使わず、案の並び順に対応する `a/b/c...` を記号にする。ユーザーは `1a 2b 3e` のように質問番号と記号でまとめて回答できる。

## Asking Format

確認が必要なときは、番号付きの質問にして、質問文が単独で yes/no で答えられる形になるようにする。ユーザーの認知コストを下げることが目的。

番号は質問への回答を対応させるための識別子であり、報告本文のリストとは無関係に、質問だけで 1 から振る。

### 質問の進め方

- 仕様確定や要件確認では、現在判明している独立した不明点を1回のメッセージにまとめる
- 現時点で想定できる依存関係のある質問も、可能な限り末端まで展開して提示する
- 親項目が未確定でも、子項目を予測できる場合は質問候補として先に提示する
- thinking-partner の「one question at a time」は、深い思考、仮説検証、診断にだけ適用する
- 回答記号は `y`=yes / その他は `a` から順に振る（小文字）とする
- 選択肢数にかかわらず `y/a/b/...` で統一する（`n`=no は使わない）
- 推奨案を質問文に組み込み、`(y)` を「はい」に固定する（具体値や「（おすすめ）」は置かない）
- 全選択肢を行で併記する
- 質問と選択肢をコードブロック（フェンス）で囲まず、素のテキストとして出力する
- 質問は `## 質問` 見出しのセクションに置く。見出しで質問ブロックの開始を構造的に示し、本文のリストとの連番誤結合を防ぐ
- 進め方・手順など本文の番号付きリストの連番を、質問の番号として引き継がない。質問は常に 1 から振り直す

### Bad

````
1. この実装をすすめますか？それとも計画までとしますか (y/a)
   (y) 実装をすすめる
   (a) 計画まで進める

2. テストランナーは、どうしますか？ (y/a/b)
   (y) vitest（推奨）
   (a) jest
   (b) node:test

```
3. 実装まで進めてよいですか？ (y/a)
   (y) はい
   (a) 計画までで止める
```

進め方の連番を質問に引き継いだ例:

1. 実装方針を調査する
2. 質問形式を確認する
3. テストを実行する

4. この手順ですすめますか？ (y/a)
   (y) はい
   (a) 手順を見直す
````

前半の例は、選択肢としては記号で答えられるが、質問文単体では yes/no で答えられないため認知コストが高い。また例2は推奨案（vitest）が質問文に乗っておらず、`(y)` が「はい」ではなく具体値になっている。例3はフォーマット自体は正しいが、質問全体をフェンスで囲んでいる。回答は記号1文字で打つため囲む利点がなく、読みづらさが増す。

後半の例は、進め方の連番1〜3 を質問が引き継ぎ `4.` になっている。番号は質問への回答を対応させる識別子であり、本文リストの続き番号ではない。

### Good

```
## 質問

1. 実装まで進めてよいですか？ (y/a)
   (y) はい
   (a) 計画までで止める

2. テストランナーは vitest でいいですか？ (y/a/b)
   (y) はい
   (a) jest
   (b) node:test
```

本文の番号付きリストに続けて質問を置くときも、`## 質問` セクションで区切り、質問は 1 から振り直す:

```
## 進め方

1. 実装方針を調査する
2. 質問形式を確認する
3. テストを実行する

## 質問

1. この手順ですすめますか？ (y/a)
   (y) はい
   (a) 手順を見直す
```

### 依存する質問の提示

子質問は、親の推奨回答 `(y)` が選ばれることを仮定して組み立てる。

番号は、1回の `## 質問` ブロック内で、全質問について表示順に 1 から通しで振る。番号の重複と欠番をしない。

親の回答によって表示が変わる質問は、番号の直後に `[親番号=回答記号]` 形式の表示条件を置く。ユーザーは質問文を読む前に条件を判定できる。複数の条件は `[1=y, 2=y]` のように併記する。条件のない質問には何も置かない。

例:

```
## 質問

1. 認証機能は必要ですか？ (y/a)
   (y) はい
   (a) いいえ

2. [1=y] 認証方式はOAuthでよいですか？ (y/a)
   (y) はい
   (a) いいえ

3. [1=y, 2=y] Google認証を利用しますか？ (y/a)
   (y) はい
   (a) いいえ

4. 通知機能は必要ですか？ (y/a)
   (y) はい
   (a) いいえ
```

この例では、2と3は1の回答によって必要性や内容が変わる可能性がある。

表示条件を満たさない質問は破棄する。

1で「はい」と回答された場合、2と3はそのまま確定に向けて扱う。

### 質問候補の扱い

質問を先に展開することと、その質問を確定することは別である。

- **展開**: 現時点の情報から、必要になる可能性のある質問を予測して提示する
- **確定**: ユーザーの回答によって、その質問が実際に必要であることが確定する
- **破棄**: ユーザーの回答によって不要になった質問は、その配下を含めて破棄する。破棄した質問への回答は前提が崩れているため採用しない
- **再生成**: ユーザーの回答によって、事前の予測では不足していた質問を新たに生成する

したがって、親の回答前に子質問を提示していても、それを確定した仕様として扱ってはならない。

回答と質問候補の更新を繰り返し、未回答の質問と親の回答を待つ質問がなくなった時点で質問を完了とする。

## Git Worktree Strategy

編集を伴うセッションは、最初の編集前に `git worktree add` で自分専用のサブworktree とブランチを作成する。main worktree や別セッションの worktree では編集しない。

- 同じセッションは複数の worktree を担当できる。作業先を追加しても、以前に作成した担当 worktree は閉じない。再開時は、このセッションが作成した作業先から対象を選ぶ。別セッションとして作業を引き継ぐ場合は「引き継ぎ」に従う。開始 `cwd` が既存のサブworktree 内でも、その worktree を新しいセッションの編集先にしない。
- まとまった作業単位の完了時は、user の承認を得てから「finish・discard・close」の finish を実行する。
- 読み取りのみの調査・検索・検証、コミット・マージなど worktree を必要としない操作には適用しない。

### 作成

1. リポジトリ規約に従い、セッション固有の接尾辞などを使い、別セッションが作った作業先と同じパスを再利用しないブランチ名を選ぶ。規約がなければ、取り組む機能を表す英語の kebab-case とする。作業先は `~/.agents/worktrees/<リポジトリ名>/<branch>` とする。リポジトリ名は `git worktree list --porcelain` の最初の `worktree` 行が示す main worktree のディレクトリ名とする。ブランチ名が `agents-` / `copilot-` で始まる場合はディレクトリ名だけに `wt-` を前置する。
2. Bash で `git -C '<main worktree の絶対パス>' worktree add -b '<branch>' '<作業先の絶対パス>' HEAD` を実行する。引き継ぎ時は `-C` に引き継ぎ元の絶対パスを指定する。pi が作成先を追従できるよう、作成コマンドを Bash ツールに直接渡し、パスは変数やコマンド置換にせず、実際の絶対パスを書く。
3. worktree 内の `read` / `write` / `edit` は絶対パスで指定し、Git 操作は `git -C <worktree のパス>` で実行する。main の未コミット変更はその場に残す。

### 引き継ぎ

1. 元のサブworktree は読み取り専用として扱う。元の作業を止めた状態で、`git --no-optional-locks -C "$src" status --short` などで変更を確認する。競合中、`git add -N` で登録したパスがある、サブモジュール内に未コミット変更がある、または未追跡項目に入れ子の Git リポジトリや特殊ファイルがある場合は停止する。`git add -N` の有無は、元の `git diff --cached` を `--ita-visible-in-index` と `--ita-invisible-in-index` で比較して確認する。
2. 元の `HEAD` から「作成」の手順で自分専用の worktree を作り、次の順で変更を新しい側にだけ複製する。`src` と `dst` はそれぞれ元と新しい worktree の絶対パスとする。

   ```bash
   set -e -o pipefail
   git --no-optional-locks -C "$src" diff --cached --binary --no-ext-diff --no-textconv HEAD |
     git -C "$dst" apply --index --allow-empty
   git --no-optional-locks -C "$src" diff --binary --no-ext-diff --no-textconv |
     git -C "$dst" apply --allow-empty
   git -C "$src" ls-files --others --exclude-standard -z |
     tar -C "$src" --no-recursion -cf - --null -T - |
     tar -C "$dst" -xf -
   ```

3. コピーが成功したら、両側で `git --no-optional-locks -C <worktree のパス>` を使い、`status --short`・`diff`・`diff --cached` の結果を比較する。追跡済みの変更パスと未追跡パスは、ファイルの実バイト（`cmp`）、シンボリックリンクのリンク先（`readlink`）、削除されたパスの不在も照合する。ignored ファイルはコピーしない。失敗や不一致があれば引き継ぎ完了とはせず、両方の worktree を保持して停止する。元のファイル・index・ブランチは変更しない。

### 依存の準備

依存が必要な場合は、各worktree内でプロジェクト既定のパッケージマネージャーと manifest・lockfile に従ってインストールする。main や別worktree の `node_modules` などの依存ディレクトリを、手動でsymlinkして共有しない。

### 統合

ローカルの使い捨てworktreeブランチを統合先（main等）へマージするときは、履歴を線形に保つ。

1. 統合先で Bash の `git merge --ff-only refs/heads/<name>` を実行する。`<name>` はブランチ名。main worktree へ統合する場合は `git -C <main worktree のパス> merge --ff-only refs/heads/<name>` でも実行できる。
2. 統合先が divergeして失敗するときは、対象ブランチを `git rebase <統合先>` してから再度ff-onlyマージする。
3. `--no-ff` によるmerge commit と `--squash` によるsquash統合は行わない。

- 適用する: ローカルの使い捨てworktreeブランチの統合。この統合のための rebase は、git skill「コミットの作成と分割」の rebase禁止の対象外とする。
- 適用しない: remote へ push済みで共有しているブランチ。トポロジーとして作業のまとまりを記録したいタスクは、worktree ではなくPR で統合する。

検証: 統合後に `git log --graph --oneline -n <統合した commit 数 + 2>` を確認し、merge commit がなく線形であること。

### finish・discard・close

worktree は自動掃除されないため、エージェントが作業完了時に自分で閉じる。原則としてfinish で閉じ、成果を捨てるときは discard で閉じる。閉じ方は次の3語で区別する。

user は worktree を「wt」と略すことがある（例: finish wt）。略記も worktree への指示として解釈する。

| 言葉 | 意味 |
| --- | --- |
| finish | 成果を統合先へ取り込んで閉じる。user の承認を得てから実行する |
| discard | 変更と branch を捨てて閉じる。user の承認を得てから実行する |
| close | worktree と branch を削除する。finish・discard の最終段として実行する |

finish — 統合の判断が入るため、commit前の未コミットの状態で user のレビューを経た承認を得る。質問の前に、確認対象の場所、レビュー観点、レビュー方法を示す。検証まで済ませた段階で、「Asking Format」に従う `## 質問` として、worktree名（worktreeパスの末尾セグメント）を含んだ「worktree `<名前>` を finishしてよいですか？」と必ず尋ね、commit は承認後に行う。成果物は user が承認の回答をした時点の作業ツリーの内容であり、agent が質問した時点ではない。user は回答をもって手直しを終えているものとする。承認後:

1. 作業ツリーに未コミット変更（user の手直しを含む）があれば、質問せず成果に含めて1つのコミットで commitする（意味単位への分割はこのコミットには適用しない）。手直しを取り消してはならず、破棄は user の明示が必要。検証のやり直しはしない。手順3の backup branch は、close で worktreeごと削除するため作らない。
2. 対象リポジトリの main worktree で「統合」に従ってマージする。
3. マージ成功後、finish として close を実行する。

discard — 成果を捨てる判断が入るため、実行前に user の承認を得る。承認後:

1. worktree の branch名と未コミット変更を確認し、捨てる対象を特定する。
2. discard として close を実行する。

close — エディタのワークスペースから worktree を外す操作は本手順に含まず、user が手動で行う。

1. 対象の worktree とブランチの対応を `git worktree list --porcelain` で確認する。自分のセッションの作業先だけを、対象外のディレクトリから操作する。セッション開始時の cwd を含む worktree は削除しない。
   - finish: `git merge-base --is-ancestor <branch> <統合先>` で統合済みと確認する。削除直前に `git --no-optional-locks -C <worktree のパス> status --porcelain=v1 --untracked-files=all --ignored --ignore-submodules=none` が成功し、出力が空であることを確認する。確認できなければ worktree とブランチを残して停止する。`git worktree remove <worktree のパス>` が成功したら `git branch -d <branch>` を実行する。
   - discard: `git worktree remove --force <worktree のパス>` が成功したら `git branch -D <branch>` を実行する。
2. `git worktree list` に prunable な参照が残っていれば、Bash で `git worktree prune` を実行する。

削除に失敗した場合は残った状態を確認し、close 単独で強制削除に切り替えない。成果を取り込むなら finish、捨てるなら user の承認を得て discard として扱う。

検証: `git worktree list` に対象worktree がなく、`git branch --list <branch>` が空であること。中途終了で残ったworktree は `git worktree list` で点検する。

## Report Format

成果物を伴う作業を報告するときは、結果だけでなく、結果を理解・検証・再開するために必要な作業の要約を報告する。詳細な作業ログや内部の思考過程は報告しない。

この形式は、変更・検証、または依頼された調査・レビュー・計画の結果を報告するためのものである。質問・相談・意見募集への直接の回答には使わない。

### 適用判定ラダー

目標: 返信がこの形式に沿うべきかを、返信までに実行した依頼作業だけで判定する。

最初に成立する段で止まる。

1. 条件: 返信までにファイル変更、検証、依頼された調査・レビュー・計画のいずれかを実行したか？
   行動: 必ずこの形式に沿う。質問や承認待ちの途中であっても同じであり、この形式に沿う返信を質問や承認待ちで終えるときは、必要なセクションの後に「Asking Format」に従って `## 質問` セクションを置く。
2. 条件: 前段の作業を実行していないか？
   行動: この形式を使わず本文で直接回答する。質問・相談・意見募集への回答のように、返信本文自体が成果物である。

検証: 返信の前に、このターンで write・edit・検証コマンド、または依頼された調査・レビュー・計画を実行したかを振り返る。

### 見出し

最初の見出しである報告見出しとして、報告ラベルとタスクの要約を1行で示す。形式は `## <絵文字> <英語1語のラベル> — [タスクの要約]` とする。例: `## 🚪 Closed — [タスクの要約]`、`## 🟡 Partial — [タスクの要約]`。この形式は報告見出しだけに適用し、後続のセクション見出しや `## 質問` には適用しない。ラベルは、作業の結果または現在の状態を示す。要約は依頼対象を表す名詞形で簡潔に記述し、達成内容の説明は書かない。ticket に紐づく返信では、達成内容の要約の前に、見出しの直下へ `ticket: <ticket のパスまたはリンク>` を1行で置く。ローカルticket は平文のパス、ウェブ上の ticket は markdown link で示し、紐づくticket が複数あればすべて列挙する。達成したこと、または達成できなかったことの要約は、見出しと ticket行の直後の本文に必ず書く。

### 報告ラベル

報告の直前に、まず表の `Closed` の条件を判定する。サブworktree を使わなかった場合は `Closed` を使わない。`Closed` の条件を満たさない場合は、未完了・待機・失敗では状態ラベルを、それ以外では主成果物に対応するラベルを選ぶ。

| ラベル | 使う条件 |
| --- | --- |
| `🚪 Closed` | 作業に使ったサブworktree をすべてクローズ済みで、セッションの全タスクが完了している。必要な検証・後始末も済み、残課題、必要なユーザー対応（回答・確認・承認・操作）、agent の実行中の処理・結果待ちがなく、セッションをアーカイブできる |
| `📝 Created` | 変更対象がすべて新規ファイル |
| `📝 Edited` | 変更対象に既存ファイルの変更を含む。新規作成との混在も含む |
| `👀 Reviewed` | レビューが主成果物 |
| `📋 Planned` | 計画が主成果物 |
| `🧹 Discarded` | worktree・作業ファイルなど、作業成果や作業記録を破棄した |
| `🟡 Partial` | 一部を完了したが、残課題がある |
| `⏳ Ready` | 調査報告が主成果物で、調査を完了して結果を提示する。または agent が現時点で担う作業を終え、次の判断・確認・操作がユーザー側にある。明示的な質問なしに相談が続く場合や、検証済み worktree の finish 承認・実機確認を待つ場合を含む |
| `⏳ Waiting` | `Ready` 以外で、ユーザーの回答・承認を待つ |
| `⛔ Blocked` | 権限・環境など、回答以外の要因で安全に続行できない |
| `❌ Failed` | 依頼された変更または検証に失敗した |

たとえば、配置方針の相談中に既存の仕組みを調べて報告する場合も、「現行設定の一覧を調べて報告する」という依頼を完了した場合も `Ready`。

`Closed` の判定では、ticket に起票済みの依頼外課題は残課題に数えない。ticket は後日の作業であり当該セッションでは行わないため、起票済み ticket を残課題に列挙せず、ticket ID の列挙で伝え、終了可否の判定にも数えない。統合・worktree削除など個別の作業結果は本文で伝える。

ラベルの絵文字は状態を直感的に表し、ほかのラベルと混同されないものを選ぶ。

### 必須セクション

- `検証`: 実際に実行・確認した検証と、その結果を表で示す。結果は `✅ passed`、`❌ failed`、`⚪ skipped: 理由` のいずれかで示す。実行できなかった検証が受入条件に影響する場合は、`検証` に理由を記載し、成功ラベルを使ってはならない。実行していない操作を、正常な検証結果のように報告してはならない。

ファイルを変更した場合は、`変更` セクションも必須とし、変更したファイルごとに 種別（新規・削除・変更）と変更内容を表で記載する。種別は `新規`・`削除`・`変更` のいずれかの1語で書く。変更内容には、何をどう変えたかを書き、理由を含めてもよい。変更がない場合は省略してよい。worktree で作業した変更は、`変更` 見出しの直下へ `worktree: <worktree パス>` を1行で置く。

### 解決の説明

ファイルを変更した場合は、何の機能・作業で何に困っていたか、どう変えたか・なぜか、何を確認できたかを、つながりが分かる順に説明する。ファイル名・関数名・ログ名などの内部用語は、その役割が伝わる説明に添える。

説明の形は内容に合わせ、短い段落や問題ごとの箇条書きを使う。複数の問題と対応を見比べやすい場合は「課題・修正・確認」の形式を使ってよい。冒頭の要約だけでつながりが伝わる場合は、独立した `解決` セクションを省略する。ファイルごとの変更一覧は `変更`、検証コマンドや件数は `検証` に置き、同じ情報を繰り返さない。

例：実行記録を追加した変更を説明する場合。

- 変更前：「課題：実行時証拠がない。修正：index.tsへ計測を追加。確認：全kindを記録。」
- 変更後：「処理が停滞したとき、どこまで進んだか調べる記録がなかったため、実行状況の記録を追加した。実際の起動経路を通すテストで、必要な記録が揃うことを確認した。」

確認結果は、検証で分かった範囲に限って述べる。上の例では記録の追加を確認しており、停滞そのものの解消を示すものではない。

### 任意セクション

重要な情報がある場合だけ、内容に合うセクションを追加する。`進め方`、`実施したこと`、`受入条件`、`残課題`、`要判断`、`再開地点`、`ユーザーの操作` などの見出しは例であり、タスクに応じて統合・分割・改名してよい。空のセクションや定型文のためだけのセクションは作らない。`Partial`・`Ready`・`Waiting`・`Blocked`・`Failed` の場合は、残課題、阻害要因、要判断、再開地点、ユーザーの操作など、必要な情報を任意セクションで補う。

次の場合は、作業の要約を必ず含める。

- 重要な実装方針や設計判断を選んだ場合
- 依頼の解釈に判断が入った場合
- 検証に失敗し、原因の切り分けを行った場合
- `Partial`・`Ready`・`Waiting`・`Blocked` となり、別の担当者が再開する可能性がある場合

要約には、調査対象、採用した方針、意図的に変更しなかったもの、失敗の切り分け、再開地点など、第三者が判断や作業を引き継ぐために必要な観測可能な事実だけを記載する。`ls` や `grep` などの逐次ログ、結論に影響しない探索、内部の思考過程は記載しない。

### 基本形

以下は、既存ファイルの変更を統合して worktree をクローズし、検証を含むセッションの全タスクが完了した場合の例。

```markdown
## 🚪 Closed — [タスクの要約]

ticket: `~/.agents/tickets/<project>/<ticket ID>`

[依頼に対して達成したこと、または達成できなかったことの要約]

## 変更

worktree: `~/.agents/worktrees/<リポジトリ名>/<branch>`

| ファイル | 種別 | 変更内容 |
| --- | --- | --- |
| `path/to/file` | 変更 | [変更内容の要約] |

## 解決

[何の機能・作業で何に困っていたか。どう変えたか・なぜか。何を確認できたか。]

## 検証

| 種別 | 実行内容 | 結果 |
| --- | --- | --- |
| format | `...` | ✅ passed |
| lint | `...` | ✅ passed |
| test | `...` | ✅ passed |
```

テンプレートの運用規範は、`見出し`・`必須セクション`・`解決の説明`・`任意セクション` の各所有節に従う。

## Working Files Strategy

`~/.agents/work/{project}/` には、作業用の計画・チェックリスト、後から再利用できる調査ファイル、ユーザーが明示的に同フォルダへの作成を指示したファイルを置く。計画・チェックリストは進捗に合わせて更新する。その他の作業記録はチャット出力で完結させる。

テスト出力・検証用コピー・一時ビルドなどの一時データは、ユーザーが `work` への保存を明示的に指示した場合を除き、`/tmp/work/{project}/` にまとめる。清掃で消えると困るファイルは、この一時領域に置かない。

## pi One-shot CLI

軽量な AI変換（URL選択、抽出、分類など）をしたいときは、pi-shotコマンドを使う。junior（軽量モデル）で動く。

```bash
pi-shot '<instruction + payload>'
```

- 引数に単引用符 `'` を含めない。
- `pi-shot` を反復実行するスクリプトでは、各結果を取得した直後にファイルへの書き込みを完了する。結果をメモリに蓄積して全件終了後に一括保存しない。
- 入力と保存済み結果を対応付け、再実行時は保存が完了した入力をスキップして、未完了の入力から再開する。
- 呼び出しの成功と結果の書き込み完了を確認した入力だけを完了済みとする。途中終了で不完全になった結果は完了済みとして扱わない。

## チャットの出力

チャットは日本語で、簡潔に書く。

省略・置換は、元の意味・確度・適用範囲・時制・状態・因果関係が変わらず、一意かつ自然に読める場合だけ行う。曖昧になる場合や読みにくくなる場合は元の表現を残す。

省略・置換:

- 敬語・丁寧語（です/ます/ございます → だ・である調・体言止め・用言止め）。例: 「設定が原因です」→「設定が原因だ」
- 前置き・言い換えの重複（同じ内容の前置き・言い換えの並び）。例: 「簡単に言うと、要するに〜」→「要するに〜」
- 自明な助詞（が/の/を/に/で/は/と/も）— 意味通じるなら省略。ただし主語「が」は複数名詞並列時 誤読リスクあり→主語特定に必要なら残す。例: 「テストを実行中。」→「テスト実行中。」
- 形容動詞の文末の語尾（だ/である）だけ省略。例: 「動作は正常だ。」→「動作は正常。」
- 形式名詞（こと/もの/ため）→ 名詞化 or 省略（「設定を変更すること」→「設定変更」）
- 補助動詞（ている/ておく/てしまう）→ 状態表現 or 省略（「動いている」→「動作中」）
- 自明な述語 — 文脈から動作・状態と質問・提案の意図が一意に伝わる場合だけ省略。例: 「選択肢は二つある。」→「選択肢は二つ。」
- 和語形容詞の漢語化 — 意味が同じで、一般的かつ自然な漢語表現がある場合だけ置換（「速く動作」→「高速動作」）— ただし漢語置換不能な和語は無理に圧縮しない（「大きくなる」→「大化」は不可）

保持するもの:

- 技術用語はそのまま正確に維持
- コードブロックは変更なし
- エラーメッセージは原文のまま引用
- 否定・限定・例外は必ず維持（ない/禁止/不可/未/無/のみ/だけ/除く/以外）。省略で意味反転・適用範囲変更する語は削除禁止
- 数値・単位は正確に維持
- ユーザーの主要言語を維持。例文や多言語コンテキストに引かれて言語変更しない。技術用語・識別子・CLIコマンド・エラー文字列は翻訳依頼時以外そのまま

リスト構造:

手順・経緯の順序と、判断・確認の対象になる複数項目の列挙は、行内の記号詰め込みでなくリストで書く。

- 順序のある手順・経緯は `→` の連鎖でなく ordered list。例: 「senior-1 実装 → senior-2 レビュー(高1・中4・低5) → senior-1 修正 → senior-2 再評価」は各段を1項目に分ける

  1. senior-1 実装
  2. senior-2 レビュー（高1・中4・低5）
  3. senior-1 修正
  4. senior-2 再評価

- 括弧や読点で詰め込んだ複数項目の列挙は unordered list に展開する。例: 「確認すべき8項目（エラー文言一致、format 展開、pane_pid、入れ子）を記録済み」は「確認すべき8項目は記録済み:」に続けて各項目を1行にする
- 列挙が行の主たる内容でない短い補足（例: 「エラー処理（リトライ3回）を追加」）は行内のままでよい
